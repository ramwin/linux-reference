
## 先回答你的疑问

你这个问题的原始问法是：每个 token 都要和历史上所有 token 做向量计算，才能从候选里选出下一个字，那不就意味着每次推理都要遍历全部 token、访存占比极高？有没有"先按向量的第一维排除一部分内存扫描"的技术？

拆成四问，答案先放这里：

| 疑问 | 一句话回答 |
|------|-----------|
| 每生成一个 token，真的要把历史 KV 全扫一遍？ | **是真的**。而且这一笔访存就是长上下文推理的主要延迟来源：decode 阶段读 KV 占掉 **53%** 的时间，32K 上下文时占整体推理延迟 **50% 以上**（Quest 实测数据） |
| 有没有"按某一维先排除一部分内存"的技术？ | **有，但不是按单维**。单维给不出界（其余维度会抵消），必须用**逐维 min/max 组成的包围盒**算上界；而且排除单位必须是 **page/block 这种连续内存块**，不能是单个向量 |
| 那为什么不直接建向量索引（KD-tree / HNSW）去查？ | 两个方向都不通：**数学上**注意力是"对全部 key 的 softmax 加权求和"，不是 top-k 检索，任何剪枝都是近似；**工程上** GPU 带宽靠连续访问，随机跳着读比顺序全扫更贵；再加上 **d≈128 的维度灾难**，树结构本来就几乎剪不掉东西 |
| 那工业界到底在用什么？ | 四档：**白送档**（GQA / KV 量化 / FlashAttention / MLA）、**免训练剪枝档**（page 级上界剪枝、token 淘汰）、**改架构档**（LSH / SSM）、**系统档**（投机解码 / continuous batching）。详见第四节 |

下面逐条展开。

## 一、先搞清楚一次 decode 到底在读什么

### 1.1 两笔 O(N) 的账

每生成一个 token，模型要做两件"和长度成正比"的事，注意它们扫的**不是一个东西**：

| 扫什么 | 形状 | 量级（LLaMA-2-7B） | 谁受影响 |
|--------|------|--------------------|----------|
| **Attention 扫 KV cache** | 每层每头 `q(1×d) × Kᵀ(d×L)`，再 `×V(L×d)` | 32K 上下文约 **17 GB** | 上下文长度 L |
| **LM head 扫词表** | `hidden(1×d) × W(4096×V)` | 262 MB（V=32000） | 词表大小 V |

你问的"从所有输出里选合适的文字"是第二笔。它确实是 O(V)，但通常**不是主瓶颈**：7B 模型词表 32000 时它只占每 token 权重读取量（约 14 GB）的 2%。只有当词表极大时才值得单独优化（比如 hidden=8192、词表 15 万的模型，这一笔就要读 2.5 GB）。

**真正的瓶颈是第一笔，也就是你说的"遍历所有 token"。** 算一下就知道为什么：

```text
每 token 每层每头: 2(K和V) × 128(头维度) × 2(FP16) = 512 字节
每 token 全部层头: 512 × 32 层 × 32 头            = 512 KB
32K 上下文:        512 KB × 32768                 ≈ 17 GB
```

每生成**一个** token，就要把这 17 GB 从头读一遍。在 RTX 4090 上，Quest 论文测出来**光是读这一遍就至少 11 ms**，占单步解码时间的一半以上；如果 prompt 16K、回答 512 token，整个请求 **86% 的时间花在 decode 阶段**。

所以你的原始直觉是对的：**访存占比确实极高，而且高得离谱。**

### 1.2 为什么这是"访存问题"而不是"算力问题"

用 roofline 模型一算就清楚。A100 80GB 的数是 2.04 TB/s 带宽、312 TFLOPS（FP16）：

- 拐点（等于算力和带宽相配的算术强度）：`312 ÷ 2.04 ≈ 153 FLOP/byte`
- decode 阶段 batch=1 时：每个权重读进来 2 字节，只做 1 次乘加（2 FLOP），**算术强度约 1 FLOP/byte**

**比拐点低两个数量级。** 也就是说 GPU 的算力单元有 98% 以上的时间在等数据，这是一个纯带宽受限的负载。

```{note}
记住这句话，后面所有优化都是它的推论：
**长上下文 decode 的成本 ≈ 读了多少 GB，而不是算了多少次乘加。**
任何不减少"连续内存块搬运量"的优化，在 GPU 上都是负优化。
```

对照 [KV Cache 与 Prompt Cache](./kv-cache.md)：那篇讲的是"怎么不重复**算** KV"，这篇讲的是"算完之后，怎么少**读** KV"。两件事，前者早就是标配，后者还在卷。

## 二、"按第一维排除"：错在哪，对在哪

### 2.1 单维给不出界

注意力分数就是点积：

```text
q · k = q1·k1 + q2·k2 + ... + qd·kd
```

你想"看第一维 `q1·k1` 很小，就把这个 key 排除掉"。问题在于：**其余 d−1 维可能全是反号的大值，把第一维的贡献整个抵消掉。** 单看一维，既不能证明它大，也不能证明它小。

想排除，必须对**剩下的每一维**都拿到上界：

```text
q · k  ≤  Σ |qi| · max|ki|        （i 从 1 到 d，max 在一组 key 上取）
```

也就是说：你得对**一组 key 的每一个维度**维护最大值和最小值，得到一个"包围盒"，再用包围盒算出这组的分数上界。上界低于当前 top-k 阈值，整组跳过。

**这个思路完全正确，而且已经有人在工业级实现里做了 —— 就是 Quest。** 它把 KV cache 按 page（16 个 token）切块，每块维护逐维的 min/max，然后用下面这个估计量给 page 打分。

### 2.2 包围盒怎么算：Quest 的做法

对一个 page，记它所有 key 在第 i 维上的最小值为 `m_i`、最大值为 `M_i`。给定当前 query 的分量 `q_i`，无论 `q_i` 正负，page 内任一 key 的 `q_i·k_i` 都不超过：

```text
U_i = max(q_i · m_i,  q_i · M_i)
```

把每一维累加，就得到**这个 page 里所有 key 的注意力分数上界**：

```text
score_upper(page) = Σ U_i        ≥   max over keys in page (q · k)
```

接下来三步：

1. 只读每块的 min/max 元数据（不读 KV 本体），算出所有 page 的上界；
2. 选出上界最高的 top-K 个 page（token budget，比如 2048）；
3. 只把这 top-K 个 page 的 KV 真正读进显存，在里面做精确注意力。

算一下省了多少内存搬运。设每块 S 个 KV，上下文 L 个 token，共选 K 个块：

```text
只读元数据:      2·M·L/S  字节     （每块只读 min 和 max 两个向量，不是 S 个）
读 top-K 块本体: 2·M·K·S  字节
完整 KV:         2·M·L    字节

比例 = 1/S + (K·S)/L
```

代入 Quest 论文的例子：S=16、上下文 64K、token budget 4K（即 K=256 块）：

```text
1/16 + 4096/65536 = 0.0625 + 0.0625 = 0.125   →  8 倍
```

**访存量降到 1/8，而准确率几乎不掉。** 论文报告：32K 上下文、budget 2048 时，self-attention 延迟降低 **7.03×**，端到端（配 4-bit 权重量化）**2.23×**，在 PG19 / passkey retrieval / LongBench 上精度损失可忽略。

关键前提是**注意力本身极度稀疏**：论文实测，除了最前面两层，**不到 10% 的 token 就足以达到同样精度**（即 >90% 的稀疏度）。这是所有剪枝方法能成立的物理基础 —— 你的"排除一部分内存扫描"直觉，正是建立在这个稀疏性上的。

### 2.3 为什么必须"块级"，不能"逐元素"

这是你的想法和现实之间最大的一个 gap，也是 GPU 和 CPU 的本质差别：

| 剪枝粒度 | 代表做法 | 实际结果 |
|---------|---------|---------|
| 单个向量（一个 token 的 K） | 你说的"按第一维排除" | **负优化**。剩下的元素散在显存各处，每次跳转都是一次 cache miss，带宽利用率掉一个数量级 |
| page / block（连续 16~64 个 KV） | Quest、InfLLM、PagedAttention | **正解**。整块跳过 = 真的少搬了连续内存，带宽直接省下来 |
| channel（维度）级 | Double Sparsity、SparQ | 有效但需要专门的硬件/内存布局支持，通用性差 |

原因就一句话：**GPU 要跑满带宽，必须做 128 字节对齐的连续访问（memory coalescing）。** 你把"顺序流式读"变成"随机跳着读"，理论上是少读了 90%，实际上可能比全读还慢。

所以正确的表述不是"按维度排除一部分内存扫描"，而是：

> **按块维护逐维的上下界，用上界判断哪些块不可能进 top-k，整块跳过。**

前者是数据结构思维（CPU 友好），后者是访存思维（GPU 友好）。**在 GPU 上，省"比较次数"没有意义，省"字节数"才有意义。**

## 三、为什么"精确剪枝"不可能：四条硬约束

### 3.1 注意力是求和，不是 top-k 检索

softmax 的输出永远不会精确等于 0，每个 token 都对结果有贡献：

```text
attention output = Σ_i  softmax(q·ki / √d) · vi
```

你没法说"这个 token 权重太小，当我没看见"—— 少一项就是少一项。所以：

- 所有剪枝方法**必然**是近似的；
- 误差会随层数**累积**（32 层，每层差一点，最后差很多）；
- 每生成一个 token 就重新选一次，误差还会随自回归步数**放大**。

这就是为什么 H2O 那类"按历史注意力分数淘汰 token"的方法，在 passkey retrieval 这种需要远程召回的任务上会直接崩掉（Quest 论文的表 1 里，H2O/TOVA/StreamingLLM 在 10K passkey 上的准确率是 0%~3%，Quest 是 99%）。**关键 token 可能"现在没用、以后有用"，按历史分数淘汰会把它永久删掉。**

### 3.2 维度灾难：树结构在 d≈128 时基本失效

你可能会想：那用 KD-tree / ball tree 精确查最近邻不就行了？

不行。高维空间里，**最近邻和次近邻的距离差会趋于 0**（所有点几乎一样远），任何基于距离剪枝的树结构，剪枝率都会崩塌，最终退化成线性扫描。KD-tree 在 d=10 以内好用，d=128 时和全扫没区别。

这也是为什么工程上没人给 KV cache 建树，而是用"page 级 min/max"这种**没有剪枝结构、只有上界估计**的 O(1) 元数据 —— 它的构造是增量的（新 token 进来就更新对应块的 min/max，代价 O(d)），不像 HNSW 那样要付出图插入的成本。

### 3.3 query 每一步都在变，任何"预建索引"都在过期

检索系统里索引可以离线建好、查询时反复用。注意力里没有这个前提：

- 每一步的 query 都是**全新**的；
- KV cache 本身还在**增长**；
- 所以任何"针对某个 query 建好的索引"只能用一次。

这直接判了很多 ANN 方案的死刑：建索引的成本摊到一次查询上，还不如直接扫。

### 3.4 那还有一条路：把"读"这个动作本身变小

既然不能少读几个，那就让每个"读"变便宜：

- **KV 量化**（KIVI 等）：FP16 → 2/4 bit，字节数直接砍到 1/8~1/4；
- **GQA / MQA**：多个 query 头共享一组 KV 头，KV 头数除以共享比例；
- **MLA**（DeepSeek-V2）：把 KV 压成一个低秩 latent 向量，论文报告 **KV cache 减少 93.3%**、最大生成吞吐提升到 **5.76 倍**。

这一类是"从源头让要读的东西变少"，没有近似误差，代价是需要模型架构支持（MLA 要重训）。**这也是为什么 DeepSeek 的长上下文成本能比同行低一个量级 —— 不是推理引擎更强，是模型结构上少存了一个数量级。**

## 四、技术光谱：从白送到重训

按"落地难度"排，同一个目标（少读内存）的四条路：

| 档位 | 技术 | 具体砍掉什么 | 要重训? | 精度 | 落地成本 |
|------|------|-------------|---------|------|---------|
| **L0 白送** | GQA / MQA | KV **头数**减少 4~8× | 模型自带 | 无损失 | 选对模型即可 |
| L0 白送 | KV 量化（KIVI） | 每元素 16 bit → 2~4 bit | 不用 | 极小 | 换推理引擎参数 |
| L0 白送 | FlashAttention | 不砍量，砍 HBM 往返次数（分块 + 不落盘中间矩阵） | 不用 | 无损失 | 库默认开 |
| L0 白送 | PagedAttention | 不砍量，砍碎片浪费，顺带成为块级剪枝的基础设施 | 不用 | 无损失 | vLLM 默认 |
| **L1 免训练剪枝** | **Quest** | **page 级上界剪枝**，访存降到 `1/S + KS/L` | 不用 | 近无损 | 中（要改 attention kernel） |
| L1 免训练剪枝 | InfLLM / Double Sparsity | block 级 + 代表 token / 维度稀疏 | 不用 | 小 | 中高 |
| L1 免训练剪枝 | H2O / SnapKV / TOVA | 按注意力分数**永久淘汰** token | 不用 | **有风险**（远程召回会崩） | 中 |
| L1 免训练剪枝 | StreamingLLM | 只留 attention sink（最前面几个 token）+ 最近窗口 | 不用 | 长文会遗忘 | 低 |
| L1 免训练剪枝 | PQCache / RetrievalAttention | 乘积量化 + 对 KV 建 ANN 索引命中 | 不用 | 中 | 高 |
| **L2 改架构** | **Reformer LSH** | 把 q/k 哈希到桶，只在桶内算注意力 | 要 | 有损 | 很高 |
| L2 改架构 | MLA（DeepSeek-V2） | KV 压成低秩 latent，**-93.3%** | 要 | 无损失 | 改架构 |
| L2 改架构 | 稀疏注意力（Longformer / BigBird） | 固定连通模式 | 要 | 有损 | 高 |
| L2 改架构 | Mamba / SSM / 线性注意力 | 从根上消灭 O(L²) | 重训 | 换赛道 | 极高 |
| **L3 系统** | **投机解码** | 一次访存验证 k 个候选 token，**每输出 token 访存 ÷k** | 不用 | 无损失 | 低 |
| L3 系统 | Continuous batching | batch↑ → 权重读摊到 32 个请求上，算术强度↑32× | 不用 | 无损失 | 低（vLLM 默认） |
| L3 系统 | PD 分离（prefill/decode 分机） | 让访存密集和算力密集各用各的硬件 | 不用 | 无损失 | 高 |

顺着看下来会发现一件事：**L3 的"投机解码"其实最直接地回答了你的问题。** 它不减少任何一次扫描，但它让**一次扫描产出多个 token** —— 每输出一个 token 的访存成本直接除以接受长度。这和"少读几个 KV"是同一个目标的另一种解法：**要么每次少读，要么每次多产出。**

## 五、怎么选：按场景直接抄

| 你的场景 | 直接抄这一套 | 预期收益 |
|---------|-------------|---------|
| 只是自建服务、跑开源模型 | GQA 模型 + KV 量化 + vLLM（PagedAttention + continuous batching）+ 投机解码 | 吞吐通常几倍到十几倍，**零精度损失** |
| 长上下文（32K+）、要省钱 | 上面一套 + Quest 式 page 剪枝（或换 DeepSeek 这类 MLA 模型） | 长上下文延迟再降 2~7×，精度近无损 |
| 要极致吞吐、能改模型 | MLA / GQA + 更小 KV + 量化 | KV 直接降一个数量级 |
| 只想验证原理 | 用纯 Python 模拟 page min/max 上界选择 | 能直接看到跳过比例和误差累积 |

**明确不建议的**：给 KV cache 建 KD-tree 做精确最近邻检索。数学上不成立（注意力不是 top-k），工程上必然负收益（随机访问打崩带宽），维度上也失效（d=128 无剪枝率）。

**一个反直觉但很重要的判断标准**：评估任何长上下文加速方案时，先问一句"它减少了多少**连续内存搬运量**"。减少比较次数的不算，减少随机访问的算负分。

## 六、一句话总结

- **你的理解基本正确**：每生成一个 token 确实要扫一遍全部历史 KV，而且这笔访存就是长上下文推理的主要成本（decode 阶段占 53% 时间）；
- **"按第一维排除"单维不成立**，但它的正确版本——"逐维 min/max 包围盒 + 整块跳过"——就是 Quest 在做的事；
- **剪枝单位必须是 page/block 这类连续内存块**，逐元素剪枝在 GPU 上是负优化；
- **所有这类方法都是近似**，因为 softmax 是求和不是 top-k，误差会随层数和步数累积；
- **最便宜的三招**（GQA、KV 量化、continuous batching + 投机解码）零精度损失、开箱即用，先把这三招吃满，再考虑 page 剪枝。
