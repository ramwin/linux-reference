## 一句话答案

| 问题 | 回答 |
|------|------|
| DeepSeek 缓存的 TTL 是多少 | **没有公开的固定值**。官方口径只有一句"缓存不再使用后会自动被清空, 时间一般为几个小时到几天" |
| 同一会话隔多久再问还会命中 | 几分钟内必中; 一两小时内大概率中; 隔夜(十几小时)看运气; 隔两三天别指望 |
| 决定命中的是不是"间隔" | **不是**。是"前缀有没有变" + "缓存有没有被淘汰"; 时间只影响后者 |

一句话: 缓存的"保鲜期"不是一个数字, 时间只是淘汰概率的一个因子, 真正决定命中与否的是**你那串前缀还在不在、坏没坏**。

## 一、官方口径: 只有区间, 没有 SLA

DeepSeek 上下文硬盘缓存文档里, 和"多久"相关的只有这两条([官方文档](https://api-docs.deepseek.com/zh-cn/guides/kv_cache)):

> 1. 缓存系统是"尽力而为", 不保证 100% 缓存命中
> 2. 缓存构建耗时为秒级。缓存不再使用后会自动被清空, 时间一般为几个小时到几天

注意三件事:

- **没有可配置、可查询的 TTL**, 也没有"续期"接口。生命周期完全由平台内部决定, 你在代码里调不了;
- 措辞是"**不再使用后**"才清空 —— 隐含"一直在用就一直留着"的方向性保证, 但这不是承诺;
- "尽力而为"意味着"昨天同样的前缀还能命中, 今天 miss 了"**不算 bug**, 这是文档写明的行为。

所以对"一个会话里多久之内再问会命中"这个问题, 唯一诚实的答案是: **没有保证的阈值, 只有概率上的"越近越稳"**。

## 二、为什么给不出精确数字

缓存不是靠"一条定时器"过期的, 而是和容量淘汰耦合在一起的:

1. 缓存条目占显存和硬盘, 池子容量有限, 淘汰通常是 **容量上限 + LRU + 时长阈值** 一起起作用;
2. 池子是**多租户共享**的 —— 这段时间别人把池子挤满了, 你的前缀就可能提前被挤出去;
3. 命中还依赖**路由**: 请求要落到持有这份缓存的那台机器上才可能命中。OpenAI 的文档把这点写得很直白("cached states live on individual machines"), DeepSeek 没有明写, 但"尽力而为"基本就是这个意思。

三条叠在一起, 结果就是一个区间(几小时~几天), 而不是一个可承诺的参数。

## 三、比时间重要得多: 前缀有没有被写脏

DeepSeek 的命中规则只有一条: **本次请求的前缀, 必须完整匹配一个已经"落盘"的缓存前缀单元**。落盘有三个时机:

| 落盘时机 | 说明 |
|----------|------|
| 请求结束位置 | 每次请求在**用户输入结束处**和**模型输出结束处**各产生一个缓存前缀单元 |
| 公共前缀检测 | 系统发现多次请求共有某段前缀时, 把这段公共前缀单独落盘 |
| 固定 token 间隔 | 长输入/长输出按 token 间隔切片, 避免长前缀永远等不到"结束位置"而完全不可缓存 |

由此可以推出下面这张表 —— 它和"隔了多久"完全无关, 只和"前缀一不一致"有关:

| 场景 | 是否命中 | 原因 |
|------|----------|------|
| 同一会话继续追问(历史只追加) | **命中, 命中前面全部** | 旧前缀被完整复用, 新增的只有尾部 |
| 会话中途删掉/改写早期消息 | 从改动点往后**全部 miss** | 改动点之后不再是同一个前缀 |
| 每轮在最前面插一句"当前时间" | **全 miss** | 第一个 token 就不同了 |
| 新开会话重发同一份长文档 | 第一次 miss, **第二轮起命中** | 公共前缀检测把"system + 文档"落了盘 |
| 换模型 / 换接口版本 | miss | 是另一套缓存 |
| 超长会话被客户端截断历史 | 通常整体 miss | 截断点之后的位置关系变了 |

实践结论很朴素: **稳定内容放前面, 每轮变化的内容放后面**。这一条比任何"多久之内问"的口诀都有用。

## 四、本机实测: 长会话里的命中率有多高

拿本机 DSH 的历史会话记录统计(数据来自 `~/.dsh/sessions/` 下的 `session.v4.jsonl.zstd`, 每个 step 都带 usage):

| 会话 | step 数 | 新增输入(未命中) | 命中缓存 | 命中率 |
|------|---------|------------------|----------|--------|
| fe710230 | 318 | 383,730 | 63,569,664 | 99.4% |
| 757b51aa | 254 | 191,128 | 39,288,832 | 99.5% |
| 2ec290d2 | 140 | 105,098 | 10,840,064 | 99.0% |
| 30c34ef1 | 90 | 124,984 | 9,861,888 | 98.7% |
| 8fdbfccc | 110 | 115,300 | 6,520,832 | 98.3% |
| 682b13cc | 116 | 94,014 | 5,248,512 | 98.2% |

全机会话累计: 1334 步, 未命中输入 145 万 token, 命中缓存 1.5 亿 token, **整体命中率 99.0%**。

这组数字说明两件事:

1. **同一会话内连续追问, 缓存几乎是白送的** —— 每步真正按全价付的只有几百到几千 token(新问题 + 新工具结果), 历史上下文全部 1/10 价甚至更低;
2. **DSH 每轮注入的 AGENTS.md、memory 索引、运行时快照并没有打断前缀** —— 如果这些内容嵌在前缀中间且每轮都变, 命中率会立刻掉到个位数。实测 99%, 说明注入位置在末尾或者内容本身稳定。

注意: 上表是"连续跑一个会话"的数据, **不能**用来证明"隔 N 小时还能命中"(这些会话里 step 间隔都是秒级)。跨会话、跨天的时效, 官方没给数, 实测也没法在本地复现, 只能按"几小时到几天"的区间去预期。

## 五、怎么自己验证命中情况

**API 侧**: 响应 `usage` 里有两个字段, 看它们就够了:

```json
"usage": {
  "prompt_tokens": 28288,
  "prompt_cache_hit_tokens": 27776,
  "prompt_cache_miss_tokens": 512,
  "completion_tokens": 1024,
  "total_tokens": 29312
}
```

**DSH 侧**: 会话文件是 zstd 压缩的 jsonl, 一行一个 step, 每个 step 的 `usage` 里是 `inputTokens`(未命中)、`cacheReadTokens`(命中)、`outputTokens`:

```bash
for f in ~/.dsh/sessions/*/*/session.v4.jsonl.zstd; do
  name=$(basename "$(dirname "$f")")
  zstdcat "$f" 2>/dev/null \
    | grep -o '"usage":{"inputTokens":[0-9]*,"outputTokens":[0-9]*,"cacheReadTokens":[0-9]*' \
    | awk -F'[:,]' -v n="$name" '{i+=$3; c+=$7; k++} END{if(k) printf "%-40s steps=%-4d miss=%-7d hit=%-9d rate=%.1f%%\n", n, k, i, c, c*100/(i+c)}'
done
```

(`-F'[:,]'` 之后 `$3` 是 inputTokens、`$5` 是 outputTokens、`$7` 是 cacheReadTokens。)

如果某个会话命中率明显偏低, 优先怀疑: 每轮在开头注入了变化内容、历史被编辑/截断、或者换了模型。

## 六、一句话总结

**缓存没有"保鲜期", 只有"前缀一致 + 没被淘汰"。** 时间只决定淘汰风险, 不决定能否匹配 —— 想省钱的正确姿势不是"趁热赶紧问", 而是"别让前缀变"。
