# Agent 测试系统的意义与"通用 DAG"辨析

把 AI 大模型当做一个人：对人的训练都可以抽象成"给他知识、让他工作"。那么做 Agent 测试系统有什么意义？直接做一个通用 DAG 是不是就能完成任何工作？AI 自动生成 DAG 之后是不是就通用了？Agent 开发者会失业吗？本文记录这组讨论。

## 一、测试系统的意义：考核 ≠ 培训

"给人知识、让他工作"这个抽象漏掉了一半：人除了培训，还需要**考试、试用期、绩效考核、质检**。原因是人的能力是不可直接观测的黑盒——不能看一个人的大脑就知道他会不会犯错，只能通过"让他做题、看他产出"来度量。

大模型把这个特点放大了：

- **非确定性**：同一个人、同一道题，昨天答对今天可能答错（temperature、上下文扰动）。人的波动小，模型的波动大得多。
- **版本漂移**：人毕业后再培训的频率很低；模型 provider 悄悄升级一次，整个 agent 的行为可能就变了。
- **能力边界未知**：人可以问"你学过这个吗"，模型永远是"自信地回答"，包括它不会的东西。

所以测试系统（eval 体系）的意义不是"让它工作"，而是**建立信任度量**：上线前知道能力边界在哪，上线后发现回归，迭代时证明新 prompt 真的更好而不是碰巧更好。没有 eval 的 agent 迭代，本质上是在碰运气。

## 二、通用 DAG 能完成任何工作吗？

不能。DAG 表达的是**已知的流程**，而 agent 要解决的恰恰是**流程事先未知的任务**。

- 如果一个任务的步骤可以被人穷举并写死成 DAG，那这个任务本来就不需要"智能"，传统的程序/工作流引擎早就解决了。把 LLM 塞进 DAG 节点，只是给确定性流程加了几个会犯错的节点，不确定性并没有消失。
- 真实任务（修一个没见过的 bug、调研一个陌生领域）的关键步骤是"走到一半才知道下一步干什么"。这需要动态规划（ReAct / planner），DAG 的静态拓扑表达不了"根据观察结果决定后续分支数量和内容"。

所以 DAG 和 agent 不是替代关系，是分工：**流程可枚举的部分用 DAG（可预测、可审计），开放部分用 agent**。真正难的也不是编排拓扑，而是每个节点里的上下文工程、工具设计、错误恢复——换一个 DAG 框架并不能省掉这些。

## 三、AI 自动生成 DAG，是不是就通用了？

"根据上下文生成下一步任务"和"AI 自动生成 DAG"这两条路线都已经存在，并且**收敛成了 agent 本身**：

- 动态生成下一步 = ReAct 循环，最原教旨的 agent 定义：观察 → 想一步 → 做一步 → 再观察。
- 自动生成 DAG = Planner-Executor 架构（Plan-and-Execute、LLMCompiler 这类）：先让模型把计划展开成 DAG 再执行，走偏了重新规划。

所以结论不是"通用 DAG 取代 agent"，而是 **DAG 动态化之后收敛成了 agent**。编排层的形态之争是伪命题，最后大家都是"模型在某个循环里决定下一步"。

瓶颈不在架构，在三个更硬的地方：

1. **错误沿计划放大**。静态 DAG 错一个节点，影响是局部的；自动生成的计划第一步规划错了，后面整条链都在错误前提上执行。规划自动化程度越高，**验证层（verifier）越关键**——而验证本身是难题：代码任务好验证（跑测试就行），"写一份市场分析"谁来判断好坏？这就是 generator-verifier gap：模型生成能力普遍强于自我验证能力。
2. **可审计性与安全边界**。人写的 DAG 是白名单：能调什么工具、花多少钱、访问什么数据，一眼可见。模型现场生成的流程是黑名单逻辑——得防它做出任何没预料到的动作。金融、运维这类场景不敢用纯动态规划，不是技术不够，是治理不允许。
3. **状态与上下文**。长任务跑到一半，上下文里该保留什么、丢弃什么，计划怎么表示成模型能持续操作的中间状态——比"生成下一步"本身难得多，目前也没有通用解。

工程实践因此收敛到**混合架构**：高层骨架由人或模板定死（可控、可审计），骨架内部的局部步骤允许模型动态决策（灵活性），外面再套一层 checkpoint + verifier + eval。纯动态 agent 目前只在"可验证、可回滚、失败代价低"的场景（写代码、查资料）真正好用。

## 四、Agent 开发者会失业吗？

不会消失，但工作内容在迁移。历史上每次抽象层级提升（汇编 → 高级语言 → 框架 → 低代码），消失的都是"重复搬运"的部分，留下的是离问题本质更近的部分：

- **在贬值的**：手写 prompt 雕花、堆 if-else 补模型短板、自己造编排轮子。
- **在升值的**：上下文工程（给模型什么信息比怎么问重要得多）、工具/API 设计、**评估体系**、护栏与成本控制、把领域知识结构化喂给 agent 的能力。

一个证据：模型越强，eval 越重要而不是越不重要。弱模型不行就肉眼可见；强模型"看起来都行"，只有系统化的测试才能区分 90 分和 95 分——而生产环境里 90 分往往就是不可用。

## 五、结论

知识和工作只是 agent 的"供给端"，测试是"验收端"；DAG 只能编排已知，agent 的价值在于探索未知；而"AI 自动生成计划"没有让测试系统变得多余，反而让它从"验收端"变成了**运行时的一部分**（verifier、checkpoint、在线 eval）。规划质量怎么度量、verifier 靠不靠谱、回归怎么发现——每一步都指向测试和评估体系，这正是 Agent 工程化里壁垒最深的部分之一。
