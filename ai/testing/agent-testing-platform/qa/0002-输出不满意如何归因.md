# 0002 平台输出不满意,怎么定位是模型 / 平台 / prompt / 资料的锅

## 一、问题

七阶段管线已经跑起来了,但**对输出结果不满意**。问题不是"哪里要改",而是**怎么知道是哪里该改**:是模型不行、平台设计不对、prompt 不行,还是输入资料不行?有没有可对比的维度、可量化的口径?

**提问时的上下文**(影响结论的前提):

- 场景:云服务集成验证测试(控制台 API + 云资源 + 多租户 + 计费/鉴权跨服务链路);
- 现状:七阶段契约已落地(见 [../README.md](../README.md)、[../architecture.md](../architecture.md)),但**归因手段基本是"换个模型试试""改改 prompt 再跑一遍"**;
- 已有资产:[../case-redis-upgrade.md](../case-redis-upgrade.md) 这类案例、"强制证据"纪律、评审与生成分离的拓扑设计;
- 缺的:失败样本库、阶段级指标口径、以及"每份产物用的是哪版资料/哪版 prompt/哪个模型"的指纹记录。

## 二、外部模型回答

## 三、内部模型回答(原样贴)

### 1. 先纠偏:四类不是选项,是可单独替换的因子

"是模型问题还是平台问题"这个问法注定得不到答案,因为四类因素在真实管线里**同时存在且互相遮蔽**。正确做法是把它们做成**可以一次只动一个的旋钮**,然后看指标怎么动——归因不是分析出来的,是消融(ablation)出来的。

因子清单要比提问里的四类多两格:

| 因子 | 具体含什么 | 为什么必须单列 |
|---|---|---|
| M 输入资料 | 需求文档、OpenAPI、错误码表、changelog、历史用例;**含是否被检索到、版本是否过期、歧义程度** | 云服务测试里"漏测"十有八九是资料没写清楚,不是模型笨 |
| P prompt | 指令、约束、few-shot、上下文顺序、压缩策略、schema 注入 | 最容易过拟合、最容易背锅 |
| L 模型 | 型号 + **版本指纹** + 温度/采样 + 长上下文能力 + JSON 稳定性 | provider 会静默升级,今天好明天坏 |
| S 平台设计 | **S1 执行层**:契约 schema、拓扑、工具、重试、门禁;**S2 度量层**:golden 集、指标口径、judge 校准 | 两者坏法完全不同,S2 坏了最隐蔽——你连"不满意"都量不出来 |
| E 环境/被测系统 | 控制台状态机、配额、网络、租户数据、执行机 flaky | 集成验证里"失败"常常是环境,不单列就会算到模型头上 |

### 2. 平台设计的坏法 checklist(用户问的"平台问题"具体指什么)

| 编号 | 坏法 | 典型症状 |
|---|---|---|
| S1-1 | 契约缺字段(如没有 `evidence` / `source` 字段) | 模型**无处**写出处,只能编 → 看着像模型幻觉,其实是契约逼的 |
| S1-2 | 生成-评审同源(同模型、同材料、同会话) | 评审拦截率虚低或全误报,自评自过 |
| S1-3 | 上下文装配粗糙(几万行 OpenAPI 整段塞入) | 中段信息丢失(lost in the middle),换多长上下文的模型都没用 |
| S1-4 | 阶段间串了对话历史 | 下游面对不确定输入,结果无法复现 |
| S1-5 | 重试/解析策略静默降级 | 解析失败悄悄退化成"只输出通过",指标反而好看 |
| S1-6 | 门禁阈值过松或过严 | 质量退化不报警 / 好模型进不来 |
| S2-1 | golden 集是"AI 自己的输出"当期望值 | 同源污染,越回归越退化 |
| S2-2 | 指标是单分数 | "多写 200 条没用的用例"与"漏 3 个 P0"得分相同 |
| S2-3 | judge 未与人工校准 | 指标漂移被误读成模型退化 |
| S2-4 | 产物没有 (资料版本, prompt 版本, 模型指纹) 三元组 | 事后归因根本不可能,只能重跑猜 |

### 3. 指标:分层,并且漏和错分开计

L0 端到端(发布结论是否正确、漏到线上的缺陷)——**太粗,没有归因信息**,只用于对外的置信度。
L1 阶段级指标——归因主力,每阶段 2~3 个。
L2 行为级——证据命中、schema 合规、澄清项数、token、跨次方差。

每阶段的 L1 指标(定义要能算出分母):

| 阶段 | 主指标 | 定义 | 归因价值 |
|---|---|---|---|
| 1 需求理解 | 需求点召回率 | 命中定稿需求点 / 定稿总数 | 全模型都低 → 资料缺或没写 |
| | 虚假需求率 | 无出处需求点 / 全部需求点 | 该列率 |
| | 出处命中率 | 引用文件+章节真实存在且相关 / 全部引用 | 低 → 上下文/RAG/资料问题 |
| 2 用例生成 | 需求点覆盖率 | 有用例的需求点 / 全部需求点 | 覆盖不了 → 阶段 1 契约丢字段(平台) |
| | 维度覆盖率 | 已覆盖的(正常/边界/权限/状态/回滚) / 5 | 覆盖了需求但没展开矩阵 → prompt 模板缺矩阵约束 |
| | 证据命中率 | 预期结果带可核验出处的 / 全部预期结果 | 低且契约里没有 evidence 字段 → 平台契约问题 |
| 3 用例评审 | **阻断精确率** | 人工复核认为真该阻断的 / 全部阻断 | 低 = 误报多,prompt 太宽或门禁太松 |
| | **阻断召回率** | 该拦且被拦的 / 该拦总数 | 低 = 检测器失效,主要看是否同源 |
| 4 脚本生成 | 首次可执行率 | 一次通过静态检查+能跑 / 全部 | 低 → 模型或框架约定没给 |
| | 断言保持率 | 断言未被弱化成 log 的用例 / 全部 | 断崖下降 = 模型"逃避行为" |
| 6 失败分诊 | 根因命中率 | 与缺陷单最终归因一致 / 全部 | 混淆矩阵直接给量级 |
| | 置信度校准 ECE | 预测置信度与实际正确率的偏差 | 高置信度错 = 比低置信度错更危险 |
| 7 报告 | 事实一致性 | 结论能在上游结构化产物里找到依据 / 全部结论 | 低 → prompt 没锁"不许新增结论" |

量化"好坏"时三条纪律:

1. **不要单分数,用向量 + 字典序**:质量向量 = (P0漏, P1漏, 事实错, 编造, 证据缺失, 契约不合规, 可执行性)。比较两个配置时先比 P0 漏,再比编造……测试领域漏测代价远高于多测。
2. **先算噪声底**:同配置、同输入跑 k=3~5 次,报 mean ± std。两个配置差异小于跨次 std 就是噪声,不是改进。**大量"这次感觉好了"是单次采样的统计假象。**
3. **错因码位**:把"不满意"变成可统计的分布。建议一套有限标签:`N` 漏(该有没)、`W` 事实错、`H` 编造无出处、`S` 契约不合规、`E` 证据不可溯、`D` 降级/逃避、`F` 环境 flaky、`T` 截断/上下文丢失。归因 = 看分布 shift。

### 4. 归因方法:从便宜到贵

**① 噪声底(半天,先做)。** 同配置重跑 3 次。若离散度大到覆盖你想观察的差异,先解决采样/温度/上下文顺序,别谈归因。

**② 缺料敏感度(资料问题的金标准)。** 主动抽掉半份资料(去掉错误码表 / 把 changelog 全文换成 300 行摘录),看指标掉多少:
- 补全资料后指标显著上升 → **资料问题**;
- 补全了也不涨 → 不是资料问题,别再往这儿投入。

**③ 错误集重合度(区分系统性 vs 模型能力)。** 换模型后算两批错误的 Jaccard:
- 同一批错都错 → 系统性(资料 / 契约 / prompt);
- 错法各不相同 → 模型能力或口味问题。

**④ 生成-评审交叉(定位检测器)。** 评审召回低 + 生成召回低 → 看是否同源(换成另一个模型当评审);若换评审后指标回升,是 **S1-2 平台拓扑问题**,不是模型。

**⑤ 部分因子实验(2^k,只跑 8 组)。** 4 因子 2 水平,估主效应 + 交互项。**强交互是最重要的信号**:比如"只加 evidence 字段不换 prompt"就把证据命中率拉上去,说明根因是契约缺字段,而不是 prompt 写得不好。

**⑥ judge 校准。** 任何靠 LLM 打分的指标,先人工标 50~100 条算 Cohen's kappa;多厂商 judge 交叉,分歧当置信度而不是当结论。

**⑦ 版本指纹 + 漂移告警。** 产物元数据必须带 (资料版本, prompt 版本, 模型名+版本+温度)。同 golden 集每周跑一次 baseline,只跌不涨就是 provider 静默升级——这类"退化"和你改的任何东西都无关。

### 5. 现象 → 一次判定实验(可当 ops 手册用)

| 现象 | 先怀疑 | 一次判定实验 |
|---|---|---|
| JSON 解析失败率高但内容看着对 | L 或 S1-5 | 同 prompt 换模型 + 开 JSON mode;全好 = 契约没做 schema 兜底(平台) |
| 漏掉整类维度(如跨租户越权)且所有模型都漏 | M 或验收口径 | 补鉴权矩阵/错误码表再跑,看召回是否升 |
| 漏了的点,模型**标了"需澄清"** | **M,且模型行为正确** | 这不是模型的错:资料没写清。回填文档后重跑该节点 |
| 漏了的点,模型**直接编了** | P 或 L | 检查有没有"不许编造/必须给出处"约束、契约有没有 evidence 字段 |
| 评审意见多但人复核多为误报 | P(评审模板)或 S1-6 | 算精确率;若 <0.5 且分不清阻断/建议 → prompt 分级粒度不够 |
| 每次跑结果差异很大 | 采样/上下文顺序 | k=5 离散度;固定 temperature 后是否收敛 |
| 长文档(几万行)表现差 | **S1-3 上下文装配** | 同模型:喂全文 vs 喂检索片段(同预算 token),比较指标 |
| 今天好明天坏 | L 版本漂移 | 版本指纹 + golden 集周期性 baseline |
| 断言被弱化成 log 输出 | P 或 L(逃避行为) | 算断言保持率;降 prompt 温度/加"禁止修改断言"是否回升 |

### 6. 一个符合主题的例子:Redis 7 升级集成验证的用例生成

**现象**:发布前验收,人工在阶段 2 产出上补了 14 条用例,其中"升级中配额/计费一致性"和"跨 AZ 切换后不重复计费"整类缺失。团队判定"AI 输出质量不满意"。

**做 4 因子 2 水平、8 组部分因子,k=3 重复**:

- M:changelog 摘录 300 行 vs 全文 1200 行 + 错误码表 + 计费口径文档;
- P:模板 v1(无矩阵要求)vs v2(显式 正常/边界/权限/状态/回滚 + 强制 evidence);
- L:内部主力 A vs 备选 B;
- S:契约无 evidence 字段 vs 有 evidence + 强制"需澄清"字段。

示意结果(数字仅示意,不是实测):

| 配置 | 需求点召回 | 维度覆盖 | 证据命中 | 评审阻断精确率 |
|---|---|---|---|---|
| baseline | 0.71 | 3/5 | 0.55 | 0.48 |
| + 完整资料 | **0.86** | 3/5 | 0.62 | 0.52 |
| + prompt v2 | 0.74 | **5/5** | **0.93** | 0.71 |
| + 换模型 B | 0.69 | 3/5 | 0.51 | 0.44 |
| + evidence 契约 | 0.71 | 3/5 | **0.90** | 0.68 |
| 全因子 | 0.91 | 5/5 | 0.96 | 0.79 |

读法:

1. **资料是召回主因**:+0.15,且换模型(B)几乎不动 → 模型不是召回瓶颈;
2. **prompt 是维度覆盖主因**:3/5 → 5/5,但召回只动 0.03 → prompt 只修"展开不细",修不了"不知道有这么个点";
3. **契约缺字段是平台缺陷**:只加 evidence 字段、不动 prompt,证据命中就从 0.55 到 0.90(prompt 独立贡献只有 0.93-0.90 的一小截)→ 根因是"契约里没有地方写出处",属于 S1-1,不是模型幻觉;
4. **换模型 B 全面略降且错误集与 A 高度重合**(Jaccard 示意 0.68)→ 系统性问题的又一证据。

**改善 ROI 排序**:资料装配(补错误码表/计费口径进检索路径)> 契约加 evidence 字段 > prompt 矩阵条款 > 换模型(不建议)。

**再补一刀**:baseline 下评审阻断精确率只有 0.48,追查发现评审与生成同模型 → 换成 B 当评审后升到 0.66。这是纯 **S1-2 平台设计**问题,与模型能力无关;漏拦的 14 条里 9 条资料里本来就没有依据,回到资料问题。

### 7. 落地分档与建议

| 档 | 内容 | 投入 | 能回答 | 不能回答 |
|---|---|---|---|---|
| 0 标本台 | 10 条失败样本(输入/期望/差异码位)+ 10 条人工定稿 + 四个手工对照(换模型/换 prompt/删半份资料/重跑三次) | 半天~1 天 | 定性归因、噪声底 | 阈值、小众阶段 |
| 1 指标埋点 | 阶段级 2~3 指标 + 三元组指纹 + golden 30~50 条 + k=3 | 1~2 周 | 90% 日常归因 | 交互项、跨阶段归因 |
| 2 因子平台 | 配置矩阵驱动 + 部分因子 + 缺料敏感度 + judge 校准 + 漂移告警 | 1~2 月 | "改哪最划算"、主效应/交互 | 自动决策 |
| 3 评测即服务 | 归因树自动分诊,现象→实验→结论自动化 | 季度级 | 归因变成平台能力 | 需要稳定消费方 |

**明确建议**:从档 0 + 档 1 的一半起步,只做三件事——

1. 建 10 条失败样本库,人工定稿 **不是**"我觉得对的输出",而是**能映射到发布判定的口径**(哪条 P0 需求点没被覆盖);
2. **每份产物打三元组指纹**(资料版本、prompt 版本、模型名+版本+温度)——没有它,后面所有归因都只能重跑猜;
3. 先算噪声底再谈改进。

**明确不要先做**:①不要先调 prompt(最难归因、最容易过拟合到那几条样本);②不要在无指标时换模型(会陷入"换个模型试试"的循环);③不要把"不满意"当整体处理,必须先切到**具体阶段的具体维度**。

**一个反直觉的判断**:优先级里"平台设计 + 资料"通常比"模型"更常见。因为模型是通用商品,而契约 schema、上下文装配、评审同源、门禁阈值、产物指纹才是你们的独特资产,也是最容易坏的地方。判据:**同一批错换模型还在 → 平台/资料;错法随模型变 → 才是模型。**

- 采纳:上述因子清单、阶段级指标、四类归因实验(缺料敏感度 / 错误集 Jaccard / 评审交叉 / 部分因子)、错因码位;
- 需要改的文档:
  - [../README.md](../README.md) 第五节 golden 集只有四个指标(契约合规率/diff 率/拦截率/成本),缺"漏测召回"与"证据命中率"两个更贴测试业务的指标 → 待补;
