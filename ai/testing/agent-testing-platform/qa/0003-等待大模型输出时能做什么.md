# 0003 等待大模型输出的时候,人和平台各自该干什么

## 一、问题

七阶段管线跑起来之后,每个 AI 阶段都要等模型:分诊十几秒、评审几十秒、用例生成一两分钟、脚本生成 agent 循环几分钟。**这段时间人在干等,平台在转圈**。问题不是"怎么让模型更快"(那是 provider 的事),而是:等的时候我能做什么,平台又该为这段等待做什么?

**提问时的上下文**(影响结论的前提):

- 场景:云服务集成验证测试,七阶段契约已落地(见 [../README.md](../README.md)、[../architecture.md](../architecture.md));
- 现状:AI 调用基本是同步的,页面提交后转圈等结果,人等结果时只能刷手机或者反复刷新;
- 已有纪律:生成-评审分离、契约流转、golden 集、版本指纹(见 [0002](./0002-输出不满意如何归因.md));
- 时间压力:发布窗口里一个模块的用例生成要跑好几轮,"等"是可感知的日常成本;
- 目标不是"把等待填满",而是让等待**不消耗人的注意力**。

### 1. 先换问法:等待有三种成本,对应三种策略

| 成本 | 表现 | 靠什么降 |
|---|---|---|
| 延迟成本 | 墙钟时间,端到端返回慢 | 并行、重叠、预取、换快模型(压缩) |
| 心智成本 | 不知道还要多久,不敢走开,反复看进度条 | 进度可见、预估剩余、流式先给部分(降不确定性) |
| 机会成本 | 这段时间本可以干别的 | 后台化、通知、断点续跑(可离开) |

关键判断:**三者的优先级是 心智 > 延迟 > 机会**。因为"用另一个任务填满等待"是最差解——多任务切换的代价是丢失当前上下文,回来要重建,而这个重建成本通常以 5~15 分钟计,远大于你填进去的那 90 秒。**用一次上下文切换去换一次等待,是负收益。**

所以完整策略不是"等的时候干什么",而是三句话,顺序不能反:

1. **让等待可离开**(后台 + 通知 + 断点续跑);
2. **让等待变短**(阶段重叠、预取、草稿-精修);
3. **让等待不空**(填充动作,只用"为验收做准备"这一类)。

### 2. 先量:你的等待到底多长

没量过就别优化。按阶段埋三个数,一周就有分布:

```python
# 每个阶段一条记录:首 token 延迟、总时延、token 数,带版本指纹(0002 的纪律)
INSERT INTO stage_latency(phase, model, prompt_ver, t_first_token, t_total, tokens)
```

用 P50/P95 决策,规则可以很直接:

- **首字延迟 P95 > 10s** → 该阶段上流式(先给部分结果);
- **总时延 P95 > 60s 且 P95/P50 > 3** → 该阶段转后台 job(流式救不了长尾);
- 两条不冲突:**流式负责"可看",后台负责"可走"**。

经验量级(必须用自己的数据替换):分诊 5~20s(短,不值得动)、评审 10~40s(适合流式)、用例生成 30~180s(流式 + 重叠)、脚本生成 agent 60~600s(直接后台)。

### 3. 人这一侧:等待清单

核心原则:**等待时只做"为验收这次输出做准备"的事,不开新任务。** 验收动作天然接着当前上下文,不需要重建;开新任务要重建,是双重损失。

| 等多久 | 干什么 | 为什么偏偏是它 |
|---|---|---|
| < 30s | **不切换**。盯住预估剩余,扫一眼已经流式落下来的前几条 | 切走再回来 > 30s,负收益 |
| 30s ~ 3min | **写验收核对点**:这次输出必须覆盖的 3~5 条(哪个需求点不能漏、哪个错误码必须出现、上一批人工补的是哪类) | 结果一到逐条打勾,验收速度翻倍,且零上下文重建 |
| 30s ~ 3min | **审上游**:阶段 1 的需求点清单有没有漏。漏了就别等阶段 2 了,直接回滚重跑 | 上游错了,下游全白跑,多等一分钟都是浪费 |
| 3 ~ 10min | 转后台,再做"弱相关但随时能回"的事:写一条 [qa/](./README.md)、给 [../reviews/pending.md](../reviews/pending.md) 加一条待校验断言、整理上一批 golden | 与当前模块无关,被打断也不心疼 |
| > 10min | **明确离开**:关页面、设通知,去干整块的事 | "半看"(盯一眼切一下)是最贵的状态 |

三个"不要":

1. 不要开另一个模块的设计/编码——会丢掉本模块的验收节奏,回来还得重建;
2. 不要趁等待"顺手改个 prompt 再跑一遍"——把等待变成不可比实验(没有指纹、没有噪声底,违反 [0002](./0002-输出不满意如何归因.md) 的纪律);
3. 不要频繁看进度条当休息:单次只花 2 秒,但注意力残留按分钟算。

**一个判据**:如果你在等的时候需要频繁看表来判断"要不要切走",说明平台缺的是进度预估,不是人缺自律。

### 4. 平台这一侧:四档

#### 档 0:可见性(半天) —— 降心智,不降延迟

进度可见 + 预估剩余:SSE 推送已生成条数/预计总条数/预估剩余时间,配骨架屏和阶段耗时。**这一档的价值全在"敢不敢走开"**,它让等待从"未知长度"变成"已知长度"。

#### 档 1:流式契约(1~3 天) —— 首字延迟从 P50 降到 P50/N,性价比最高

让模型按**行**输出 JSONL,而不是一口气吐一个 JSON 数组;前端逐条渲染,人从"等结束"变成"边看边标"。

```python
async def gen_cases_stream(req: RequirementDoc):
    # prompt 约束:每条用例一行 JSON,不要包成数组
    async for line in llm.stream(prompt=CASE_GEN_PROMPT, inp=req):
        try:
            case = json.loads(line)   # 半截行抛错就跳过,等下一行
        except json.JSONDecodeError:
            continue                  # 必要时上 partial-json-repair
        if not schema_ok(case):       # 契约校验兜底,坏条不往下游走
            continue
        yield f"data: {json.dumps(case, ensure_ascii=False)}\n\n"
```

风险就一条:JSON 稳定性(见 [../architecture.md](../architecture.md) 第三节"差异层")。用 schema 校验兜底,坏条丢弃而不是报错中断。

#### 档 2:并行与重叠(1~2 周) —— 降墙钟

**① 评审叠在生成上**(架构拓扑三的流式版):下游不再 `await` 上游完成,而是消费上游的流。

```python
async def stage2_then_3(req):
    pend = []
    async for case in gen_cases_stream(req):
        buf.append(case)
        if len(buf) % 10 == 0:                  # 每 10 条一批
            pend.append(asyncio.create_task(review_batch(buf[-10:])))
    await asyncio.gather(*pend)                 # 只等尾批
```

墙钟从 `T2 + T3` 变成 `max(T2, T3) + ε`。这是**收益最大的一步**,因为七阶段里最贵的两段正好是生成和评审。

**② 预取**(等的时候系统自己干活,不花模型额度):等阶段 2 时,阶段 4 一定会用到的东西先拉起来。

```python
async def prefetch_for_stage4(module: str):
    await asyncio.gather(
        git_pull(TEST_CODE_REPO),             # 测试代码仓
        warm_exec_env(module),                # 执行机容器 + 依赖
        load_framework_conventions(module),   # 框架约定 / 历史脚本
        ensure_model_route("script-generator"),  # 网关连接与配额预检
        return_exceptions=True,               # 任何一项失败都不阻塞主线
    )
```

判断标准只有一条:**这一步的产物在后续阶段一定会被用到,且准备它不消耗模型额度** → 可以提前。所以真正该预取的是**环境与资料**,不是"猜模型会输出什么"(投机生成要花额度、缓存命中率还低)。

**③ 草稿-精修双跑**:flash 先出草稿(便宜快,人先看),pro 后到覆盖(强,定稿)。人从等 90 秒变成 15 秒就看到可评审的版本,但要明确标记"未定稿",防止草稿被当真。

#### 档 3:后台化 + 把等待窗口变成资产(2~4 周)

长任务转 job(架构 7.4 方案 B 已有):提交即返回 `job_id`,完成推 IM/邮件/看板,页面关了也继续;DAG 节点缓存保证回来只跑受影响节点。

这一档测试平台有个**独有红利**:等待主结果的窗口,正好可以跑不影响主线的旁路计算——**k=3 重复采样(噪声底)、影子流量、golden 抽样**。主结果回来时你已经知道这次波动在不在噪声里,而不是拿单次采样下结论。

```python
async def while_waiting(primary):
    shadows = [asyncio.create_task(gen_cases_shadow(i)) for i in range(2)]  # 凑 k=3
    return await asyncio.gather(primary, *shadows)
```

### 5. 四档对比

| 档 | 内容 | 投入 | 降什么成本 | 主要风险 | 什么时候值得 |
|---|---|---|---|---|---|
| 0 可见性 | 进度/预估/骨架屏/阶段耗时 | 半天 | 心智 | 预估不准反而更烦 | **立刻** |
| 1 流式契约 | JSONL + 逐条渲染 + schema 兜底 | 1~3 天 | 首字延迟 | JSON 稳定性 | 长输出阶段(2/4) |
| 2 并行重叠 | 评审叠生成 + 环境预取 + 草稿-精修 | 1~2 周 | 墙钟 | 实现复杂度、限流竞争 | 发布窗口紧、模块大 |
| 3 后台 + 旁路 | job 化 + 通知 + 断点续跑 + k=3 | 2~4 周 | 机会成本;把等待变资产 | 状态管理、额度占用 | 单次 > 3min 成常态 |

### 6. 一个具体场景:等 90 秒的用例生成

```{mermaid}
sequenceDiagram
    autonumber
    actor U as 人
    participant P as 平台编排
    participant F as flash 草稿
    participant S as 强模型
    participant R as 评审模型
    U->>P: 提交模块(需求点清单)
    P-->>U: t+2s 骨架屏 + 预估 90s
    P->>F: 流式生成(每条一行 JSON)
    F-->>U: t+15s 前 3 条用例可看
    P->>P: t+20s 预取代码仓 / 执行机容器
    P->>R: t+35s 已出用例分批送评审
    P->>S: t+40s 强模型覆盖草稿
    R-->>P: t+60s 阻断 2 条
    P->>F: 立即回滚给生成方修
    S-->>U: t+85s 全量定稿
    Note over U: 等待被拆成三条并行轨:可看的流、在跑的预取、在攒的评审
```

关键不是"把这 85 秒填满",而是人在 t+15s 到 t+85s 之间**一直在看东西、一直在给反馈**,而且随时可以走开再回来(靠 job + 通知)。

### 7. 明确建议

先做档 0 + 档 1 的一半,同时埋点,用一周数据决定要不要上档 2/3。三件事:

1. **埋点**(半天):`first_token / t_total / phase`,按 P50/P95 出报表。没有它,后面所有判断都是拍脑袋;
2. **阶段 2 改 JSONL 流式**(1~2 天):首字延迟从 90s 量级降到 15s 量级,前端逐条落;
3. **立一条人侧 SOP**(今天就能):> 30s 只做"写核对点 + 审上游",不切新任务。

**不要先做**:①不要先做"等待动画/小游戏",不解决任何成本;②不要先做投机生成(花额度、命中率低),先做环境与资料预取;③不要在没埋点时凭感觉上后台化。

**一个反直觉的判断**:"利用等待时间多干点活"是伪效率。等 AI 这种**碎片化、完成时刻不可预期**的等待,人的切换成本远大于能填进去的那点时间。真正的杠杆顺序是 **让等待可离开 > 让等待变短 > 让等待不空**,倒过来做,越做越累。

## 五、结论与动作

- 采纳:三种成本与优先级、人侧"只做准备动作"的等待清单、四档方案(可见性 → 流式 → 重叠/预取 → 后台+旁路)、三件起步动作;
- 需要改的文档:
  - [../architecture.md](../architecture.md) 7.4(高性能扩展)可补一句"长任务的首字延迟与可离开性是两件事,分别由流式与 job 化解决" → 待补;
  - 本文与 [0002](./0002-输出不满意如何归因.md) 联动:等待窗口跑 k=3 噪声底,正在把 0002 的"先算噪声底"落成平台能力;
- 仍存疑 → 进 [../reviews/pending.md](../reviews/pending.md):
  - JSONL 流式在长输出下的 schema 兜底成功率(要不要 partial-json-repair、覆盖率多少);
  - "环境/资料预取"的 ROI 是否有现成的度量做法(命中率 × 节省时间);
  - 等待期跑 k=3 旁路会不会抢 provider 限流额度,导致主任务更慢。
