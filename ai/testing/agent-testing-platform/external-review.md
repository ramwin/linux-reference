## 一、为什么需要这一层

公司内网只能用内部模型,这带来三个具体问题:

1. **单一模型盲区**:同一个模型既写方案又点评方案,错误会被"一致化"——它认同自己错误的前提;
2. **版本不可见**:内部模型的版本与能力边界不透明,今天对的回答明天可能变;
3. **时效差**:内部模型的知识截止时间通常早于外部,新工具(openJiuwen、新 harness、新论文)它可能根本没听过。

所以这里的纪律是:**结论标来源,争议交外部,差异记成表**。不是"外部模型说得对就信",而是让两边各自在不知道对方答案的情况下表态,差异本身就是信息。

- **Claude CLI 修复**:
  ```bash

  export ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic                        # 或任意兼容端点
  export ANTHROPIC_API_KEY=...
  ```

## 三、校对的三个对象

不要拿整篇文章去问"帮我看看有什么问题"——那样只能得到泛泛的赞同。校对要打到具体断言上:

| 对象 | 例子 | 期望外部模型给出的 |
|---|---|---|
| **事实断言** | "openJiuwen 的 agent-gateway 未开源""Finding the Right Fit 做了 66 组交叉评测" | 一手链接、是否过期、数字是否对 |
| **因果判断** | "契约 schema 是迁移成本非线性,所以不能动" | 反例 :什么情况下换契约反而是对的 |
| **取舍建议** | "方案三等消费方 ≥3 再上" | 阈值依据、更早/更晚的信号 |

## 四、工序:一次对比的五步

1. **提一条断言**(不是一整篇),附上我们的一手依据与链接;
2. **让两边独立回答**:先问外部模型(不问内部结论),再贴内部模型的回答——顺序反了就会被锚定;
3. **只记差异**,三类分开处理:

   | 差异类型 | 判别 | 处理 |
   |---|---|---|
   | 事实错 | 能用手一来源裁决 | 直接改正文,补链接 |
   | 前提不同 | 两边假设不同(规模、团队、模型能力) | 把前提写进正文的"适用条件" |
   | 取舍不同 | 都成立,偏好不同 | 记成两档方案 + 明确建议,别强行统一 |

4. **回写正文**:修正后在该文档「参考资料」或文末补一行来源,并在版本记录里加一条;
5. **留痕**:对比表写进 `reviews/YYYY-MM-DD-主题.md`,结论写进 `qa/`。

## 五、提问模板

发给外部模型时,用这个结构(可直接复制):

```
背景:在做多智能体测试平台(验收端):七阶段(DAG 编排)+ 阶段间 JSON 契约 + golden 评测集回归,
模型可替换。团队 3~5 人,已有测试代码仓和执行机,内网只能跑内部模型。

待校验断言(原文):<贴 1~3 句,不要贴整篇>

我们的一手依据:<链接 / 实测结果 / 文档出处>

请只回答四件事:
1. 同意 / 反对 / 需要附加条件(先给结论);
2. 反例:什么情况下这条断言会失效;
3. 如果你不同意,给出你的版本(同样 1~3 句);
4. 你能给的一手依据(论文 / 官方文档 / 实测),给不出一手依据就写"无"。
不要扩写成文章,不要复述我的背景。
```

有了它,回答才可比——"同意/反对 + 失效条件 + 一手依据" 是可对照的字段,而"我觉得这个方案很好"不可对照。

## 六、记录格式

`reviews/` 下每次校对一个文件,模板见 [reviews/_TEMPLATE.md](./reviews/_TEMPLATE.md)。核心是一张三方对照表:

| 断言 | 外部模型(DeepSeek) | 外部模型(Kimi) | 内部模型 | 裁决 |
|---|---|---|---|---|
| …… | 同意 + 条件 | 反对 + 反例 | 待贴 | 采纳外部 / 保留 / 拆两档 |

**必须标注**:模型名、日期、是否开启联网检索。模型知识有截止日期,不标日期的结论半年后就是噪音。

## 七、和 `qa/` 的分工

- `qa/`:**问什么**。一条问题 → 外部回答 → 内部回答 → 差异 → 结论。适合"平台该怎么设计 X"这类开放问题。
- `reviews/`:**对不对**。一条断言 → 两边表态 → 失效条件 → 裁决。适合校验已有文档里的事实与判断。

问题先落 `qa/`,其中能被证伪的部分抽出来进 `reviews/pending.md` 排队等外部校对。
