> 一句话:**这四个产品都被叫作"AI 工具",但它们回答的是四个不同问题**——Codex 负责把代码写完,
> DSH 负责给你一个能改装的工作台,openJiuwen 负责把 Agent 批量造出来,扣子负责让业务同学把流程拖出来。
> 多智能体测试平台回答的是第五个问题:**怎么知道它们干得好不好**。
> 把五者塞进同一张评分表,本身就是维度错配;但先把前四个量清楚,才能说清第五个为什么不在这一排。

## 一、先拆词:它们各自回答什么问题

"AI 工具"是一个偷懒的说法。按"要解决的核心问题"分,这四个产品其实站在四个位置:

| 产品 | 它回答的问题 | 核心资产 | 典型用户 | 一句话比喻 |
|---|---|---|---|---|
| **Codex** | 怎么让 AI 把一件软件工程任务从头做到尾 | 任务轨迹、代码 diff、PR | 开发者、研发团队 | 雇一个不用管基础设施的工程师 |
| **DSH** | 怎么让 AI 在一个可改、可嵌、可观测的工作台里干活 | 插件生态、会话与记忆、编排原语 | 想改内核的开发者、平台团队 | 买自由,自己承担打磨 |
| **openJiuwen** | 怎么在一个组织里批量造 Agent、跑 Agent、管 Agent | Agent Runtime、Studio、Swarm 与 Skill | 企业平台团队 | 开一家 Agent 工厂 |
| **扣子** | 怎么让不懂代码的人把业务流程拖出来 | 画布、插件市场、渠道发布 | 业务、运营 | 把画布卖成订阅(已宣布退场) |
| **多智能体测试平台** | 怎么对 Agent 建立信任、发现回归 | 契约、golden 评测集、证据链 | QA、测试团队、发布决策会 | 质检科,不是生产线 |

前四个是**供给端**:造 Agent、让 Agent 干活、把 Agent 卖给别人。最后一个(本仓讨论的那个平台)是**验收端**:度量 Agent 的能力边界、发现行为回归。这条分界线贯穿全文,也是第四节的主线。

## 二、逐个说清楚

### 2.1 Codex:把"写代码"做成一条能交付的流水线

Codex 是 OpenAI 的软件工程智能体。到 2026 年它已经长成四种入口:命令行 `codex`、IDE 扩展、桌面 app、云端 Codex Cloud。四种入口共享一套能力面:

- **执行**:在沙箱里读文件、改代码、跑命令、跑测试,权限与审批是显式可调的;
- **交付**:GitHub 集成、PR 里当审查员、worktrees 并行隔离、`codex exec` 非交互模式塞进 CI/CD;
- **扩展**:MCP、Agent Skills、插件、Rules & Hooks、子代理(只有你显式"开口"它才拆);
- **记忆与治理**:AGENTS.md 项目说明书、Memories 与 Chronicle 跨会话记忆、企业管理与治理。

2026 年 9 月,Codex 的云端环境开始支持跨设备复用——任务丢在云上跑,人在手机上也能接着看、接着改([TechCrunch 报道](https://techcrunch.com/2026/09/29/openai-gives-codex-reusable-cloud-environments-that-work-across-devices/))。同年还有语音 CLI、代码评审等升级([Windows Report](https://windowsreport.com/openai-gives-codex-a-major-upgrade-with-cloud-environments-voice-cli-code-review/))。

**计费**:随 ChatGPT 会员提供,Plus 每月 20 美元,Pro 100/200/500 美元;也可用 API Key 按量付费。会员买的是"额度",限额按 5 小时窗口估算消息数([七牛云 2026-11 测算](https://news.qiniu.com/archives/1793672118526))。

**边界与坑**:

- 闭源。你能用 MCP 和插件扩展它,但改不了宿主本身;
- 能力强绑定 OpenAI 模型与账号体系。Codex 可以通过 Responses 兼容端点接第三方模型,但它的系统提示和工具定义是按自家模型调的,换模型后复杂工具调用的稳定性要重新验证;
- 多 Agent 不是它的重点:子代理要显式开口,更接近"并行开几个会话",不是"团队编排";
- 对简单任务,长时自主反而是浪费——一个会话可能调用模型几百次。

**适合谁**:想把"写代码这件具体的事"整体外包出去,不想管基础设施、不想调插件、愿意为成熟度付费的开发者。**不适合谁**:要私有化离线部署、要改内核、要把 harness 嵌进自己产品的团队。

### 2.2 DSH:一个开源、可改装、可嵌入的工作台

DSH(DeepSeek Harness)是 DeepSeek 在 2026 年 8 月发布的开源 Agent 框架,MIT 协议,命令行叫 `dsh`,npm 包 `@deepseek-ai/dsh`。它最有辨识度的一点:**内核是 Cordis 依赖注入容器,一切皆插件**——模型、工具、沙箱、会话存储、UI,甚至 agent 循环本身都是 npm 插件,用 `dsh plugin add` 装进来([dshbase 对比文](https://dshbase.com/zh/blog/vs-claude-code/))。

入口有 Web UI、TUI、headless、Python SDK,2026-09-30 起还有官方桌面端(Windows、Apple 芯片 macOS 双击安装,自带运行时)。默认安装带一百多个一方插件,社区插件目录已收录一千多个,但首轮实测的 101 个里 81 个是 GitHub 源码仓、3 个装不上——"能装"和"好用"之间还有距离。

能力面比"编程"更宽:

- **技能与记忆**:`SKILL.md` 技能、memory 层(本仓的记忆体系就跑在它上面);
- **编排原语**:子智能体、AgentTeams(队长—成员—任务 DAG)、AI 会议室(异模型评审 + 人工打断窗口)、workflow 脚本、定时任务;
- **模型自由**:默认接 DeepSeek API,也可指向任意 OpenAI 兼容端点或本地模型;
- **可嵌入**:headless 模式与 Python SDK,能被别的系统当组件调。

**计费**:软件免费(MIT),只付 token。按七牛云 2026-11 的测算口径,一个每天跑 5 个中等任务的开发者,用 DeepSeek V4.1 Flash 每月模型费约 100 元;Claude Code、Codex 的入门会员都是每月 20 美元。另外,DeepSeek 的联网 Search/Fetch 从 2026-11-01 起按次计费,每 1,000 次 5 元。

**边界与坑**:

- 开发者预览阶段,迭代快、插件质量参差,"审核"是你的活;
- 装插件会踩 `ERR_PNPM_FETCH_404`、`ERR_REQUIRE_ESM`、装了没反应这类坑,排查成本不低;
- 生态早期,成熟度和 Claude Code、Codex 仍有差距;它更像"可组装的零件库",不是"开箱即用的成品"。

**适合谁**:想读源码、改内核、把 Agent 嵌进自己系统、需要私有化或内网部署的开发者与平台团队。**不适合谁**:只想双击装一个稳定工具、不愿为插件质量买单的人。

### 2.3 openJiuwen:华为系的生产级 Agent 工厂

openJiuwen(开源九问)是华为实验室、华为云、小艺团队联合开源的 Agent 平台,Apache 2.0,2025 年底开源,2026-08-27 在 828 B2B 企业节上正式发布。它不造模型,造的是**Agent 全生命周期的工业体系**:

| 层 | 代表 | 作用 |
|---|---|---|
| 开发面 | [Agent Studio](https://atomgit.com/openJiuwen/agent-studio) | 可视化低代码:Agent 编辑、工作流编排、Prompt 调优、在线调试 |
| 核心 SDK | `agent-core`(`pip install openjiuwen`) | ReAct + Workflow 双模式,`@tool` 装饰器自动生成 function-call schema,支持状态保存与断点续跑 |
| 运行面 | `agent-runtime` | 多租户隔离、弹性扩缩、跨集群互通、会话生命周期 |
| 协同面 | JiuwenSwarm / Swarm Skills / Team Skills | 多 Agent 蜂群协同、把"团队协作 SOP"封装成可复用技能 |
| 资产面 | SkillHub / Agentic Hub(2026-09) | 技能、连接器、插件、专家、专家团的创建—安装—发布—复用 |
| 协议面 | `agent-protocol` | MCP、A2A、A2X Registry |

它与华为云 AgentArts 企业版同源度超过 90%,社区版可以平滑升级企业版;落地案例包括邮储银行 PSBC-Claw(7×24 全自动情报监测)和华为云 OfficeClaw(泛办公)。详见本仓[openJiuwen 分析](./landscape-openjiuwen.md)。

**边界与坑**:

- 部署门槛最高:要跑完整平台得 Docker 拉多容器,SDK 本身不带 Web 界面;
- 文档偏粗,实测中 MCP 自动发现没跑通、前端校验过度;
- 部分仓(如 `agent-gateway`)仍标注 Opening Soon;
- "同源 >90%"是优点也是风险——小项目用社区版、大项目被引导升级企业版,这条路径依赖要提前确认。

**适合谁**:有平台工程能力、要私有化、要多租户和断点续跑、要接华为云生态的企业团队。**不适合谁**:想一天出原型的个人开发者。

### 2.4 扣子:把画布卖成订阅,然后退场

扣子(Coze)是字节的低代码智能体开发平台。2023 年 12 月海外上线,2024 年 2 月国内上线;拖拽画布 + 插件市场 + 多渠道发布(飞书、微信、抖音),让业务同学不写代码就能把"检索新闻 → 去重 → 筛选 → 摘要 → 推送"串成一条自动流程。2025 年它以 **19.3% 的份额位居中国智能体开发平台公有云市场第一**,2025 年 6 月月访问约 458 万;2025 年 7 月,字节开源了应用开发平台与智能体运维工具(Coze Studio / Coze Loop);2026 年 7 月,企业标准版月费从 498 元调到 980 元,默认席位从 2 个增至 5 个。

然后急转弯。

- 2026-08-24:字节把扣子和 TRAE 团队并入豆包体系;次日"豆包工作"上线,并与飞书打通;
- 2026-10-29:公告企业标准版和旗舰版 **2026-11-30 起暂停向新客户销售**,**2027-12-31 全面下线**;通过火山引擎购买的旧个人进阶版、旧企业版、旧团队版,2026 年底先行下线。

为什么?按[36 氪的复盘](https://www.36kr.com/p/4062230230488961):浅层需求被通用助手免费接走,高价值重度客户在平台验证完业务逻辑后,出于数据安全和资产自主权转向开源自建或直接买算力;独立 SaaS 平台获客与深度服务成本摊不薄。更深一层,文章给了个很狠的判断——**人拖画布预设流程,本质是模型能力不足时的临时产物**;当模型能自主拆解步骤,画布就从"效率神器"变成反直觉的冗余工程。

**边界与坑**:

- 纯 SaaS,数据不出网、代码不能自托管,资产迁出方案此前未定;
- 企业版退场后,自托管只能走 2025-07 开源的 Studio / Loop,运维责任回到自己,功能边界也与商业版不同;
- 本文只讨论国内企业版;海外版不在讨论范围,不做延伸猜测。

**适合谁**:短期 PoC、外围辅助工具、运营同学自己折腾的场景。**不适合谁**:把核心业务压在上面的人——时间表已经写死了。

## 三、七个维度,一张评分表

### 3.1 先把尺子讲清楚

评分 1–5 分,锚点:1 = 基本没有,3 = 够用,5 = 同赛道标杆或独一档。**分数是"对某个角色的适配度",不是绝对好坏**;每个分数下面给证据,不同意可以自己改权重。

| 维度 | 它问的问题 | 为什么重要 |
|---|---|---|
| 任务闭环 | 能不能把一件完整的活干完并交付 | 决定它是"玩具"还是"生产力" |
| 编排与多 Agent | 从单兵到团队,能不能编排、能不能编程 | 决定复杂任务上限 |
| 工程化与可控 | 权限、沙箱、审计、可嵌入、可复现 | 决定能不能进生产 |
| 数据主权与私有化 | 能不能自托管、离线、改内核 | 决定合规与长期成本 |
| 上手与运营成本 | 装起来、用起来、养起来要多少人力 | 决定落地速度(反向计分) |
| 生态与可持续性 | 插件/技能/社区/厂商承诺 | 决定三年后还在不在 |
| 评测与可观测 | 能不能度量好坏、接 eval、留轨迹 | 决定迭代是碰运气还是工程 |

### 3.2 打分

| 维度 | Codex | DSH | openJiuwen | 扣子 |
|---|---:|---:|---:|---:|
| 任务闭环 | 5 | 4 | 4 | 2 |
| 编排与多 Agent | 3 | 5 | 5 | 3 |
| 工程化与可控 | 4 | 4 | 5 | 2 |
| 数据主权与私有化 | 1 | 5 | 5 | 1 |
| 上手与运营成本 | 4 | 3 | 2 | 5 |
| 生态与可持续性 | 4 | 4 | 4 | 1 |
| 评测与可观测 | 3 | 4 | 3 | 2 |
| **合计(满分 35)** | **24** | **29** | **28** | **16** |

逐条给理由:

- **任务闭环**:Codex 5 分,因为它把"执行—验证—交付"做成了产品(云端环境、PR 评审、CI);扣子 2 分,它擅长可枚举流程,开放任务弱,而且企业版正在退场;
- **编排**:DSH 与 openJiuwen 5 分,一个靠可编程的 AgentTeams/workflow,一个靠 Swarm 与 Studio 画布;Codex 3 分,子代理要显式开口;扣子 3 分,有"多智能体协作"套餐,但仍是预制逻辑;
- **工程化**:openJiuwen 5 分(多租户、审计、协议、断点续跑);Codex 4 分(沙箱审批与企业治理齐全,扣在闭源);扣子 2 分(SaaS 黑盒);
- **主权**:DSH 5 分(MIT、可离线、可 fork)、openJiuwen 5 分(Apache 2.0、可私有化);Codex 与扣子各 1 分;
- **上手**:扣子 5 分(拖拽);Codex 4 分(四种入口,成熟);DSH 3 分(桌面端改善了安装,但插件仍要挑);openJiuwen 2 分(多容器部署);
- **生态**:Codex 4 分(OpenAI 背书,插件/MCP 生态成熟);DSH 4 分(一千多个插件,但早期、质量参差);openJiuwen 4 分(华为生态 + Agentic Hub,但社区还年轻);扣子 1 分(可持续性已经归零);
- **评测**:DSH 4 分(会话轨迹、Python SDK 可嵌、被第三方 harness 评测选为被测对象);Codex 3 分(有用量与轨迹,但评测是附属能力);openJiuwen 3 分(`agent-core` 有 evaluation 模块,公开资料未展开);扣子 2 分(有调试日志,没有系统 eval)。

### 3.3 换一组权重,排名就翻转

总分只对"同一个角色"有意义。给两个典型角色配权重,结果立刻不一样(本文自拟权重,仅作演算):

| 维度 | 个人开发者权重 | 企业平台团队权重 |
|---|---:|---:|
| 任务闭环 | 20 | 15 |
| 编排与多 Agent | 10 | 20 |
| 工程化与可控 | 10 | 20 |
| 数据主权与私有化 | 10 | 20 |
| 上手与运营成本 | 25 | 5 |
| 生态与可持续性 | 15 | 10 |
| 评测与可观测 | 10 | 10 |

加权结果(百分制):

| 角色 | Codex | DSH | openJiuwen | 扣子 |
|---|---:|---:|---:|---:|
| 个人开发者 | 74 | **79** | 74 | 52 |
| 企业平台团队(国内、要私有化) | 65 | 87 | **88** | 41 |

个人开发者眼里 DSH 第一,企业团队眼里 openJiuwen 第一,Codex 从并列第二掉到第三。**这不是矛盾,是"选型 = 给维度配权重"的直接后果**——和 Finding the Right Fit 论文里"模型 × harness × 任务排名会反转"是同一个现象(见[openJiuwen 分析 §5.8](./landscape-openjiuwen.md))。所以任何" XX 最强"的榜单,都要先问:它是给谁排的?

> 补一句公平性:Codex 在"企业"一列只有 65 分,是因为这里假设的是**国内、要私有化、要内网**的语境。放到不要求私有化的海外团队,主权权重下来,Codex 会回到第一梯队。

## 四、多智能体测试平台和它们到底差在哪

### 4.1 结论:不是同类竞争,是产业链上下游

四者是**供给端**:解决"怎么把 Agent 造出来、让它把活干完"。测试平台是**验收端**:解决"怎么度量它、发现回归、给发布决策提供证据"。两者重合度很低,但接口关系很强——测试平台要把它们造出来的东西当被测对象,也要复用它们的组件。

### 4.2 六个不同

| | 供给端(Codex / DSH / openJiuwen / 扣子) | 多智能体测试平台 |
|---|---|---|
| **目标函数** | 产出一个工件:代码、报告、流程 | 对另一个系统建立信心,或发现风险 |
| **多 Agent 的角色** | 分工干活的生产力 | 被构造、被观测、被评分的测试场景 |
| **核心资产** | Agent、工作流、Skill、插件 | 契约、golden 集、缺陷模式、flaky 名单、证据链 |
| **评测的位置** | 附属能力,通常只有跑分和日志 | 主战场:oracle 构造、环境生命周期、可重复性 |
| **用户与收入** | 开发者/业务,订阅或 API 计费 | 组织质量体系、发布决策会,按测试资产与算力计 |
| **什么不变** | 模型、框架、插件都可以换 | 契约 schema、golden 集、门禁流程不随模型变 |

逐条展开最关键的三条:

1. **目标函数不同**。普通任务成功 = 工件存在且质量不错;测试成功 = 你**有理由相信**某个结论。后者天然需要 oracle(判对错的标准)、环境生命周期(准备被测系统、造数据、清理)、可重复性(昨天过了今天没过,要能定位是谁变了)。这三样通用平台天生缺乏——通用 Agent 能点完一个登录流程,但"返回 200 但权限校验没生效"算不算 bug,需要领域知识。
2. **多 Agent 的用法不同**。在供给端,多 Agent 是生产力:拆活、并行、互相评审。在测试平台,多 Agent 是**被测现象**:要能构造"需求理解 → 用例生成 → 用例评审"这种协作拓扑,然后给每个环节打分。一个要它干得快,一个要它干得**可度量**。
3. **资产沉淀的方向不同**。供给端沉淀 Agent 和技能(越用越强的产品);测试平台沉淀**测试资产**(越用越准的判据)。扣子的退场恰好证明了前者会被模型能力抹平,后者不会——契约、golden 集、缺陷模式、证据链,不随某个模型或某个平台下线而失效。

```{mermaid}
        D["DSH<br/>开源可改装工作台"]
        J["openJiuwen<br/>Agent 工厂"]
        K["扣子<br/>低代码画布"]
    end
    S --> A["被测 Agent / 被测 harness"]
    A --> T["多智能体测试平台<br/>需求→用例→评审→脚本→执行→分诊→报告"]
    T --> R["回归门禁 / 选型报告 / 发布决策"]
    T -.-> G["golden 集、缺陷模式、证据链"]
    G -.-> T
```

### 4.4 别用第三节的尺子量测试平台

如果硬把测试平台塞进 3.2 那张表,它大概会得 20 分出头:任务闭环一般(不产出代码)、上手一般(要建评测集)、生态早期。**这不是它弱,是尺子选错了。** 供给端的尺子量的是"能不能干活",验收端该量的是:

| 验收端维度 | 怎么算 | 决策价值 |
|---|---|---|
| 契约合规率 | 输出能否过 schema 校验 | 低于阈值直接拒绝该模型 |
| 与基线 diff 率 | 字段级对比 | diff 大到人看不完 = 有风险,抽审 |
| 评审拦截率 | 评审方阻断意见数 | 翻倍即生成质量退化 |
| 成本 / 延迟 | token 与耗时 | 同质量选便宜的 |
| 回归发现率 | 版本漂移被提前拦下的比例 | 决定敢不敢升级 provider |
| 证据链完整度 | 执行录屏、断言明细、最小复现 | 决定报告能不能被信任 |
| golden 集覆盖率 | 真实输入被评测集覆盖的比例 | 决定上面所有指标可不可信 |

一句话:供给端问"能不能做",验收端问"凭什么信"。详见[为什么需要专门的测试系统](./why-agent-testing.md)。

### 4.5 怎么和它们相处:三档方案

| 方案 | 做法 | 利 | 弊 | 适用 |
|---|---|---|---|---|
| A. 当被测对象 | 把四者构建的 Agent / harness 接进来跑用例(走 MCP/A2A 或 harness 适配器) | 零耦合,借生态势能,立刻有对比数据 | 无代码级复用 | **现在就做** |
| B. 复用组件 | 按需引入 DSH 的 Python SDK/插件、openJiuwen 的 `agent-protocol`/`agent-memory`、Codex 的 `codex exec` 当执行器 | 松耦合、可控、可替换 | 集成成本,版本跟随 | **主力路线** |
| C. 基于它搭底座 | 用某家的 Runtime + Studio 做底座,上面加测试层 | 最快出全套能力 | 平台锁定,资产被绑架(扣子是活教材) | 只做 PoC |

**建议:B 为主、A 为辅,C 只做 PoC。** 具体可复用的点:

- **Codex**:`codex exec` 适合当"脚本生成 / 失败修复"的执行器;Codex Cloud 的隔离环境可以当被测 harness 之一;
- **DSH**:Python SDK 与插件机制适合把"角色实现"塞进去;它的 AgentTeams 任务 DAG、会话日志,可以直接借来做轨迹与审计;本仓的平台文档里已经把它当"方案二的活标本"评估过;
- **openJiuwen**:`agent-protocol`(MCP/A2A)直接用,别自研;Swarm Skills 的团队 SOP 建模与"多 Agent 协作测试场景"同构,可以兼容格式;`agent-memory` 可参考其记忆抽取与压缩;
- **扣子**:只作为"低代码构建的 Agent"这类被测对象的来源,不做底座。

### 4.6 反向:测试平台能为它们做什么

- **选型评测**:同一个模型配不同 harness,分数能差一个数量级,排名还会反转(arXiv [2610.00917](https://huggingface.co/papers/2610.00917) 的 66 组交叉评测;[2610.32483](https://arxiv.org/abs/2610.32483) 讨论了 "模型还是 harness 的错")。只有跑组合评测,才能回答"我们该选谁";
- **回归门禁**:provider 悄悄升级一次、prompt 改一版,行为就可能漂移;没有 golden 集,你只能靠用户投诉发现;
- **证据链**:"AI 说测试通过了"要能被发布决策会信任,需要执行录屏、断言明细、最小复现——这是测试平台的专属产出。

## 五、选型建议

| 你的场景 | 首选 | 备选 | 不建议 | 理由 |
|---|---|---|---|---|
| 个人/小团队写代码,要稳 | Codex | Claude Code | openJiuwen | 成熟度与交付闭环最好,订阅制不用管基础设施 |
| 要省钱、要改内核、要离线 | DSH | openJiuwen | Codex | MIT + 可嵌入 + 只付 token;代价是自己当审核员 |
| 企业级多租户、要华为生态 | openJiuwen | DSH | 扣子 | Runtime/多租户/协议齐全;扣子是 SaaS 且退场 |
| 业务同学零代码 PoC | 扣子(限期) | Dify | 把核心业务压上 | 上手最快,但时间表已定;长期看 Studio 自托管或开源方案 |
| 要评估"到底哪个工具好" | 自己的组合评测 | 论文榜单 | 单一榜单 | 排名随模型 × harness × 任务反转 |
| 做多智能体测试平台 | 四者都当被测对象/组件 | — | 任何一家当底座 | 验收端要独立于供给端,否则判据被供应方定义 |

一句话建议:**先用 Codex 或 DSH 把生产力跑起来,再用测试平台把"信任"建起来;openJiuwen 留给有平台工程能力的企业;扣子只做短期验证。**

## 六、三个反直觉的结论

1. **工具越强,eval 越重要**。弱模型不行,肉眼可见;强模型"看起来都行",只有系统化测试才能区分 90 分和 95 分——而生产环境里 90 分往往就是不可用。
2. **供给端会被模型能力持续抹平,验收端的资产不会**。扣子三年走完"份额第一 → 企业版退场",不是因为产品做得差,而是画布这种形态本身在贬值;而契约、golden 集、缺陷模式、证据链,不随某个模型或平台下线而失效。所以"等模型再强一点再说"对供给端成立,对验收端不成立——越晚建越亏。
3. **"选工具"本身是个评测问题**。榜单不可信,因为排名随组合反转;真正该做的是拿自己的任务集,把候选 harness 各跑一遍,看分数、成本、轨迹。这件事恰好就是测试平台的产品能力——**验收端不只验收业务 Agent,也验收工具本身**。

## 七、一页纸

| 问题 | 该找谁 | 一句话 |
|---|---|---|
| 把代码写完、交付 | Codex | 成熟、省心、闭源、按订阅付费 |
| 把工作台改装、嵌进系统 | DSH | 开源、可改、便宜,自己当审核员 |
| 在企业里批量造/跑/管 Agent | openJiuwen | 生产级基础设施,门槛最高 |
| 让业务同学快速搭个流程 | 扣子(限期)/ Dify | 上手最快,别压核心业务 |
| 知道 Agent 好不好、有没有回归 | 多智能体测试平台 | 契约 + golden 集 + 证据链,不是生产线 |
