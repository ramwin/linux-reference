你已经有的：agent 工程（循环、工具、MCP、上下文）、评测意识、DAG 编排、prompt 设计、平台架构。这些在[个人 AI 熟练度](./personal-ai-proficiency.md)里已经到 L4、正向 L5 走。你缺的不是更多 AI 知识——是**把 AI 系统跑稳的机器侧知识**。

一个判断依据：你能定义"什么算对"，但目前还不太能证明"系统本身没在骗你"——环境漂移了你看不出来，资源被抢了你归因不到，评测分数差 5 分你说不清是不是噪声。这篇按"现在卡脖子 → 决定个人层级 → 长期底座 → 明确不学"四档排，每一项都给**可验收的"会了"标准**，不给"了解一下"。

## 二、P0：现在不补就卡住

### P0-1 Linux 资源与隔离（约 15 小时）

**为什么现在学：** 你上一轮说"CPU、内存信息我想的都是 Zabbix 这种 10 年前的技术"——这正是缺口。CPU 使用率**不是**资源压力的正确信号，PSI 才是；内存超卖导致 OOM 的现场在 `dmesg` 和 `memory.events` 里，不在监控面板上。

**"会了"的验收标准（能动手做，不是能复述）：**

1. 用 `systemd-run --scope -p MemoryMax=512M -p MemoryHigh=400M` 把一个进程压到 OOM，并解释 `dmesg` 里那几行分别是什么；
2. 用 `cat /proc/pressure/memory`（以及 `cpu`、`io`）读出 `avg10/avg60/avg300` 与 `full`，说清"some 高、full 低"和反过来的区别；
3. 用 `nsenter -t <pid> -n ss -lntp` 进入容器网络命名空间排查端口问题；
4. 手画一张包路径图：veth → bridge → iptables/nftables → 宿主网卡，能指出 CNI 在哪一步插入规则；
5. 给一个进程设 cpuset 绑定到 2 个核，并用 `mpstat` 证明它没跑出这两个核。

**资料：** 内核文档 `Documentation/admin-guide/cgroup-v2.rst`、`Documentation/accounting/psi.rst`；`man 7 namespaces`、`man 7 cgroups`；Brendan Gregg《Systems Performance》第 2、6、7 章（方法论 + CPU + 内存）。

**在项目里怎么练：** 给环境系统加"按环境的 cgroup 配额 + PSI 告警"，并复现一次"一个环境把同节点邻居拖慢"。

### P0-2 K8s 的运维真相（约 40 小时，最大一块）

**为什么现在学：** "web 服务容器化随时启停"只到打包层。**"随时启停"本身是编排器的工作**：就绪探针、优雅退出、PDB、驱逐、排水。你清单里的灰度和容灾，在 K8s 里都是原语，不会用就只能自己写一遍。

**"会了"的验收标准：**

1. 单机装 k3s，用 Helm 把一个环境模板（含前置依赖、配置、健康检查）部署起来；
2. 写一个 CRD（比如 `TestEnv`）+ controller，能真正创建/删除环境（用 kubebuilder 或 operator-sdk 都行）；
3. 独立定位四类故障：`Pending`（资源/污点/亲和性）、`CrashLoopBackOff`、`ImagePullBackOff`、`Evicted`；
4. 解释 request / limit / QoS 三类（Guaranteed / Burstable / BestEffort）与驱逐顺序的关系；
5. 用 PDB + `preStop` + 优雅退出，做到"滚动升级时在跑的环境不中断"；
6. 说清 Service / Ingress / Gateway API 三者的边界，以及 DNS 在集群内怎么解析。

**资料：** kubernetes.io 官方 Concepts（按 Workloads → Scheduling → Storage → Networking 顺序读，不要从头刷）；k3s 文档；Operator 模式官方文档。

**在项目里怎么练：** 把当前 Docker compose 定义迁到 k3s + Helm，跑通"创建 → 打测试 → 销毁 → 孤儿回收"闭环。

### P0-3 可观测性实操（约 25 小时）

**为什么现在学：** 稳定性不是"感觉稳"，是"能被度量"。你现在有 Zabbix 的主机/触发器思维，需要换成"指标模型 + 查询语言 + 追踪"的思维。

**"会了"的验收标准：**

1. 用 20 行 Python 写一个 exporter，暴露"环境总数、创建成功数、创建时延直方图"；
2. 手写 10 条 PromQL，至少覆盖：`rate()`、`histogram_quantile()`、`sum by()`、`absent()`、以及一条"如果 5 分钟内没有上报就告警"；
3. 用 OTel SDK 给上报链路埋一个 trace，在 Jaeger/Tempo 里看到跨 3 个服务的瀑布图，并能从慢 span 定位到具体函数；
4. 用 `container_cpu_cfs_throttled_periods_total` + PSI 解释一次"随机变慢"，而不是说"CPU 高"；
5. 说清 counter / gauge / histogram 的适用边界——尤其为什么时延不能用 gauge 的平均值。

**资料：** Prometheus 官方 Concepts 与 PromQL 基础、直方图与分位数文档；OpenTelemetry "Getting Started"；SRE Book 第 6 章《Monitoring Distributed Systems》。

**在项目里怎么练：** 落地[环境稳定性那篇](./../testing/agent-testing-platform/environment-management-stability.md)的第四条验收指标：创建成功率、P95 就绪时延、孤儿回收率、失败归因准确率。

### P0-4 容量与过载（约 12 小时）

**为什么现在学：** 你刚提的"接口分级 + 流控 + 降频丢弃"就是这一块，而它背后有成熟理论，不需要自己发明。

**"会了"的验收标准：**

1. 用 `并发 = 到达率 × 停留时间`（Little's Law）算出环境创建的并发上限，并用压测验证误差在 ±20% 内；
2. 实现三档降级 + 下发策略，并**实测**"源头降频"比"服务端丢弃"少多少入口请求（按 10,000 台算，应该是 166.7 → 33 QPS 量级）；
3. 做一次混沌演练：杀掉一个 collector，验证补传与"恢复期限速"，记录恢复时间；
4. 说清令牌桶、并发信号量、自适应并发、队列过期丢弃各自防的是什么，以及你系统里该用哪一种。

**资料：** SRE Book 第 21 章《Handling Overload》（客户端自适应限流）、SRE Workbook 过载那一章、Envoy 自适应并发与本地限流文档、CoDel 的思路（控制排队时延，而不是队列长度）。

**在项目里怎么练：** 直接落地[环境稳定性那篇第九节](./../testing/agent-testing-platform/environment-management-stability.md)。

## 三、P1：决定你能不能从"最强执行者"往上走

### P1-1 SLO 与错误预算（约 6 小时）

验收：给环境系统定 3 条 SLO（创建成功率 ≥99%、P95 就绪 ≤3min、孤儿 1 小时内回收 100%），算出 30 天错误预算，并写一条"预算耗尽就冻结发版"的规则。资料：SRE Workbook 第 2 章（Implementing SLOs）与第 5 章（Alerting on SLOs）。

### P1-2 ADR 与技术选型（约 5 小时）

验收：写 3 篇 ADR，每篇必须含"3 个被排除的方案 + 排除理由 + 什么条件下会重新考虑"。这正好补上你在[架构视野那篇](./architecture-option-refresh.md)里缺的那一环——判断力要能被人看见。资料：adr.github.io 的模板，外加你自己的架构卡片。

### P1-3 评测的统计显著性（约 10 小时）

**这是最容易被跳过、但对测试平台最值钱的一项。**

验收：

1. 用 50 条真实 golden 样本算成功率，并用 **Wilson 区间**给出 95% 置信区间（不要只报一个百分比）；
2. 说清 **pass@k 与 pass^k 的区别**，并各实现一版：前者是"k 次里有一次成功"，衡量能力上限；后者是"k 次全部成功"，衡量**稳定性**——对 agent 和测试系统，后者才是你真正想要的指标；
3. 拿两个模型在同一批样本上跑，用区间重叠判断"4 个点的差距是不是噪声"；
4. 能解释为什么 12 条样本的评测结果不能用来做发布决策。

资料：τ-bench 论文（提出 pass^k）、Wilson 区间公式、bootstrap 重采样的入门材料。

### P1-4 多 Agent 与分布式可靠性模式（约 8 小时）

验收：在你系统里找出 3 个级联失败点（重试风暴、超时不级联、非幂等重试），写出修复并复现一次。资料：SRE Book 第 22 章《Addressing Cascading Failures》、DDIA 第 8 章《The Trouble with Distributed Systems》。

## 五、明确不学：省下的时间拿去练手

| 不学 | 为什么 | 什么时候再考虑 |
|---|---|---|
| Transformer / 反向传播推导 | 你不训练模型，调 API 和评测用不到 | 除非转算法岗 |
| 从零写调度器 / K8s 组件 | 用现成的，写了也没人维护 | 基本不会 |
| 异地多活 / 机房级容灾 | 测试平台停半天，人工预案比多活便宜 | 平台变成公司级基础设施时 |
| eBPF 内核编程 | 会看 Hubble / Tetragon / `bpftrace` 就够用 | 要做深度性能剖析时 |
| 前端框架深度 | 不是你的瓶颈 | 你要自己做产品界面时 |
| 更多 AI 框架横评 | 你已经够用，边际收益接近零 | 出现明确不适用的场景时 |

## 六、12 周排期（每周 5 小时）

| 周 | 主题 | 产出物 | 验收 |
|---|---|---|---|
| 1–2 | Linux 资源与隔离 | 配额 + PSI 告警 | 复现一次邻居干扰并归因 |
| 3–5 | K8s 运维真相 | k3s + Helm 环境模板 + `TestEnv` CRD | 创建/销毁/回收闭环跑通 |
| 6–7 | 可观测性 | 自写 exporter + 4 条 SLO 指标 | 一张能定位故障的看板 |
| 8 | 容量与过载 | 三档降级 + 混沌演练 | 实测入口 QPS 下降比例 |
| 9 | SLO 与错误预算 | 3 条 SLO + 冻结规则 | 预算耗尽有动作 |
| 10 | 评测统计 | 50 条 golden + Wilson 区间 | pass^k 跑通，能判断显著性 |
| 11 | ADR + 可靠性 | 3 篇 ADR + 3 处级联修复 | 评审时能用上排除理由 |
| 12 | 复盘 | 一篇"我补了什么"的笔记 | 能讲给别人听 |

每周配比建议：**1 小时读 + 3 小时动手 + 1 小时写文档**。只读不动手的那部分基本等于没学。

如果每周只有 3 小时，把 12 周拉成 20 周，顺序不变——**顺序比速度重要**：先 P0 的物理层和编排层，再观测，再容量，最后才是 P1 的方法论。

## 七、如果只有 10 小时：压缩版

按"投入产出比"选三件：

1. **3 小时**：PSI + cgroup 实操（`systemd-run` 压内存、读 `/proc/pressure/*`）——立刻能解释"随机变慢"；
2. **4 小时**：PromQL 10 条 + 自己写一个 exporter——立刻有"能被度量"的稳定性；
3. **3 小时**：Little's Law + 三档降级——立刻能回答"上限定多少"。

## 八、怎么判断"学会了"：三条通用标准

不管学哪项，都用这三条验收，而不是"看完文档"：

1. **能在故障现场用上**。概念能在白板上讲不算，能在凌晨的日志里定位才算。
2. **能给出数字**。上限是多少、拐点在哪、预算剩多少、误差多大——给不出数字，说明只是记住了名词。
3. **能教会别人**。写一篇能被同事照着做的文档，是检验理解最狠的方式。
