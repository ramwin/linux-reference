# 把高权限交给 AI 后，我如何防止数据丢失

```{contents}
```

我深度使用 AI 写代码、整理文档和处理日常文件。为了减少反复确认，我给过 AI 很高的系统权限：它可以读写工作目录、执行命令、操作 Git，甚至批量处理文件。

这确实方便，但也带来一个问题：**AI 不只是在“生成内容”，它还可能真实地修改我的数据。**

一次错误的 `rm`、一次批量移动、一个错误的 Git 操作，都可能造成损失。更危险的是，如果所有设备都在自动同步，错误还可能迅速传播到每一台设备。

所以，我现在的核心原则不是“相信 AI 不会犯错”，而是：

> **允许 AI 犯错，但任何错误都不能毁掉唯一的原件和备份。**

严格来说，在 AI 拥有全部权限的情况下，无法绝对保证数据不丢失。能做的是通过隔离、版本管理和独立备份，让数据始终可以恢复。

## 我目前的方案：NAS 不运行 AI，电脑通过 Git 同步

我的资料主要放在 NAS 上，NAS 本身不运行 AI。日常使用多台电脑，代码和文档通过 Git 管理，再推送到 NAS 上的 Gitea。

这个方案有几个明显优点：

- AI 不直接接触 NAS 上的全部资料。
- 多台电脑之间可以方便地同步代码和文档。
- Git 能保留修改历史，普通误改通常可以恢复。
- NAS 与 AI 工作环境分离，整体结构简单清晰。

但它并不等于完整的数据备份方案。

### Git 和 Gitea 不是备份

如果 AI 误删文件并提交、推送，删除操作也会成为同步内容的一部分。虽然 Git 历史通常能帮助恢复，但如果 AI 同时掌握高权限账号，还可能执行强制推送、删除分支甚至删除仓库。

因此，重要的 Gitea 仓库还需要：

- 禁止强制推送，保护重要分支。
- AI 使用单独的账号或 Token，不授予不必要的管理权限。
- 定期备份仓库、数据库、配置、附件和 Git LFS 数据。
- 将备份保存到 AI 无法删除的位置。

### NAS 也不是天然安全

NAS 可能发生硬盘损坏、整机故障、误操作或账号失陷。RAID 解决的是部分硬盘故障，不解决误删和损坏；快照解决的是快速回滚，也不等于独立备份。

如果所有资料最终都只有 NAS 这一份，NAS 就仍然是单点故障。

### Git 不适合管理全部照片和视频

照片原图、视频等大量二进制文件不适合全部交给 Git。更合适的方式是：

- 照片和视频使用文件级备份、快照和异地副本。
- Git 管理照片整理脚本、标签数据、说明文档等文本内容。
- 缩略图、AI 索引和识别结果可以重建，不必与原件采用相同的备份策略。

## 我会建立的四道防线

### 1. 限制 AI 的影响范围

方便不等于必须让 AI 控制整台机器。更合理的方式是让 AI 在工作区里高度自由，在工作区之外没有权限。

例如：

- 给 AI 使用独立的系统用户，不使用 root 或 sudo。
- 只挂载需要处理的项目目录。
- NAS 默认以只读方式挂载，另设一个可写的临时工作区。
- 不让 AI 接触备份系统的删除权限。
- Gitea Token 只授权需要的仓库，不授予删除仓库和管理系统的权限。
- 重要操作放到单独的 Git 分支，审核后再合并。

如果确实需要执行高风险的系统命令，可以在虚拟机或容器中运行 AI，而不是直接开放宿主机。

真正有效的限制应由操作系统权限、挂载属性和独立账号实现，不能只靠提醒 AI“不要删除文件”。

### 2. 保留可回滚的版本

在让 AI 批量处理前，先创建快照或版本点：

- 代码使用 Git 提交和分支。
- NAS 文件开启快照。
- 重要目录保留历史版本。
- 批量删除先进入隔离区，保留一段时间后再清理。

版本管理解决的是“改错了怎么回去”，但不能替代独立备份。

### 3. 建立 AI 无法修改的独立备份

我倾向采用经典的 **3-2-1 备份原则**：

- 至少保留 3 份数据。
- 使用 2 种不同的存储介质或存储系统。
- 至少 1 份放在异地或离线环境中。

一个实际组合可以是：

1. 电脑上的工作副本。
2. NAS 上的 Gitea 或文件副本，并开启快照。
3. 定期备份到移动硬盘，完成后断开连接，或者加密备份到异地存储。

关键不在于具体使用哪块硬盘，而在于：**运行 AI 的电脑和 NAS 上的 AI，都没有权限删除最后的备份。**

快照、RAID 和同步都不能单独算作这一份独立备份。

### 4. 定期验证恢复

没有验证过的备份，只能算“看起来有备份”。

我会定期做几件简单的事：

- 随机恢复一个 Git 仓库。
- 从备份中找回几张照片。
- 检查备份任务是否真的成功，而不是只看任务是否存在。
- 确认恢复所需密钥、密码和说明没有只保存在同一台设备上。

## 几种方案的对比

| 方案 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|
| NAS 不运行 AI，仅电脑使用 AI | 简单，NAS 与 AI 隔离 | AI 仍可能通过同步影响 NAS | 当前代码、文档工作流 |
| AI 在电脑虚拟机或容器中运行 | 权限边界清晰，兼顾便利性 | 需要配置共享目录和资源 | 日常开发、批量处理文件 |
| NAS 容器中运行 AI，原件只读 | 适合长期任务，不必打开工作电脑 | 需要严格控制容器挂载和输出目录 | 照片识别、标签和分类 |
| 独立 AI 主机处理 NAS 副本 | 隔离效果最好，不消耗主要设备资源 | 成本和维护工作最多 | 大量照片、视频和长期自动化任务 |

我的建议是：**代码和文档继续沿用现在的 Gitea 方案；高风险任务放进容器或虚拟机；NAS 可以运行 AI，但不要让 AI 同时拥有原件、备份和系统管理权限。**

## NAS 上运行 AI 整理照片，应该怎么做

“NAS 不开 AI”是一种有效的隔离方式，但并不是唯一选择。对于照片梳理这类任务，NAS 反而很适合运行 AI，因为数据不用反复复制到电脑。

关键不是 NAS 能不能运行 AI，而是采用下面的流程：

**照片原件只读 → AI 生成整理建议 → 写入独立待审核区 → 人工确认 → 执行整理**

具体可以这样做：

1. **原件目录只读**

   AI 容器只能读取照片目录，不能删除、移动或修改原图。更稳妥的做法是让 AI 读取只读快照或专门复制的副本。

2. **输出目录单独开放写权限**

   AI 的数据库、缓存、缩略图、标签文件和识别结果放到独立目录。即使 AI 把自己的工作区全部删掉，也不会影响原件。

3. **先输出建议，不直接整理原件**

   AI 可以生成重复照片列表、人物分组、时间线和推荐目录结构，但不要自动永久删除照片。

4. **删除改为隔离**

   确认需要清理的照片先移动到回收区，保留一段时间。确认无误后，再由独立任务清理。

5. **AI 不接触备份**

   照片备份由另一个账号或备份系统负责，AI 容器没有备份目录的写权限，也不能管理 NAS 快照。

6. **容器不使用特权模式**

   不挂载宿主机根目录，不开放 Docker Socket，不复用 NAS 管理员账号。AI 应用需要写数据库时，只开放它自己的数据目录。

即使使用只读挂载，也要注意：只读主要防止修改和丢失，并不能防止数据被读取或上传。如果照片涉及隐私，还应优先选择本地模型，或者明确云端服务的数据传输和保存策略。

## 我的最终选择

我不会试图通过“少给 AI 一点能力”来解决所有问题，因为那也会牺牲 AI 自动化的价值。我更愿意把权限收束在明确的边界里：

- 工作区内尽量自由。
- 原件默认只读。
- 批量修改先产生结果，再审核执行。
- 删除必须有回收期和版本历史。
- 最后一份备份永远不在 AI 的控制范围内。
- 定期演练恢复，而不只是检查备份是否存在。

这样即使某次 AI 操作完全错误，最坏情况也只是重新恢复一个工作区，而不是失去多年积累的代码、文档和照片。

**真正安全的自动化，不是 AI 永远不会出错，而是它出错时，我仍然有能力把一切找回来。**
