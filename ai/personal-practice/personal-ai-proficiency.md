# 从会提问到能运营: 个人使用 AI 的六个熟练度阶段

```{contents}
```

判断一个人使用 AI 是否熟练, 最容易采用、也最容易误判的标准是: 会多少提示词技巧、用过多少模型、能不能解释 Transformer。更有区分度的标准其实是另外四件事:

1. 能否把模糊需求变成可验收的任务;
2. 能否验证 AI 的结果, 而不是凭感觉采纳;
3. 能否把一次成功变成可重复的工作流;
4. 能否让这套流程长期运行, 并对质量、安全和成本负责。

按这个标准, 个人使用 AI 大致可以分成 L0 到 L5 六个阶段。它们不是给人的永久评级, 而是针对某个任务域的能力描述: 一个人可能在编程 Agent 上到了 L4, 在数据分析上仍停留在 L1, 在图片生成上只是 L0。

## 六个阶段总览

| 阶段 | 角色变化 | 核心问题 | 代表性产出 |
|---|---|---|---|
| L0 尝鲜 | AI 是聊天工具 | 它能做什么 | 一次问答、一段草稿 |
| L1 提问 | AI 是初稿生产者 | 怎样稳定得到像样的结果 | 可复用的提问模板 |
| L2 协作 | AI 是工作搭档 | 怎样保证它真的做对 | 需求文档、验收清单、评审记录 |
| L3 流程化 | AI 是流程中的一个环节 | 怎样让成功重复发生 | 脚本、模板库、CI 任务、DAG |
| L4 构建 | AI 是能使用工具的系统 | 怎样完成多步骤、开放式任务 | Agent、工具集、RAG、记忆、评测 |
| L5 运营 | AI 系统是一项长期资产 | 怎样让它持续可信且值得投入 | 指标、轨迹、灰度、回滚、安全与成本报告 |

## L0: 尝鲜——知道 AI 能做什么, 也知道它不能做什么

这个阶段的典型用法是问概念、查语法、写一段文案。产出偶尔令人惊喜, 但结果高度依赖运气, 使用者也容易在“AI 无所不能”和“AI 都是胡说”之间摇摆。

**应该具备的知识:**

- 大模型是在生成概率上合理的文本, 不是在天然地查询事实;
- 幻觉、知识时效、上下文长度和隐私泄露是客观存在的边界;
- 同一个问题换种问法可能得到不同答案, 流畅不等于正确。

**应该掌握的技能:**

- 提出一个边界清楚的单点问题, 补充必要背景;
- 对日期、数字、法规、命令和代码等高风险内容做独立核验;
- 不把密码、客户数据、内部地址等敏感信息直接交给不可信的模型服务。

**进入下一阶段的标志:** 不再因为一次惊艳回答而盲信, 也不再因为一次错误回答而全盘否定; 能说出哪些任务适合交给 AI, 哪些必须由人核实。

## L1: 提问——从“偶尔答得好”到“稳定产出可用初稿”

这个阶段的重点不是背提示词口诀, 而是学会给模型足够明确的工作条件。

**应该具备的知识:**

- token、上下文窗口、模型能力差异和结构化输出的基本含义;
- 任务、背景、约束、示例和输出格式分别解决什么问题;
- 为什么长对话会遗忘前面的要求, 为什么重生成可能丢掉已经正确的部分。

**应该掌握的技能:**

- 用“任务 + 背景 + 约束 + 输出格式 + 验收标准”组织需求;
- 给一两个高质量示例, 而不是堆很多互相矛盾的要求;
- 通过局部修改、追问和反例迭代, 把有效问法保存成模板;
- 要求输出 JSON、表格或固定章节, 让结果便于检查和复用。

**进入下一阶段的标志:** 同一类任务不是偶尔得到好答案, 而是能重复得到八九不离十的初稿, 并且知道怎样修改不满意的局部。

## L2: 协作——从“得到答案”到“共同交付可验收结果”

从这一阶段开始, 人和 AI 的关系不再只是“问与答”, 而是共同完成真实工作。熟练度的核心也从表达能力转向**定义完成和验证结果的能力**。

**应该具备的知识:**

- 单一事实源、需求版本、优先级、验收标准和需求溯源;
- 上下文工程的基本思想: 模型答不好, 可能是该读的材料没有给它;
- 生成者与评审者分离、人工检查点、增量修改和最小变更;
- 代码、文档、测试用例等不同产出各自应该怎样验证。

**应该掌握的技能:**

- 把模糊需求写成带编号的文档, 先让 AI 复述、找冲突和缺口, 再允许它动手;
- 要求结论附出处, 代码审查意见附文件和行号, 无法确认的内容显式标记“需澄清”;
- 用测试、构建、引用核对、抽样复核或另一模型评审来检查结果;
- 保留“需求 → 产出 → 验证”的对应关系, 不让要求散落在聊天记录里。

**进入下一阶段的标志:** 交付物不再是一段看起来不错的聊天内容, 而是有依据、有验收记录、能进入真实项目的结果。

### 本地记录对照: 我已经跨过了这一阶段

我的[需求提问记录](../coding/requirements-prompting.md)已经使用需求编号、优先级、单一事实源、生成前复述、冲突裁决和验收溯源; [结对编程记录](../coding/pair-coding.md)则把“开发与审查分离”“审查只读”“意见必须带文件和行号”落成了具体流程。这说明我已经不只是会要初稿, 而是在有意识地控制 AI 交付的质量。

## L3: 流程化——从“一次协作成功”到“流程可以重复执行”

当同一个动作每周都要做几次, 继续复制聊天记录就会变成负担。这一阶段要把验证过的协作方式固化成模板、脚本和流水线。

**应该具备的知识:**

- API、JSON、工具调用、版本管理和基本自动化;
- 工作流与 Agent 的区别: 流程已知时优先固化, 不必把每一步都交给模型自由发挥;
- DAG、缓存、重试、超时、幂等、并发限制和中间产物;
- 权限最小化, 以及哪些节点必须保留人工确认。

**应该掌握的技能:**

- 把“生成 → 审查 → 修复 → 验证”写成可重复运行的脚本;
- 将稳定流程接入 Git、CI 或定时任务, 让输入、输出和失败都有记录;
- 把长任务拆成有独立产物的节点, 支持局部重跑和失败定位;
- 把提示词、Skill、项目记忆和领域文档纳入版本管理;
- 数据量确实需要时再引入 RAG, 而不是把向量库当作默认答案。

**进入下一阶段的标志:** 至少有一条真实工作流成功运行多次; 失败时有日志可查, 修改一个环节不必全部重来, 高风险动作仍受人控制。

### 本地记录对照: 我已经有了流程化实践, 不只是流程概念

[DAG 记录](../agent-engineering/dag.md)中的最小执行器包含拓扑调度、并行、节点缓存和失败重试, 并记录了缓存键遗漏代码版本这一真实问题及其修复; [内网 DSH 接入记录](../tools/dsh-intranet/README.md)进一步把协议探测、配置、冒烟、故障诊断和 mock 验证做成了工具箱。这些实践说明我已经能把 AI 协作固化为可检查、可重跑的工程流程。

## L4: 构建——从“调用 AI”到“设计能完成任务的 Agent 系统”

这一阶段的主角不再是一条工作流, 而是一个能够根据中间结果选择下一步动作的系统。它需要模型, 也需要工具、上下文、状态和边界。

**应该具备的知识:**

- Function Calling、Agent 循环、MCP、RAG、短期状态与长期记忆;
- Agent 循环、DAG、多 Agent 各自的适用边界;
- 工具描述、结构化契约、上下文裁剪、轨迹记录和失败传播;
- 评测集、任务成功率、工具调用正确率、成本与延迟;
- 提示词注入、沙箱、权限隔离和危险操作人审。

**应该掌握的技能:**

- 设计原子、明确、返回短小结构化结果的工具;
- 让 Agent 在最大轮数、超时、重试和权限范围内工作;
- 根据任务选择单 Agent、工作流或多 Agent, 而不是为了架构先进而堆组件;
- 保存并回放运行轨迹, 从失败样本反推上下文、工具或流程的问题;
- 用固定评测集比较模型、提示词、工具和检索方案的改动。

**进入下一阶段的标志:** Agent 不只是演示时完成过一次任务, 而是能在明确边界内反复完成多步骤任务; 成功率可以度量, 失败可以分类, 副作用受到约束。

## L5: 运营——从“系统能跑”到“长期可信、可改进、算得过账”

L5 的分水岭不是系统更复杂, 而是出现了持续的证据链: 每次变更好在哪里、每次失败为什么发生、每份成本换来什么价值, 都能用数据回答。

**应该具备的知识:**

- 真实评测集、数据分层、人工标注、LLM-as-judge 校准和回归评估;
- 全链路轨迹、质量与性能指标、告警、故障回放和失败聚类;
- 灰度发布、版本兼容、回滚、审计、数据生命周期和多租户隔离;
- 单任务成本、P95 延迟、人工接管率、采纳率和投入产出比。

**应该掌握的技能:**

- 从真实成功与失败样本中持续维护 golden 集, 防止评测集只代表演示场景;
- 把低分轨迹聚类为知识缺失、工具错误、规划遗漏、格式错误等可行动的类别;
- 对模型、提示词、Skill、记忆和工具分别做版本管理与回滚;
- 主动进行提示词注入、越权、敏感信息泄露和故障恢复演练;
- 根据质量、延迟和成本选择模型与流程, 并敢于删除没有收益的组件。

**这一阶段的代表性交付:** 一份持续更新的运行报告, 至少包含任务成功率、人工修正率、失败分类、P95 延迟、单次被采纳结果的成本, 以及最近一次回归和回滚的结果。

## 我当前最需要补的技能和经验

### 1. 把小型演示评测升级为真实任务评测

[RAG 评测脚本](../fundamentals/rag_demo/eval_rag.py)已经用 12 道标注问题比较 HitRate@k, 这是很好的起点, 但它主要回答“检索器能否找到正确片段”, 不能代表完整 Agent 的任务成功率。

下一步应选一条真实流程, 例如 CI 失败分诊或 Redis 升级测试, 先积累约 50 条来自真实工作的样本。每条样本包含输入、期望行为、证据出处、可接受的答案差异和风险等级, 并覆盖正常、边界、历史故障与对抗场景。每次换模型或改模板都跑同一套回归, 用分数变化代替“感觉更好”。

### 2. 积累连续运行和失败复盘经验

本地记录中方案设计多, 连续运行数据相对少。需要让一条流程在真实项目里持续运行数周, 保存模型、提示词、工具和知识版本, 以及输入、工具调用、输出、耗时、token 和人工修改记录。

重点不是追求“全自动”, 而是每周回答三个问题: 哪类失败最多, 人工在哪一步接管, 哪个改动让指标真实改善。这样才能把[自进化方案](../testing/agent-testing-platform/self-evolution.md)里的“失败聚类 → 定位层级 → 实验验证”从设计变成经验。

### 3. 把安全与可靠性知识变成演练记录

现有文章已经正确强调最小权限、沙箱、注入防护、灰度和回滚, 下一步要证明这些机制真的有效。至少应主动演练:

- 在工具输入中放入恶意指令, 验证 Agent 不会越过权限;
- 在多用户知识和记忆中检查跨用户泄露;
- 对重复执行、超时、限流和工具返回异常验证幂等与降级;
- 分别回滚一次模型、提示词、Skill 和记忆变更, 确认旧版本可恢复。

“知道应该做什么”属于 L4 的知识储备, “做过并留下证据”才是 L5 的运营能力。

### 4. 建立价值核算, 而不只统计 token 和生成量

需要保留人工基线: 同类任务不用 AI 时花多久、错误率多少。然后再比较 AI 流程的端到端耗时、人工修正时间、采纳率和基础设施成本。

真正值得跟踪的是“每个被采纳结果的总成本”和“节省的人工时间”, 而不是生成了多少用例、调用了多少模型。这个核算也会帮助决定什么时候该用小模型、单 Agent、固定 DAG, 甚至不用 AI。

### 5. 练习做减法, 形成技术选型判断

我已经整理了 DAG、多 Agent、RAG、共享记忆、Skill 个性化和自进化等方案, 下一阶段更重要的能力可能不是继续增加组件, 而是判断哪些组件当前不需要。

例如, 固定流程不急着改成多 Agent; 文档能被工作区检索时不急着上向量库; 用户反馈没有形成可靠标签时不急着自动更新画像。能说明“为什么不采用更复杂的方案”, 是系统构建者走向运营者的重要标志。

## 当前不必优先补什么

如果目标仍是 AI 应用与测试智能体, 而不是模型训练或推理引擎研发, 我暂时不必把主要精力放回补更多 Transformer 推导、收集更多框架 API, 或画更大的多 Agent 架构图。现有记录里的原理与架构储备已经足够支撑下一阶段实践。

更短的一条行动路线是:**选一个真实、读多写少、容易由人评审的流程, 给它补上 golden 集、全链路轨迹、安全演练和价值报告, 连续运行并复盘。** 这份证据比再增加十篇概念笔记更能推动我进入 L5。

## 结语

个人使用 AI 的成长, 不是从“不会写提示词”走向“会写更玄的提示词”, 而是不断扩展自己能够对结果负责的范围:

- L0 到 L1, 对提问负责;
- L2, 对交付结果负责;
- L3, 对重复流程负责;
- L4, 对 Agent 系统负责;
- L5, 对系统长期产生的质量、风险和价值负责。

我当前正处在 L4 向 L5 过渡的位置。下一步最关键的不是让系统看起来更自主, 而是让它在真实使用中更可验证、更可解释, 也更值得信任。
