# 弱模型被迫分层,会比强模型的「摊平」更好读吗

```{contents}
```

> 问题:理解整个项目架构时,强模型上下文大、一口吞下,产出容易摊得平;
> 弱模型装不下、被迫一块一块看,产出天然分层——后者反而更利于人类阅读理解?
> 这个直觉对了一半,但归因错了。

## 一、直接结论

- **对的一半**:人类读架构确实要分层(progressive disclosure)。
  一份「信息完备但平铺」的架构描述,对人是灾难——没有地图,只有全部街景。
- **错的一半**:强模型摊平不是能力问题,是**默认输出格式**问题;
  弱模型分层不是优点,是**被迫的生存本能**。而分层这件事的质量,
  恰恰取决于弱模型最缺的东西——全局视野。
- 所以答案不是「换弱模型」,而是:**给强模型加分层输出契约**;
  项目大到装不下时,用 **map-reduce 两阶段**——小模型做局部摘要(它本来只需要局部),
  大模型做全局综合(跨模块判断必须它来)。弱模型在这个 pipeline 里有位置,
  但位置是 map 不是 reduce。

## 二、为什么「弱模型分层更好」大多不成立

### 1. 分层的本质是选抽象边界,这是个全局活

好的架构分层 = 按**职责和依赖方向**切(接入层 / 领域层 / 基础设施层),
不是按目录切。要知道「这几个文件该归一层」,得先看到它们和别处的调用关系。
弱模型一次只看一个目录,切出来的只能是**物理边界的复读**:
「`src/foo/` 里有这些文件,`src/bar/` 里有那些文件」——这是目录树,不是架构。

### 2. 块间关系靠猜,幻觉依赖最伤人

逐块摘要时,每块内部基本没问题,但**块与块之间**的调用关系、数据流、
时序,弱模型只能根据块内看到的 import 和命名去推断。推断错的比例不低,
而且错得自信——「A 模块调用 B 模块的 `process()`」写得斩钉截铁,
实际是 A 发出事件、B 异步消费。人类拿着这份分层图去读代码,
**每一步对不上都在消耗信任**,比没有图更糟。

### 3. 局部正确 ≠ 全局正确

每份局部摘要单独看都通,拼起来对不上:接口名漂移、字段语义漂移、
同义词不统一(这块叫「订单」,那块叫「交易」)。把 N 份局部摘要合并成
一份一致的全局视图,本身就是一次需要推理的 reduce——这正是弱模型做不了的那步。

## 三、强模型为什么摊平,怎么治

不给结构约束时,模型的默认策略是「信息完备的流水账」——它不知道你只要 L1 地图,
它怕漏。治法是**输出契约**,不是换模型。可照抄的分层输出模板:

```text
你要为这个项目写一份架构说明,严格按三层结构输出,禁止越层:

L1 一页纸(≤300 字 + 一张 mermaid 图):
  - 这个系统是干什么的(一句话)
  - 分成哪几大块(不超过 7 块,每块一句话职责)
  - 块与块怎么连(只画块间依赖,不画块内细节)
  到 L1 为止,不许出现任何文件名、函数名、字段名。

L2 模块卡(每块一张卡,每张卡 ≤150 字):
  - 职责 / 输入 / 输出 / 依赖的其他模块 / 入口文件路径(只给路径,不贴代码)

L3 下钻指引(每块 3 条以内):
  - 「想看 X 的细节,去读 文件:行号」格式的指针列表。

硬性规则:
  - 每层必须能独立读懂:只看 L1 就能向别人讲清这个系统;
  - 不确定的依赖关系标 ⚠️ 并说明两种可能,禁止编造;
  - 总长度超预算时,砍 L3,不许砍 L1。
```

同一个强模型,加不加这段契约,产出形态完全不同。**摊平是提示词问题,不是模型档位问题。**

## 四、直觉里真正值钱的部分:装不下 → 分治,这是对的

项目大到任何模型都装不下时,「被迫分块」就从缺点变成了唯一选择。
这时候正确的姿势不是让弱模型自己拼,而是 **map-reduce**:

```text
# map 阶段 prompt(派给小模型,每个模块一次,彼此并行、互不感知)
你只负责 <模块路径> 这一个目录。读完后输出一张模块卡:
  职责(一句话) / 对外暴露的接口(签名级) / 依赖了哪些模块(只写你
  在 import / 调用里亲眼看到的,标 ✅;推断出来的标 ⚠️ 并写依据) /
  关键数据结构(名字 + 一句话) / 入口文件。
≤200 字,不许评价设计好坏,不许推测其他模块的内部。

# reduce 阶段 prompt(派给大模型,输入是全部模块卡)
附件是 N 份模块卡,每份由独立代理对单个模块实地阅读后产出。
你的任务:
1. 交叉校验:不同卡片对同一依赖的描述是否一致,接口名/字段是否对得上,
   对不上的列成「矛盾清单」;
2. 自顶向下重组:把卡片按职责聚成不超过 7 个大块,画块间依赖图;
3. 按 L1/L2/L3 三层输出最终架构文档(结构同上节模板);
4. 所有 ⚠️ 标记的推断依赖,要么在卡片间找到旁证升级为 ✅,
   要么保留 ⚠️ 并写进「待人工确认」清单。
```

关键洞察:**生产顺序和消费顺序是反的。**

- 机器生产自底向上:文件 → 模块卡(map)→ 全局视图(reduce);
- 人类消费自顶向下:L1 地图 → L2 模块卡 → L3 源码。

把自底向上的材料**重组成自顶向下的叙事**,是 reduce 阶段的核心工作,
需要同时拿着全部卡片做聚类、校验、取舍——这活必须给大模型。
弱模型在 map 位置是能力匹配的(局部阅读本来就不需要全局上下文),
还顺手省 token(参见 [./model-routing.md](./model-routing.md))。

## 五、三档方案对比

| | 档 1:强模型 + 分层模板 | 档 2:map-reduce 两阶段 ★ | 档 3:AgentTeams 分层团队 |
|---|---|---|---|
| 适用规模 | 整个项目装得进上下文 | 装不下,模块各自装得进 | 架构文档要长期保鲜 |
| 做法 | 一次调用 + 第三节模板 | 小模型 map,大模型 reduce | 每层独立产出 + 独立评审,矛盾清单走 repair 循环 |
| 分层质量 | 高(全局视野在) | 高(局部实地 + 全局校验) | 高,且可持续更新 |
| 成本 | 一次大模型调用 | N 次小模型 + 一次大模型 | 最高(多角色多轮) |
| 主要风险 | 项目大了装不下 | map 卡质量参差,靠 reduce 交叉校验兜底 | 工程复杂度,值得与否看维护频率 |
| 可溯源性 | 中(L3 指针靠模型自觉) | 高(每张卡有出处,⚠️ 机制) | 高(评审留痕) |

**建议:日常用档 1 起步——先用分层模板验证「你要的三层长什么样」;
项目装不进上下文就升档 2;档 3 只在架构文档要跟着代码长期演进时才值。**
无论哪档,「弱模型单独干全程」都不在表里:它省的那点钱,
会在「人拿着错的分层图读代码」的环节加倍还回去。
