```{contents}
```

如果你在一个 Agent 项目里担任 DAG 模块负责人, 这篇文章给出两份清单: 你手里应该有哪些产出, 以及汇报时怎么呈现。技术背景见 [AI 工作流里的 DAG](./dag.md)。

## 一、产出清单(Deliverables)

| 类别 | 具体产出 | 汇报中的作用 |
|------|---------|------------|
| 框架层 | DAG 执行器(拓扑调度、并发、缓存、重试、循环检测) | 证明"底座稳" |
| 接口层 | 节点注册接口、统一 LLM 节点封装(如 `ask_kimi` 那种) | 证明"业务方好接入" |
| 业务层 | 已固化的流程模板/图定义(N 张图在跑) | 证明"有真实落地" |
| 可观测 | 中间产物落盘、失败节点报告、审计能力 | 证明"出问题能查" |
| 质量 | 节点 eval、回归测试、缓存键含代码版本等坑的修复记录 | 证明"质量可控" |

## 二、汇报呈现结构(一页纸 / 10 分钟版)

### 1. 模块定位(30 秒)

一句话: "DAG 负责流程可枚举的部分——可预测、可审计、必终止; 开放探索交给 Agent 循环。两者是分工不是替代。" 这句定位每次都讲, 让听众建立稳定预期。

### 2. 本期进展(里程碑式, 不讲代码行数)

- M1 执行器跑通 → M2 接真实 LLM 节点端到端 → M3 生产化(限流、失败跳过) → M4 沉淀模板
- 每个里程碑配一个状态: ✅ 完成 / 🚧 进行中 / 阻塞原因

### 3. 现场 demo(汇报的核心, 用运行日志说话)

按 DAG 已验证的四个收益演示:

- **局部重跑**: 现场改一个节点 → 日志显示只有该节点执行, 上游全部命中缓存
- **并行**: 展示两个无依赖分支的完成时间戳几乎同时
- **可审计**: 打开 `.dag-cache/` 中间产物, 演示"报告出错如何逐环定位"
- **失败兜底**: 注入两次异常, 第三次重试成功

### 4. 量化指标(一屏表格)

- 缓存命中率、端到端耗时对比(并行前后)、token 消耗对比(vs 单条长 prompt)、节点失败率/重试成功率

### 5. 边界与风险(主动讲, 反而加分)

- 哪些任务明确不走 DAG(开放探索类), 当前走 Agent 循环, 固化后再 DAG 化
- 已知坑和处理: 并发打爆 API 限额(线程池按配额设限)、节点拆太碎(编排开销超收益)

### 6. 下步计划

下个里程碑 + 需要的支持(如 API 配额、业务方接入排期)。

## 三、不同场合的裁剪

- **周会**: 只讲进展 + 指标变化 + 风险阻塞, 5 分钟
- **月度/季度汇报**: 完整六段, demo 是重头戏
- **述职/答辩**: 产出清单 + 指标 + "边界认知"(说明你理解模块在整体架构中的位置, 而非只会写代码)

## 总结

DAG 模块的汇报优势是可演示性——少讲设计文档, 多放运行日志和缓存命中截图, 让四个收益(局部重跑、并行、可审计、必终止)被亲眼看到。
