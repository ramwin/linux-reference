```{contents}
```

> 背景:主会话用 Kimi(k3-256k)时 token 消耗过快。
> 本文回答两个问题:(1) 通用的「按业务选模型」怎么做;(2) 在 DSH 里具体怎么配。

## 一、先搞清 token 为什么烧得快

Agent harness(不只是 DSH,kimi-code / Claude Code 同理)的计费模型和普通聊天不一样:

1. **每一轮都重发完整上下文**。系统提示、工具定义、历史消息、历次工具输出,
   每一轮请求都原样再发一遍。会话越长,每轮的输入 token 越大——
   **输入 token 才是大头**,不是模型回复的那几百字。
2. **工具输出是隐形炸弹**。一次 `read` 大文件、一次 `web_search`、
   一次 `bash` 的长 stdout,轻松几千上万 token,而且会留在历史里被后续每一轮重发。
3. **所有轮次都按旗舰模型计费**。主会话挂了 k3-256k,那么连「嗯,继续」
   这种一句话的轮次,也是带着几万 token 上下文按 k3 的价格走。

结论:省 token 的杠杆有两个——**给不同的活配不同大小的模型**(路由),
和**压上下文本身**(上下文工程)。后者往往比换模型更立竿见影。

## 二、核心思路:不是「换小模型」,是「按业务路由」

### 任务分级:什么活配什么模型

| 任务类型 | 特征 | 建议档位 |
|---|---|---|
| 闲聊、简单问答、改写、摘要 | 无工具调用或极少 | 小模型 |
| 定时收集、新闻整理、批量格式化、逐文件扫描 | 机械、可并行、单点质量要求低 | 小/中模型 |
| 子代理调研、搜索结果初筛 | 只看结论,不看过程 | 小/中模型 |
| 日常编码、bug 修复、测试编写 | 需要工具链 + 一定推理 | 中/大模型 |
| 架构设计、复杂调试、方案评审、最终把关 | 错一步代价高 | 大模型 |
| 多代理团队的队长(规划/分派/汇总) | 需要全局判断 | 大模型 |

经验法则:**「过程不重要、只看结论」的活下沉给小模型;「错不起」的活留给大模型。**

### 路由方式:从简单到复杂三档

**档 1:人工分流(约定俗成)**

不加任何自动化,自己养成习惯:闲聊开小模型会话,正事开大模型会话。

- 优点:零成本、零风险,今天就能用。
- 缺点:靠自觉,懒了就回到「一切走大模型」。

**档 2:规则路由(按入口/任务类型静态分流)** ★ 推荐

在 harness 配置层把「入口」和「模型」绑定死:定时任务固定小模型、
子代理固定中模型、主会话固定大模型、多代理团队按角色配模型。
不需要任何「判断」,规则是人定的,行为完全可预测。

- 优点:可控、可审计、无额外调用开销;省 token 的大头(批量任务、
  子代理、定时任务)全被覆盖。
- 缺点:规则覆盖不到「同一会话内任务难度波动」的情况。

**档 3:自动判别路由(classifier / escalation)**

两种做法:

- **Classifier 前置**:每次请求先过一个便宜的小模型,判断复杂度,
  再路由到大/小模型。类似 Martian、OpenRouter Auto、RouteLLM 的思路。
- **Escalation(先小后大)**:一律先给小模型做,失败/置信度低/自检不过
  再升级大模型重试。

- 优点:理论上最省,粒度最细。
- 缺点:classifier 判错的代价不对称(该大的给了小的,产出垃圾浪费更多
  token 去返工);escalation 有重试延迟;工程复杂度最高,还需要维护
  「判得准不准」的评估集。

### 对比与建议

| 维度 | 档1 人工 | 档2 规则 | 档3 自动判别 |
|---|---|---|---|
| 实施成本 | 零 | 低(改配置) | 高(要写路由层) |
| 省 token 效果 | 看人 | 覆盖 80% 场景 | 理论最优 |
| 行为可预测性 | 高 | 高 | 中(判错有隐性成本) |
| 维护负担 | 无 | 无 | 持续(模型更新要重调) |

**建议:档 2 为主,档 1 兜底,档 3 只在「自建产品、量足够大」时才值得做。**
对个人使用,规则路由 + 上下文工程已经能把 token 砍掉一大半,没必要上 classifier。

## 三、上下文工程:比换模型更省的几招

1. **子代理隔离上下文**:把「读一堆文件再给个结论」的活丢给子代理,
   子代理读掉的几十万 token 不进主会话历史,主会话只看到结论。
2. **自动压缩(compaction)**:长会话到上下文上限前,把旧历史压成摘要。
3. **工具输出裁剪**:大文件别全量 read,用 grep 定位再按 offset/limit 读;
   长命令输出重定向到文件再分段看。
4. **及时开新会话**:一个任务做完了就开新会话,别让无关历史跟着烧。
5. **盯着计量**:装了 token/cost 计量插件就定期看,找到烧钱大户再针对性优化。

## 四、DSH 里具体怎么做

DSH 的模型路由是**分层**的:profile 默认 → 会话级选择 → 每类入口的独立覆盖。
按「省 token 收益从大到小」排:

### 1. 定时任务单独配小模型(最大头之一)

面板的「⏰ 每日定时」里,每个新闻定时任务有独立的**新闻采集模型**配置。
新闻收集是典型的「机械、量大、只看结论」任务,给小模型即可,
不必跟主会话一起烧旗舰模型。

### 2. 子代理(subagent)指定模型

`subagent` 的 spawn 后端支持在启动请求里覆盖 provider/model/reasoning effort
(`agentOptions`)。把调研、初筛类子代理指给便宜模型,主会话保持旗舰:

```text
# 语义示例:让子代理用小模型跑调研
subagent(prompt="调研 xxx 并给出结论", provider=deepseek, model=deepseek-chat)
```

### 3. workflow:按阶段配模型

workflow 脚本里 `agent(prompt, { provider, model, phase })` 支持
**逐个子代理、逐个 phase** 覆盖模型。批量审计/迁移类 workflow 的
执行 phase 用小模型,最终汇总 phase 用大模型。

### 4. AgentTeams:按角色配模型

团队里每个 member 可以单独指定 `model`/`provider`/`reasoning_effort`:
**队长(captain)用大模型**做规划、评审、汇总;**干活的 member 用小/中模型**。
这是「档 2 规则路由」的天然落地——角色即规则。

### 5. profile 默认模型与会话级切换

默认模型在 profile patch 里:

```yaml
# ~/.dsh/profiles/web/cordis.patch.yml(节选)
- id: agent-default-model
  name: "@deepseek-ai/dsh-agent-default-model"
  config:
    provider: kimi-subscription   # 默认入口:可改成更便宜的 provider
    model: k3-256k                # 如 deepseek / deepseek-chat
    # reasoningEffort: low        # 简单任务连推理强度都可以降
```

单个会话临时换模型:GUI 输入框旁的模型选择器,即选即用,
不改全局默认。闲聊会话随手切到小模型就是「档 1 人工分流」。

### 6. 压缩与计量(上下文工程)

- `dsh-compaction-basic` 默认启用:接近上下文上限自动压缩旧历史,
  也支持手动 `/compact`。
- `dsh-cost-meter` 插件:看每个会话的 token/费用分布,
  先找到烧钱大头再动手。

### 7. 想再进一步:provider 级分流

Kimi 订阅与 DeepSeek API key 可以并存。一个实用的省钱组合:

| 入口 | provider/model | 理由 |
|---|---|---|
| 主会话(架构、复杂编码) | kimi-subscription / k3-256k | 质量优先 |
| 子代理调研、初筛 | deepseek / deepseek-chat | 便宜量大 |
| 定时新闻采集 | 小模型 | 机械任务 |
| AgentTeams 队长 | k3-256k | 全局判断 |
| AgentTeams 成员 | 小/中模型 | 执行为主 |

改默认模型的稳妥做法:改 profile patch 后 `dsh web --dump-config` 预检,
确认组合树没问题再重启生效。

## 五、落地清单(按投入从小到大)

- [ ] 面板里给新闻定时任务配小模型(5 分钟,立刻省)
- [ ] 养成「闲聊/简单活切小模型会话」的习惯(档 1)
- [ ] 子代理/workflow 的批量阶段显式指定便宜模型(档 2)
- [ ] AgentTeams 团队按角色配模型:队长大、成员小(档 2)
- [ ] 定期看 cost meter,定位新的烧钱大户
- [ ] (可选,且仅当量够大)再考虑 classifier/escalation 自动路由(档 3)
