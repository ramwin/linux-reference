# 让 AI 并行开发一个代码仓的多个功能：方案全景

```{contents}
```

手里攒了五个需求，一个编码 Agent 串行做，一个下午只能交付一两个。第一反应是"多开几个 Agent 不就行了"——真这么干了就会发现：几个 Agent 对着同一个工作目录改，`git status` 乱成一锅粥，A 刚改的文件被 B 覆盖，最后谁也说不清楚哪个改动属于哪个功能。

并行开发的核心不是"多开"，而是回答三个问题：**工作区怎么隔离、任务怎么编排、产出怎么验证并合回主干**。本文按"从简单到复杂"的顺序过一遍主流方案，最后给对比表和选择建议。

## 一、先想清楚：并行要解决的三件事

任何"让 AI 并行开发"的方案，都是对这三件事的不同取舍：

| 问题 | 不解决会怎样 |
|------|-------------|
| **工作区隔离** | 多个 Agent 同时写同一批文件，互相覆盖，git 状态无法归属 |
| **任务切分与编排** | 两个 Agent 做了重复的事，或都以为对方会做，集成时发现缺块 |
| **验证与合并** | 五个分支同时回来，冲突爆炸；没有独立验证，合进去就是埋雷 |

后面的方案一~四，隔离程度从"共享一个目录"到"一人一容器"递增，编排成本也递增。

## 二、方案一：手动多开 + git worktree（最轻量，人当调度器）

最朴素的办法：开几个终端窗口，每个窗口跑一个 Agent 实例，各做一个功能。关键配套是 `git worktree`——同一个仓库同时 checkout 出多个工作目录：

```bash
# 在 myrepo 里为两个功能各开一个工作区
git worktree add ../myrepo-feat-login -b feat/login
git worktree add ../myrepo-feat-pay   -b feat/pay

# 每个目录里启动一个独立的 Agent
cd ../myrepo-feat-login && claude
cd ../myrepo-feat-pay   && kimi

# 结束后清理
git worktree list
git worktree remove ../myrepo-feat-login
```

几个关键性质：

- worktree 之间**共享同一个 `.git` 对象库和 refs**，省磁盘、分支互认；但各自有独立的 HEAD 和 index，互不污染；
- 同一个分支不能在两个 worktree 里同时 checkout（这就是为什么每个功能要建自己的分支）；
- 人负责分任务、盯进度、逐个 merge/rebase——**人是调度器**。

适合 2~4 个功能、模块边界清晰、个人开发者。常见的坑：

| 坑 | 解法 |
|----|------|
| `node_modules` / venv 每个 worktree 要独立装一份 | 脚本化 `npm install`，或用 pnpm store 共享缓存 |
| 多个 dev server 同时跑，端口冲突 | 每个 worktree 配不同端口环境变量 |
| IDE 对多目录索引卡顿 | 每个 worktree 单独开窗口，别放进同一个 workspace |
| 未跟踪文件（`.env`、本地配置）不会随 worktree 走 | `git worktree add` 后手动拷贝或用 dotenv 模板 |

## 三、方案二：云端异步 Agent（隔离最彻底，人当 reviewer）

把"每个功能一个隔离环境"推到极致：每个任务在独立的容器/VM 里 clone 仓库，Agent 在云端跑，完成后自动开 PR 等人审。代表产品：

- **GitHub Copilot coding agent**：直接给 Copilot assign issue，它在 GitHub Actions 驱动的沙箱里干活，产出 PR；
- **OpenAI Codex（云端任务）**：每个任务一个预装环境的容器，可并行跑多个任务；
- **Google Jules、Cursor background agents、Claude Code on the web、Devin**：形态类似，都是"异步派发 → 沙箱执行 → PR 回来"。

| 优点 | 缺点 |
|------|------|
| 容器级隔离，彻底不怕互相干扰 | 异步反馈慢，不适合边聊边改 |
| 不占本机资源，关掉电脑也在跑 | 沙箱访问不到你的内网服务、私有依赖、本地数据 |
| PR 模型天然接入现有 CI 和 review 流程 | 看不到本地未提交的上下文 |
| 任务可以排队派发，并行度几乎不受限 | 按任务/时长计费，成本随并行度线性涨 |

适合边界清晰的"工单式"任务：修一个独立 bug、补一批测试、做一个小功能。不适合需要频繁往返确认的探索式开发。

## 四、方案三：单会话内 subagent 并行（编排内置，共享工作区）

主流编码 CLI 都内置了子代理机制：主 Agent 在一个会话里派出多个 subagent 并行干活，各自完成后把结论带回主会话。Claude Code 的 Task/subagents、Kimi Code 的 subagent、DSH 的 `subagent`/`workflow` 都是这个形态，其中 workflow 可以写一段 JS 编排脚本，把上百个独立子任务（比如"审计这几百个文件"）扇出给子代理流水线执行。

这个方案最大的收益其实是**上下文隔离**：每个 subagent 有独立的 context window，各自读完几十个文件后只把结论回传，主 Agent 的上下文不被中间过程淹没。

但要特别注意：所有 subagent **共享同一个工作目录**。所以它适合两类活：

1. **读多写少**：并行审计、调研、批量分析——只读不冲突；
2. **写入区域完全不重叠**：事先按文件/目录边界划好势力范围，每个 subagent 只写自己的地盘。

如果多个 subagent 都要写同一批文件，这个方案会退化成方案一之前的混乱状态——隔离得靠方案一的 worktree 或方案四的分支补上。

## 五、方案四：多 Agent 团队编排（captain-worker，带质量门）

再往上走一步：不止并行干活，还要把"谁干什么、什么算干完、谁来验收"流程化。一个 captain（队长 Agent）把需求拆成任务 DAG，多个 worker 领取执行，任务之间声明依赖，质量门内建：

```{mermaid}
flowchart LR
    C[Captain<br/>拆任务 / 派工 / 验收] --> T1[任务 A<br/>feat/login]
    C --> T2[任务 B<br/>feat/pay]
    C --> T3[任务 C<br/>feat/report]
    T1 --> R[Review 质量门]
    T2 --> R
    T3 --> R
    R --> I[集成 + 回归]
    R -->|不通过| FIX[repair 修复任务] --> R
```

代表实现：

- **Claude Code Agent Teams**、**DSH AgentTeams**：captain 建队、建任务 DAG、worker 各自 claim 任务；任务可带验收标准和 verify 命令，review 不通过自动生成修复任务并回流；人随时可以查看进度、接管任务；
- 自研编排：**LangGraph / CrewAI / AutoGen / MetaGPT / OpenHands** 等框架，自己定义角色和状态机，灵活但要自己处理持久化、中断恢复、人机接管。

与方案三的本质区别：成员是**持久的独立会话**，任务有契约（目标、验收标准、归属人）和状态机，能跨小时甚至跨天协作，失败可重派、可换人。工作区隔离通常给每个成员/任务配独立分支或 worktree，把方案一的隔离手段嵌进方案四的编排里。

代价也很实在：编排本身消耗 captain 的上下文和 token；任务切得不好，冲突会在集成阶段集中爆炸——切分功力直接决定这个方案的上限。

## 六、方案对比

| 维度 | ① worktree 多开 | ② 云端异步 Agent | ③ 会话内 subagent | ④ Agent 团队 |
|------|----------------|------------------|-------------------|--------------|
| 隔离级别 | 目录+分支级 | 容器级（最彻底） | 共享目录，靠自觉划界 | 分支/worktree 级 |
| 编排者 | 人 | 平台（issue→PR） | 主 Agent | captain Agent + 人 |
| 并行度上限 | 人盯得过来的几个 | 几乎不限 | 几个~几十个（短任务） | 几个~十几个（长任务） |
| 反馈速度 | 实时交互 | 异步，分钟~小时级 | 实时 | 近实时 |
| 质量门 | 无，靠人 | CI + 人 review PR | 主 Agent 把关 | 内建 review/verify 契约 |
| 典型成本 | 本机 token | 平台计费 + token | token | token（编排开销最大） |
| 适合场景 | 2~4 个功能的日常开发 | 工单式、边界清晰的任务 | 并行调研/审计/批量分析 | 一个迭代的多个功能，要质量保障 |

## 七、无论选哪个方案，都绕不开的工程实践

**任务切分按文件边界走。** 并行冲突的物理本质是两个 Agent 写同一批文件。切任务时先画出每个功能的改动文件清单，重叠部分要么合并成一个任务，要么先把公共部分（接口定义、类型、DB migration、路由注册表）单独做掉再并行。

**先定契约，再并行。** 各功能之间的接口（函数签名、API schema、事件格式）由一个任务先行确定并合入主干，其余功能面向契约开发，而不是面向彼此的实现。

**短命分支，小步合并。** 并行的分支活得越久，合并冲突的期望越大。功能拆小、频繁 rebase 主干、尽早合回——这套 trunk-based 的基本功在 AI 并行时代重要性翻倍。

**每个分支独立跑完整验证。** 把"测试通过"前置为合并的硬条件（verify 命令 / CI 绿灯），而不是合并后再补救。

**承认 review 是最终瓶颈。** 生成可以并行，审查只能串行——并行度越高，PR 队列越长，人的注意力没有变多。机器能查的（规范、测试、类型）全部前置给机器，人的 review 集中到设计取舍上。这个话题展开见 [代码越产越快，Review 跟不上：AI 时代的审查瓶颈怎么破](./ai-era-code-review-bottleneck.md)；用异构模型交叉审查的思路见 [Kimi Code + Claude Code 结对编程](./pair-coding.md)。

**上下文要所有 Agent 都读得到。** 项目约定写进 `AGENTS.md` / `CLAUDE.md`，重要决策留 ADR——并行时每个 Agent 都是"新入职的同事"，没有共享文档就会各自发明约定。

## 八、选择建议

- **个人开发者，2~4 个功能**：方案一（worktree + 多开终端），零学习成本，先跑起来；
- **工单式任务、可以接受异步**：方案二（云端 Agent），把 issue 派出去，自己专注 review；
- **并行调研、审计、批量分析**：方案三（subagent/workflow），读多写少是它的主场；
- **一个迭代要并行推多个功能、还要质量保障**：方案四（Agent 团队），并给每个任务配独立分支或 worktree；
- **上限形态是组合**：方案四的编排 × 方案一的隔离 × 方案二的异步执行，人用 review 而不是用编码参与整个流水线。
