> 一句话:**这是一个"验收端"平台**——把"AI 做测试"拆成七个阶段、阶段之间只传结构化契约,用 golden 评测集度量每个 AI 环节的好坏,再让平台从失败里自我进化。

这个文件夹把散在 `ai/` 里的相关讨论收拢到一处,并按三种用途分区:

- **正文**(本页 + 六篇专题):沉淀已经想清楚的结论,可以直接拿去讲方案;
- **`qa/`**:以后每问一个新问题,按模板记一条,写清"外部模型怎么答、内部模型怎么答、差异在哪";
- **`reviews/`**:哪些结实、哪些还没有一手证据、外部模型校对过没有。

## 二、平台定位:做验收端,不做供给端

"多智能体"这个前缀容易让人误以为要再造一个 Agent 构建平台。定位上必须切干净:

| | 供给端(openJiuwen / Dify / Coze) | 本平台(验收端) |
|---|---|---|
| 核心问题 | 怎么**构建和运行** Agent | 怎么**度量** Agent 的能力边界、发现回归 |
| 多 Agent | 分工干活的编排能力 | 构造多 Agent 协作的测试场景并评分 |
| 自进化的对象 | Skill / 工作流(越用越强) | 测试资产(失败聚类、用例、评测集) |
| 评测 | 附属能力,通常只有跑分 | 主战场:契约合规、diff、拦截率、成本 |
| 用户体系 | 多租户资源隔离(运维视角) | 多用户评分与偏好分桶(质量视角) |

为什么值得单独做,而不是"直接用通用 Agent 平台 + 让它顺手测一下":见[为什么需要专门的测试系统](./why-agent-testing.md)的六条理由——测试的目标函数是"对另一个系统建立信心",它要 **oracle 构造、环境生命周期、可重复性**这三样通用平台天生缺乏的东西;再加上**领域资产飞轮、信任链、同模型下的成本/准确率**。结论不是二选一:底座通用,领域层必须专用。

## 三、架构一页纸

### 3.1 七个阶段,阶段间只传契约

```
需求文档/OpenAPI ─> [1 需求理解] ─> [2 用例生成] ─> [3 用例评审] ─> [4 脚本生成]
                                                                      │
       [7 报告生成] <─ [6 失败分诊] <─ [5 用例执行(非 AI)] <──────────┘
```

| 阶段 | 输入 → 输出 | AI 的边界 |
|---|---|---|
| 1 需求理解 | 需求/OpenAPI → 需求点清单(带出处与澄清项) | 只读材料,不许脑补缺失需求 |
| 2 用例生成 | 需求点 → 编号化用例 JSON(优先级、预期结果带出处) | 预期结果必须有文档依据 |
| 3 用例评审 | 用例 → 分级评审意见(阻断/建议) | 换模型评审,禁止自评 |
| 4 脚本生成 | 用例 → 可执行脚本 | 编译/静态检查兜底 |
| 5 执行 | 脚本 → 原始结果 | **AI 不参与**,传统测试框架 |
| 6 失败分诊 | 失败日志 → 分类 + 嫌疑(环境/用例/产品) | 只给嫌疑,不下判决 |
| 7 报告 | 全部结构化产物 → 报告 | 事实取自上游,不许新增结论 |

关键纪律:**阶段之间不传对话历史,只传 schema 化的契约**。契约稳,内部实现(单次调用 / 框架 / 自研循环)随便换;判对错的权力(oracle)永远不外包给 AI。

### 3.2 三种拓扑就够,不要发明第四种

| 拓扑 | 解决什么 | 用在 |
|---|---|---|
| 流水线 / DAG | 流程**事先已知**,要可缓存、可审计 | 七阶段主骨架 |
| 编排者-工作者 | 任务需要**现场拆解**,子任务数量不定 | 需求拆解、分诊归因 |
| 生成-评审对抗 | 需要**质量闭环**、要隔离自评 | 用例生成 vs 用例评审 |

### 3.3 六个横向关切(按规模逐档升级,别跳档)

记忆 · 知识与 RAG · 数据冗余与高可用 · 高性能扩展 · 模型自由切换(运维面) · MCP 工具部署形态。每一项在[架构篇](./architecture.md)第七节都有"够用 → 标准 → 重型"三档。

## 四、模型可替换:三档方案不是三选一

| 维度 | 方案一 配置级 | 方案二 接口级 | 方案三 平台级 |
|---|---|---|---|
| 能换什么 | 模型 | 模型 + 某角色的架构范式 | 模型 + 架构 + 消费方外壳 |
| 切换成本 | 天 | 周(单角色) | 消费方随便换,中台不动 |
| 前置投入 | 一周 | 1~2 月(含契约设计) | 季度级 |
| 主要风险 | 架构被冻结 | 抽象设计失误、过早优化 | 过度设计、中台无人运营 |
| 适用时机 | **现在就做** | 跑稳半年后 | 消费方 ≥3 或治理成痛点 |

要点:这是演进不是三选一——先做方案一,同时按方案二的接口边界写代码,方案三等消费方数量逼出来再上。

对接多模型的三层抽象,顺序不能反:

1. **传输层**:OpenAI 兼容 API(只统一格式,不统一能力);
2. **差异层**:**能力声明 + 适配器**(context 长度、tool calling、JSON 稳定性差异巨大,按能力选模型,不按模型名写死);
3. **架构层**:角色能力接口(换架构也是换配置)。

配置键永远用**角色名**(`case_reviewer`),模型名只是值。

## 五、怎么度量:golden 集、多用户评分、自进化

### 5.1 golden 评测集是共同底座

每个 AI 阶段维护一份 golden 集(脱敏真实输入 + 人工定稿输出),换模型/换架构/调 prompt 先离线回归:

| 指标 | 怎么算 | 决策价值 |
|---|---|---|
| 契约合规率 | 输出能否过 schema 校验 | 低于阈值直接拒绝该模型 |
| 与基线 diff 率 | 字段级 diff | diff 大到人看不完=有风险,抽审 |
| 评审拦截率 | 评审方阻断意见数 | 翻倍即生成质量退化 |
| 成本 / 延迟 | token 与耗时 | 同质量选便宜的 |

这是测试平台做 AI 架构的独有优势:**用测试的方法治理 AI 本身**,并且人工定稿的产出可以持续回流进 golden 集,飞轮越转越准。

### 5.2 多用户评分要把"客观"和"主观"分开

- 信号三来源:显式评分、隐式行为(采纳/改写/丢弃)、下游结果(用例被人工拦截、分诊结论被推翻);
- 聚合:客观正确性可跨用户共享;主观偏好必须按用户/团队分桶;
- 冷启动:先用规则 + 少量种子用户,别指望一上来就有可信的偏好画像。

### 5.3 自进化:AI 提案、评测裁判、人盖章

进化对象四层,成本从低到高:记忆 → 工具/技能 → 工作流与 prompt → 模型权重。方向靠一个闭环找:

```
失败聚类 → 影响面量化(频率 × 平均损失 × 受影响用户) → 定位进化层级(先修便宜层)
        → A/B 或影子流量验证 → 分数不回归才全量
```

自进化系统最常见的死因:错误经验污染记忆库导致自我强化式退化。所以条目要带版本与来源、支持回滚、先灰度。

详见[自进化与多用户评分](./self-evolution.md)。

## 六、哪些东西永远不改

判断标准只有一条:**换它的代价是不是线性的**。

| 不变(迁移成本非线性) | 可变(切换成本线性) |
|---|---|
| 七阶段契约 schema | 模型(网关路由) |
| golden 评测集与门禁流程 | prompt 模板 |
| 知识事实源(git 文档库 + MR 治理) | 角色实现(单次调用 / 框架 / 自研) |
| 审计日志(会话轨迹,"模型可见即可重建") | RAG 引擎与索引(可重建) |
| 角色能力接口 | 前端与部署形态 |
| 权限模型(执行权不外放) | 插件的具体实现 |

这张表也是架构评审的 checklist:任何提案先问"动没动左列"。

## 七、外部方案与可复用点

- **openJiuwen(华为)**:供给端,和我们重叠很小。建议"复用独立组件为主(`agent-protocol` / Swarm Skills 规范 / `agent-memory`)、把它做的 Agent 当作被测对象为辅";平台级底座(方案 C)不建议。风险:与 AgentArts 企业版同源,商用前要确认社区版边界。详见[openJiuwen 分析](./landscape-openjiuwen.md)。
- **Finding the Right Fit(arXiv 2610.00917)**:对 openJiuwen / OpenHands / DSH / PI 四个 harness × 5 个模型做了 66 组交叉评测,结论是**模型 × harness × 任务必须联合评测,排名会随配置反转**——这正是验收端该提供的产品能力,其开源轨迹(6,204 条)可直接当基线。
- **DeepSeek Harness(DSH)**:当作"方案二的活标本"评估过——它能被嵌进角色实现层,但框架 API 不能泄漏到契约层。

## 九、还没有定论的问题

这些是当前最值得拿去问外部模型、或者和内部模型比对的地方(详见 [reviews/pending.md](./reviews/pending.md)):

1. 方案三(平台级)的启动阈值"消费方 ≥3"是否成立,有没有更早/更晚的信号;
2. 多用户评分里客观正确性与主观偏好的分桶边界,聚合权重的定法;
3. Skill 千人千面的 router 阈值与冷启动策略;
4. golden 集规模、漂移与防污染的具体阈值;
5. openJiuwen 复用粒度(只借协议层,还是连记忆模块一起用);
6. 判官(judge)校准:同一份输出,不同模型评审的分歧如何量化与收敛。
