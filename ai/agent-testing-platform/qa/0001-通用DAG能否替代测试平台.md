# 0001 有通用 Agent 平台 + 自动生成 DAG,还需要专门的测试平台吗

## 一、问题

如果 Agent 平台已经能"自动生成 DAG 完成任务",那再做一个测试平台是不是重复投入?把测试当成一种普通任务交给通用平台不就行了?

**提问上下文**:团队 3~5 人,已有测试代码仓与执行机;内网只能跑内部模型;当前无成体系的 golden 集。

## 二、外部模型回答

| 项 | 内容 |
|---|---|
| 模型 | DeepSeek(deepseek-flash) |
| 日期 | 2026-10-25 |
| 是否联网 | 是(检索过 openJiuwen 与 harness 评测论文) |
| 结论 | **需要**,但成立条件是"四个理由里至少两个为真";纯靠"通用平台顺手测一下"会缺的是验收能力,不是执行能力 |

理由(按重要性):

1. **考核 ≠ 培训**:人需要考试、试用期、质检,因为能力不可直接观测;模型更甚——非确定性、版本漂移(provider 悄悄升级)、能力边界未知(永远自信)。没有 eval 的 agent 迭代是碰运气;
2. **通用 DAG 只能表达已知流程**:能穷举成 DAG 的任务本来就不需要"智能",传统工作流引擎早已解决;真实任务的关键步骤是"走到一半才知道下一步";
3. **测试骨架必须定死**:用例生成、评审、脚本、分诊这些阶段的骨架是领域知识,让 AI 每次现场生成 DAG 反而引入不确定性,且无法审计;
4. **领域资产飞轮**:用例库、flaky 名单、历史缺陷模式、常见误报这些结构化沉淀,通用平台没有承载位置,平台的自我进化也失去土壤;
5. **Oracle 与环境生命周期**:测试的目标不是产出工件,而是对另一个系统建立信心——判定对错的标准要领域知识,执行前要造数据、隔离、清理,执行后要可重放、可审计。通用平台没有这些内置能力。

失效条件:若平台不追求长期迭代(一次性项目)、或不做回归(每次人工全量验收),则通用 agent + 人工评审确实够用。
