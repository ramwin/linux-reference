# 平台 DAG 流: 固定还是自定义? 分层设计与四道闸

```{contents}
```

设计多智能体测试平台时, 编排层有一个绕不开的决策:

> **DAG 流应该平台定死, 还是允许用户自定义?**

定死怕不灵活——不同团队、不同被测系统的流程真的一样吗? 放开又怕失控——人人都能改流程, 质量、成本、审计怎么管? 本文给出答案:**这不是二选一, 而是一个分层问题。主骨架固定、节点内部自由、自定义按粒度分级准入。** 然后讲清每一层怎么设计、靠什么把控。

## 结论先放在前面

1. **主骨架必须固定**。测试是流程可枚举程度极高的领域——需求理解 → 用例生成 → 评审 → 脚本 → 执行 → 分诊 → 报告, 这个骨架几十年没变过(论证见[为什么不直接做通用智能体平台](./why-agent-testing.md)第六节)。固定的骨架是**领域资产**, 不是灵活性损失;
2. **灵活性给在节点内部和节点之间, 不给在骨架上**。用户能感受到的"自定义"90% 是换实现、调参数、跳过节点、加分支——这些都不需要动骨架;
3. **自定义按粒度分四级准入**: 配置参数(人人可改) < 换角色实现(过评测) < 子流程模板(评审合入) < 新节点类型(架构评审)。级别越高, 闸门越重;
4. **把控靠四道闸**: 契约 schema 校验、golden 评测门禁、权限 scope、版本锁定 + 灰度。四道闸都在, 自定义才敢放开; 缺任何一道, 放开就是裸奔。

## 一、先厘清: "自定义 DAG" 到底想自定义什么

用户说"我想自定义流程", 真实诉求通常落在四个完全不同的粒度上, 它们的风险天差地别:

| 级别 | 用户想干的事 | 例子 | 动的是什么 |
|------|------------|------|-----------|
| L0 参数配置 | 调行为, 不动结构 | 换模型、调 prompt 模板、设超时/重试、开关缓存 | 节点配置 |
| L1 实现替换 | 同一节点换个做法 | 用例生成从"单次调用"换成"agent 循环"; 换厂商模型 | 节点内部实现 |
| L2 流程裁剪/模板 | 节点增删、分支、复用一段子流程 | 小需求跳过评审; 加"安全扫描"分支; 保存"支付模块流程"为模板 | 骨架的实例化参数 |
| L3 结构扩展 | 定义新节点类型, 改骨架本身 | 在七阶段里插入第八个阶段 | 骨架 |

把"固定还是自定义"翻译成这张表后, 答案就清楚了: **L0-L2 应该尽量放开, L3 必须收死。** 大部分平台之争, 源于把四个粒度混在一起谈——拿 L2 的灵活性诉求去论证 L3 也该放开, 或者拿 L3 的风险去把 L0 也锁死。

## 二、分层设计: 骨架固定, 三层自定义

```
┌─────────────────────────────────────────────────────┐
│ 固定层: 七阶段主骨架 + 阶段间契约 schema               │  平台定死, 改它 = 架构评审
│   需求理解 → 用例生成 → 评审 → 脚本 → 执行 → 分诊 → 报告 │
├─────────────────────────────────────────────────────┤
│ 模板层: 骨架的命名实例                                 │  团队自定义, MR 评审合入
│   "支付回归流" = 骨架 - 评审 + 安全扫描分支 + 指定模型    │
├─────────────────────────────────────────────────────┤
│ 实例层: 一次运行的参数                                  │  用户自定义, 配置即改
│   本次跑哪个模板 + 换什么模型 + 什么超时/重试            │
├─────────────────────────────────────────────────────┤
│ 节点内部: 角色能力接口的任意实现                        │  开发者自定义, 过 golden 评测
│   单次调用 / ReAct 循环 / 多 agent 辩论 / dsh          │
└─────────────────────────────────────────────────────┘
```

### 固定层: 为什么骨架定死是资产而不是枷锁

[why-agent-testing](./why-agent-testing.md) 已经论证过: "每次让 AI 现场生成 DAG"在测试场景是负资产——多花 token、每次流程不一样(无法审计、无法对比历史)、重复犯已犯过的错。骨架固定的收益是系统级的:

- **可比性**: 所有团队跑同一骨架, 质量指标(拦截率、契约合规率、成本)才能横向对比、纵向追踪;
- **契约稳定**: 阶段间契约 schema 是全平台的第一不变量(见[架构](./architecture.md)十二节), 骨架一动契约就要动, 契约一动所有实现跟着迁移——这是非线性代价;
- **审计与证据链**: 测试报告是给发布决策会看的, "你们平台每次流程都不一样"直接摧毁信任链。

骨架固定不等于永远不变, 而是**变更走最重的流程**: 架构评审 + 契约版本化 + 全量 golden 回归。一年改一两次是正常的, 一周改一次说明分层错了——有些 L3 诉求其实该在 L2 解决。

### 模板层: 自定义的主战场

模板 = **骨架的一份命名配置**: 跳过哪些节点、各节点用哪个实现、超时重试策略、什么条件下走什么分支。它满足"不同团队流程不一样"的真实诉求, 同时不碰骨架:

```yaml
# 模板: 支付模块回归流 (L2 级自定义)
name: payment-regression
base: default-v3              # 基于哪个骨架版本
skip: [用例评审]               # 小迭代跳过评审(风险由模板评审时评估)
overrides:
  用例生成: {impl: agentic, model: kimi-k2, timeout: 900}
  失败分诊: {impl: prompt,  model: deepseek-v4-flash}
branches:
  - when: "变更涉及支付网关"
    insert_after: 脚本生成
    run: 安全扫描子流程        # 引用另一个模板作子流程
```

要点:

- **模板是数据, 不是代码**——存 git, 走 MR 评审, 有版本号。评审一份模板比评审一段编排代码快得多, 因为骨架和契约已经兜底;
- **跳过节点也要显式**。`skip` 写在模板里、评审时确认, 而不是运行时任人点掉——"跳过了评审"这件事本身必须可审计;
- **分支只能引用已注册的子流程/节点类型**, 不能现场发明新拓扑。这把 L2 的自由度限制在"组合已有积木", 杜绝了无限发散。

### 实例层: 运行参数

每次运行 = 模板 + 参数覆盖(换模型、调超时)。这一层完全放开, Web 界面随手改——因为它不改任何结构, 最坏结果是一次运行失败, 而 DAG 执行器的节点缓存和重试(见 [DAG 那篇](../dag.md))让失败的代价极小。

### 节点内部: 实现自由

节点对外是"输入契约 → 输出契约"的黑盒, 内部是单次调用还是多 agent 辩论, 平台不管。这是[架构](./architecture.md)三节"角色能力接口"的自然推论: **实现的自由度是无限的, 唯一门票是 golden 评测集**。

## 三、把控: 四道闸

放开的每一级自定义, 都由对应的闸门兜底。四道闸缺一道, 对应的级别就该收紧:

| 闸门 | 管什么 | 管住哪级 |
|------|--------|---------|
| **契约 schema 校验** | 节点产出必须过 schema, 畸形即失败重试/熔断 | L1/L3: 实现随便换, 产出形状不能变 |
| **golden 评测门禁** | 新实现/新模板先离线跑 golden 集, 达标才能合入 | L1/L2/L3: 质量不退步才可上线 |
| **权限 scope** | 模板/插件声明需要的权限(读哪些仓、能否触发执行), 超 scope 调用被拒 | L2/L3: 自定义不能偷偷扩权 |
| **版本锁定 + 灰度** | 编排配置锁定模板/实现版本; 新版本先小流量, 指标回退一键切回 | 全部: 任何变更可回滚 |

三道落地纪律:

1. **所有自定义都进 git, 走 MR**。模板、实现、参数预置——"谁改了流程"必须能像代码一样 blame。页面上随手改的运行参数是 L0 实例层, 不落库为模板就不影响别人;
2. **评测集是自定义的唯一通用门票**。不管是换实现(L1)、新模板(L2)还是新节点类型(L3), 准入动作是同一个: 跑 golden 集。这把"能不能自定义"从权限问题变成了质量数据问题, 治理成本低一个数量级;
3. **骨架版本化, 模板声明 base**。骨架演化时老模板继续指向老版本, 迁移是显式动作, 不会出现"骨架升了一版, 全平台模板悄悄全挂"。

## 四、决策速查: 一个自定义诉求来了, 放哪级

| 诉求 | 该放哪级 | 理由 |
|------|---------|------|
| "换个更便宜的模型跑分诊" | L0 实例参数 | 不改结构, 跑一次看效果即可 |
| "用例生成太糙, 想上 agent 循环" | L1 实现替换 | 契约不变, golden 集 A/B 说话 |
| "我们团队流程里没有评审这步" | L2 模板 `skip` | 显式化 + 评审时确认风险, 不许运行时偷跳 |
| "想在脚本生成后加一个安全扫描" | L2 模板分支(复用已有节点类型) | 组合已有积木 |
| "安全扫描是平台没有的全新阶段" | L3 编排插件 | 新契约影响全局, 架构评审 |
| "每次测试让 AI 现场规划流程" | 不放 | 测试场景这是负资产(见 why-agent-testing 六.2); 开放探索任务本来就该走 Agent 循环, 不走 DAG |

## 五、常见坑

| 坑 | 现象 | 处理 |
|----|------|------|
| 一步到位做"可视化自由编排画布" | 用户拖出千奇百怪的图, 质量无法对比, 出问题无法定位 | 先固定骨架 + 模板, 画布只用于**查看**运行状态; L3 诉求用编排插件走评审 |
| 模板做成代码而不是数据 | 改模板要发版, 团队自己写 if-else 编排, 骨架形同虚设 | 模板 = YAML/JSON + git MR, 平台只提供 schema 校验 |
| 允许运行时临时跳节点 | 审计时说不清"这次到底跑没跑评审" | 跳过必须写在模板里, 运行记录引用模板版本 |
| 自定义实现绕过评测 | 插件/新实现质量悄悄退化 | 不过 golden 集不能合入, 没有例外通道 |
| 骨架永不演化 | 真实 L3 诉求被压成畸形的 L2 hack(把新阶段伪装成旧节点的内部实现) | 定期评审模板库: 多个模板都在 hack 同一个点, 就是骨架该加阶段的信号 |
| 把开放探索任务硬塞进 DAG | 流程走不通反复改图, 又回头怪"固定骨架不灵活" | 那不是 L3 诉求, 是任务类型错了——探索任务走 Agent 循环(见 [DAG 边界](../dag.md)) |
