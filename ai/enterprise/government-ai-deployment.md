假设前提：一个 100 人左右的政府部门（委办局/区县部门），想给全体职工配一套"能写材料、能查政策、能改稿、能审合同"的 AI 助手，模型锁定 **DeepSeek-V4.1-Flash（`deepseek-flash`，V4.1-Flash-1017）**。本文回答五个问题：怎么安全地用、部署它要多少钱、token 产出速度如何、开工前要准备什么、团队要懂什么。

一句话预告结论：**在这个规模上，"模型"是最便宜也最不关键的环节；真正决定成败的是网关、数据分级、评测集和人工复核流程。而"部署"这个词对 100 人来说，大概率不该理解成"买卡装机"。**

## 结论先放在前面

1. **别自建。** 100 人部门自建一台 8 卡推理节点，3 年总投入 500～800 万元、年化 150～270 万元；同等用量走已备案 API 一年只要 0.2～8 万元。差 20～200 倍。自建只在"数据一个字都不能出内网"这类硬约束下才成立，那时它是**合规支出**，不是省钱手段。
2. **推荐路线：政务外网 + 已备案模型 API + 自建统一网关。** 网关是这套东西的"总闸"，承担鉴权、配额、脱敏、审计、内容安全、成本归因。没有网关就直接把 API Key 发给 100 个人，等于没做安全。
3. **政策上也倾向这个方向。** 《政务领域人工智能大模型部署应用指引》（中国网信网，2026-10-29）明确"县级及以下原则上应复用上级的智能算力和模型资源，不再独立进行政务大模型建设和部署"，并鼓励"企业建设运营、政府购买服务、按使用情况结算"。
4. **token 速度不是瓶颈。** 8×H200 单机实测：单流 230～390 tok/s、16 并发时每请求 189 tok/s、96 个并发 Agent 会话能跑到每分钟 287 轮。100 人办公峰值需求约 600～1200 tok/s，一台机器过配 5～10 倍，日常利用率大概率低于 5%。API 侧并发上限 2500，也够用。
5. **成本的大头在平台和人力，不在 token。** 100 人中度使用，月 token 费约 800 元；而同期的网关、知识库、审计、培训、1～2 个人力，一年要几十万到上百万。预算表要按这个结构编。

## 一、先确认你们的层级：它决定"能不能自建"

这不是技术问题，是行政层级问题。《政务领域人工智能大模型部署应用指引》把部署权限写得很直接：

| 层级 | 指引口径 | 对 100 人部门的含义 |
|---|---|---|
| 中央和国家机关部门、省级 | 可统一部署智能算力、大模型，向下属单位提供**电子政务外网环境**下的模型服务 | 你们是"提供方"，需要按千人/万人规模规划 |
| 地市 | 在省级统一要求下开展部署应用 | 可以自建小规模节点，但要并入省级统筹 |
| **县级及以下** | **原则上复用上级的智能算力和模型资源，不再独立建设部署** | 你们是"使用方"，**不该自建**，走上级平台或采购服务 |

所以动手前第一件事：**问清楚自己的算力归口在哪一级**。如果归口在省/市，你的"部署"工作其实是三件事——接平台、建网关、建知识库，而不是买服务器。这一条能省掉后面 80% 的预算争论。

指引还有两句要贴在墙上：

- "严格落实'涉密不上网、上网不涉密'……防止国家秘密、工作秘密和敏感信息等输入非涉密人工智能大模型"；
- 通用场景"需采用市场上成熟，并**已完成网信部门备案**的模型产品和服务"。

## 二、三档方案对比

```text
                                     ┌──────────────────────────┐
  A 档（推荐起步）                     │ 政务外网办公终端 / 内网门户 │
                                     └────────────┬─────────────┘
                                                  │ HTTPS + SSO
                                     ┌────────────▼─────────────┐
                                     │  统一 AI 网关（自建）      │
                                     │  鉴权·配额·脱敏·审计·风控  │
                                     └───────┬──────────┬───────┘
                                             │          │
                              B 档（中期）    │          │   A 档
                        ┌────────────────────▼──┐   ┌───▼──────────────────┐
                        │ 政务云 / 省统一平台 MaaS │   │ 已备案模型 API（公网）  │
                        │ 专属实例、私网接入       │   │ deepseek-flash 等     │
                        └───────────────────────┘   └──────────────────────┘

  C 档（仅硬隔离场景）：自建 8×H200 或 8×昇腾910C 单节点 + 存储 + 运维团队
```

| 维度 | A 档：公网已备案 API | B 档：政务云/省平台 MaaS | C 档：本地自建单节点 |
|---|---|---|---|
| 形态 | 调 `api.deepseek.com`，加网关 | 政务云专属实例或省级平台统建 | 8 卡整机 + 存储 + 推理框架 |
| 一次性投入 | 5～20 万（网关、知识库、前端） | 20～80 万（集成、迁移） | 150～300 万（含存储/网络/安全） |
| 年运行费 | token 0.2～8 万 + 平台维保 | 按实例/按量，20～80 万 | 150～270 万（含 1.5～2 人力、电、托管） |
| 首次上线周期 | 4～8 周 | 8～16 周 | 16～24 周（国产卡适配再加 4～8 周） |
| 数据出网 | **会出网**（仅限非敏感数据） | 不出政务云，但出本部门 | 完全不出机房 |
| 能力上限 | 跟随厂商，随时升级 | 中等，受平台版本约束 | 受硬件与运维水平约束，容易落后一代 |
| 故障恢复 | 厂商兜底，换供应商只改 base_url | 平台方兜底 | 自己兜底，宕机就是全部门停摆 |
| 合规工作量 | 中（备案核验、协议、数据清单） | 中高（需并入省级统筹） | 高（备案、等保、密评、安全评估全都要） |
| 主要风险 | 涉密/敏感数据误投喂 | 平台排期、能力滞后 | 利用率极低、人才留不住、模型版本停更 |

**明确建议：**

- **第 1 年走 A 档**，把网关、知识库、评测集、管理制度这四样建起来，用真实流量摸清用量曲线。这四样是任何档位都躲不掉的地基，先建它们不浪费。
- **第 2 年视情况升 B 档**：如果数据分级里"内部"级数据占比高、或省里统一平台已就绪，把模型侧迁到政务云，网关不动（因为网关只认 OpenAI 兼容的 `base_url`）。
- **C 档只在两种情况下考虑**：① 业务数据明确禁止出本部门机房；② 上级要求本地化且给了专项预算和机房。此时也建议"租赁整机 + 购买运维服务"，别自己养 GPU 团队。

## 三、先看清 V4.1-Flash 是什么：它决定自建门槛

很多人对"Flash"这个名字有误解，以为是小模型。这一代不是。

| 项目 | 数值 | 含义 |
|---|---|---|
| 主干参数 | 552B MoE，Causal-Encoder-Decoder 结构 | 不是 8B 小模型 |
| 激活参数 | 输入 8B / 输出 16B（非对称） | 每 token 计算量小，这是它便宜的原因 |
| 存储参数总量 | 763～769B | 主干之外还有 Engram 记忆表和视觉编码器 |
| 权重体积 | 510～511 GB | 原生 MXFP4（专家）+ MXFP8（密集），**不要二次量化** |
| Engram 记忆表 | 196.6B，约 189 GiB | 每 token 都要查表，必须常驻（可放主机内存） |
| 单机显存底线 | 567～614 GB | 8×H200（1128GB）或 1 托盘 GB200 NVL4（768GB） |
| 上下文 / 输出 | 1M / 最大 384K | 长上下文可用但**要限流**，见第五节 |
| 能力 | 原生图像理解、Tool Calls、JSON、1M 上下文、思考模式 | 多模态是原生能力，不是外挂 |
| 许可 | MIT | 开源给的是**许可**，不是硬件 |

几个直接影响决策的点：

1. **"单卡能否跑"的答案是"不能"。** 最低 4 卡起（配 567GB 以上显存），8×H100 的 640GB 只是刚过底线且未经验证，1M 上下文基本不现实。
2. **官方对"大规模自建"的定义是 2k 卡 + 存储集群。** V4.1-Flash 发布公告原话："如果您有大规模部署的需求且具备相应的资源（2k 卡 GPU、有存储集群），欢迎与我们联系。" 2000 张卡的投入是数亿元量级——这反过来说明，100 人部门不是这套模型的目标自建客户。
3. **开源生态还在补课。** vLLM 需要专用镜像（`vllm/vllm-openai:deepseekv41-flash-0909`，0.30.0+，架构 PR 未并入主线），SGLang 是预览镜像，llama.cpp 尚未支持。国产化路线（昇腾 910B/910C）要靠 W4A8 适配 + PD 分离，属于工程项目而非开箱即用。

四条部署路线，供 C 档评估时参考：

| 路线 | 状态（2026-11） | 适合谁 | 限制 |
|---|---|---|---|
| vLLM 专用镜像 | 预览镜像，需 0.30.0+ | 生产服务、要 OpenAI 兼容 API | 无 pip 包，参数随版本变 |
| SGLang 预览镜像 | cookbook 已合入，有低延迟/高吞吐两套预设 | 追求延迟或吞吐的调优团队 | 正式版未发布 |
| 官方参考实现 | torchrun 多卡，可读可验证 | 复现数值、审计 | 官方定性"参考而非生产引擎" |
| 昇腾 vLLM-Ascend | 社区适配（W4A8、PD 分离、DSpark） | 有信创要求的单位 | 调优成本高，需专门人力 |
| llama.cpp / Ollama | 尚不支持 V4.1 架构 | — | 暂时不可用 |

## 四、成本测算（100 人）

### 4.1 先把"用量"变成数字

所有成本测算的分母都是 token。用三档用量模型，具体数值可以按你们实际调：

| 场景档 | 轮次/人/日 | 输入 tokens/轮 | 输出 tokens/轮 | 日输入/人 | 日输出/人 |
|---|---|---|---|---|---|
| 轻：问答、翻译、润色 | 10 | 3,000 | 400 | 30k | 4k |
| 中：写材料 + 政策检索 + 改稿 | 30 | 8,000 | 700 | 240k | 21k |
| 重：长文档处理、Agent 办公流 | 60 | 30,000 | 1,500 | 1.8M | 90k |

换算参考：1 个中文字符 ≈ 0.6 token，1 个英文字符 ≈ 0.3 token；一页 A4（约 500 字）≈ 300 token，一份 100 页的 PDF ≈ 3 万 token，一部 10 万字的政策汇编 ≈ 6 万 token。所以"长文档"并不贵，贵的是反复重发、以及思考模式产生的推理 token。

100 人 × 每月 21.75 个工作日：

| 场景档 | 月输入 tokens | 月输出 tokens |
|---|---|---|
| 轻 | 6,525 万 | 870 万 |
| 中 | 5.22 亿 | 4,570 万 |
| 重 | 39.15 亿 | 1.96 亿 |

### 4.2 官方价格（2026-11，元/百万 tokens）

| 计费项 | 闲时 | 高峰 |
|---|---|---|
| 输入·缓存命中 | 0.02 | 0.04 |
| 输入·缓存未命中 | 1 | 2 |
| 输出 | 4 | 8 |
| Search / Fetch（独立 API） | 5 元 / 千次 | 同 |

高峰时段 = 工作日 9:00–12:00、14:00–18:00（不含法定节假日），其余时间及周末节假日全部半价。政府办公大部分落在高峰，所以下面按**高峰价**算，属于保守口径。

### 4.3 API 路线月/年成本

假设缓存命中率 60%（系统提示 + 知识库片段重复度高，稳定运行后通常能到 70%～80%），有效输入单价 = 0.6×0.04 + 0.4×2 = **0.824 元/百万**：

| 场景档 | 月输入费 | 月输出费 | 月合计 | 年合计（含 30% 余量） |
|---|---|---|---|---|
| 轻 | 54 元 | 70 元 | 124 元 | 约 0.2 万元 |
| 中 | 430 元 | 366 元 | 796 元 | 约 1.2 万元 |
| 重 | 3,226 元 | 1,566 元 | 4,792 元 | 约 7.5 万元 |

再加两项容易漏的：

- **联网检索**：每人每天 10 次 Search，100 人一个月 2.2 万次 ≈ 109 元/月；
- **多模型交叉校验**：对外服务场景（政策问答、智能导办）建议两个模型互校，token 成本 ×2～3。

即使三项全加上（重用量 + 交叉校验 + 检索），100 人一年也就 **15～22 万元**。这是本文最重要的一个数量级感：**100 人规模的模型费，比一个正式编制的年度人力成本还低。**

一个可以直接改参数的脚本：

```python
#!/usr/bin/env python3
"""100 人部门 DeepSeek-V4.1-Flash 月度成本估算，改参数即可复算。"""

people = 100
workdays = 21.75
rounds_per_day = 30          # 每人每天轮次
in_per_round = 8_000         # 每轮输入 tokens（含 RAG 片段）
out_per_round = 700          # 每轮输出 tokens
cache_hit = 0.60             # 缓存命中率

SUM_PRICE, MISS_PRICE, OUT_PRICE = 0.04, 2.0, 8.0   # 高峰价，单位：元/百万 tokens

in_tokens = people * workdays * rounds_per_day * in_per_round / 1e6
out_tokens = people * workdays * rounds_per_day * out_per_round / 1e6
cost_in = in_tokens * (cache_hit * SUM_PRICE + (1 - cache_hit) * MISS_PRICE)
cost_out = out_tokens * OUT_PRICE

print(f"月输入 {in_tokens:.1f}M / 月输出 {out_tokens:.1f}M")
print(f"输入 {cost_in:.0f} 元 + 输出 {cost_out:.0f} 元 = {cost_in + cost_out:.0f} 元/月")
print(f"年化 {(cost_in + cost_out) * 12 * 1.3:.0f} 元（含 30% 余量）")
```

### 4.4 自建路线成本

以一台能跑的**单节点**为单位（8×H200，或国产化的 8×昇腾 910C）。硬件报价口径差异极大，取公开区间：

| 项目 | 一次性（万元） | 年运行（万元） |
|---|---|---|
| 8 卡整机（910C 128G×8 / H200 141G×8） | 120～300 | — |
| 存储（权重 511GB + 日志 + 知识库，≥20TB NVMe） | 20～40 | — |
| 网络与安全设备（交换机/防火墙/堡垒机/日志审计） | 10～20 | — |
| 模型服务化平台（网关/RAG/审计/前端/监控） | 30～80 | 维保 10%～20% |
| 机柜与电（8 卡满载约 6kW，PUE 1.5） | — | 5～7 |
| 运维人力（1.5～2 人：MLOps + 安全） | — | 40～80 |
| 等保测评 + 密评 + 安全评估 | 10～20 | 3 年一评 |
| 昇腾适配/调优（W4A8、PD 分离、框架补丁） | 20～50 或 3～6 人月 | — |

**3 年 TCO 合计约 500～800 万元，年化 150～270 万元。** 如果改为"租赁整机 + 买运维"，硬件部分可降到 71 万元/年（运营商 2026-10 对 8×910C 整机的公开租赁报价为 5.95 万元/月），但平台、人力、测评三项省不掉，年化仍在 150 万元以上。

### 4.5 盈亏平衡点：每天 30～40 亿 tokens

按年化 200 万元、混合单价约 1.48 元/百万 tokens（输入输出 10:1、缓存命中 60%）反推：

```
200 万元 ÷ 1.48 元/百万 ≈ 1.35 万亿 tokens/年 ≈ 37 亿 tokens/天
```

而 100 人按**最重**用法也只有 1.9 亿 tokens/工作日，相差约 20 倍；按中度用法相差约 140 倍。

所以"自建省钱"在 100 人这个量级上是不成立的。自建的价值只有两个：**数据不出机房的合规要求**，和**离线/内网可用**。这两条如果成立，就按合规预算去立项，别拿"省 token 费"当理由——评审时对不上账。

顺带说清一件事：自建机器闲置不是"浪费一点"，而是"每天烧 5000 元"。一台年化 180 万的机器，一个工作日折旧加电费约 7000 元；它跑不跑都一样。

## 五、token 产生速度：够不够快

"快"要拆成三个指标看，混在一起谈就会吵架：

| 指标 | 定义 | 用户感受 | 目标值 |
|---|---|---|---|
| TTFT | 首 token 延迟 | 点了发送后多久开始"打字" | P95 < 3 秒 |
| TPOT / 单流速度 | 每个 token 的间隔，倒数即 tok/s | 打字机滚动的快慢 | ≥ 20 tok/s（阅读速度约 10～15 tok/s） |
| 聚合吞吐 | 全系统每秒输出 token 数 | 高峰期会不会排队 | 峰值需求 × 2 |

### 5.1 自建实测（8×H200，SGLang，两个 4 卡副本）

| 场景 | 数值 |
|---|---|
| 单请求输出 | 262K 上下文副本 354 tok/s；1M 上下文副本 312 tok/s；完成 BF16 密集层优化后单请求可达 392 tok/s |
| 16 并发时单请求 | 189 tok/s（262K 副本）/ 75 tok/s（1M 副本） |
| Agent 会话轮次 | 16 人 131～140 轮/分；32 人 217；64 人 276；96 人 287 |
| 单轮中位耗时 | 2.14 秒（16 人并发） |
| KV Cache 容量 | 每副本 490 万 tokens，峰值只用了 22% |

几个从实测里读出来的判断：

- **16 并发是"甜点"。** 单请求 189 tok/s 远高于人的阅读速度，再往上加并发，单请求速度掉得不多但边际收益递减；96 并发时单请求速度仍在可用区间，说明这台机器的真实上限远高于 100 人部门的需求。
- **1M 上下文要单独开副本。** 长上下文副本单请求慢 12%、16 并发时慢 60%，且要占用更多显存。正确做法是短提示词走快副本、超长提示词路由到长副本。
- **DSpark 投机解码约 3 倍加速**，是自建必开的开关（`--speculative-config`）。

### 5.2 API 侧

- 官方并发上限：`deepseek-flash` **2500**（每账号，与 API Key 数量无关；可提工单扩容且不额外收费）。
- 官方不公布 TPM 与单流速度。按 2500 并发 × 单流 30 tok/s 粗算，聚合吞吐在 **7.5 万 tok/s** 量级——但这是推算，不是承诺值。
- 真正要盯的是 **HTTP 429**：超并发会直接 429，不会排队。网关必须做队列 + 重试 + 退避。

### 5.3 100 人到底需要多少

按"20% 的人同时在线、每人每 90 秒发一次、每次输出 700 token"估峰值：

```
并发 ≈ 20 人 × (700 token ÷ 90 秒 ÷ 30 tok/s) ≈ 5～8 路
聚合需求 ≈ 5～8 × 30 tok/s ≈ 150～250 tok/s
```

就算放大 5 倍留余量，也只有 **600～1200 tok/s**。对照上表：一台 8×H200 在 96 并发下仍有余量，**过配 5～10 倍，日常利用率低于 5%**。

### 5.4 三个提速小改动（比加机器便宜得多）

1. **稳定提示词前缀顺序**。把系统提示、工具定义、知识库固定片段放最前面，且不要在开头插入时间戳/用户名/随机 ID——一插就把整个前缀缓存打掉，输入费用立刻从 0.04 元/百万 变回 2 元/百万，差 50 倍。
2. **按场景关掉思考模式或降 `reasoning_effort`**。该模型默认开启思考、强度 50（别名 low=25 / high=50 / xhigh=75 / max=100）。办公写作、翻译、格式转换这类任务用 low 或直接关掉，输出 token 能降 2～5 倍，延迟同步下降。
3. **流式输出 + 前置骨架**。用户感知的是 TTFT，不是总时长。先返回"正在检索政策库…"再出正文，体感差异比换硬件明显。

## 六、怎么"安全"使用：四层防线

安全不是一个功能，是四层同时成立。少任何一层，另外三层都会被绕过。

### 6.1 合规层

| 事项 | 依据/要求 | 交付物 |
|---|---|---|
| 模型备案核验 | 《生成式人工智能服务管理暂行办法》；指引要求用"已完成网信部门备案"的模型 | 供应商备案号 + 官网核验截图存档 |
| 算法备案 / 安全评估 | 自建且面向公众提供服务时需履行 | 备案材料、安全评估报告 |
| 生成内容标识 | 《人工智能生成合成内容标识办法》（2025-09-01 施行） | 界面显式标识 + 文件元数据隐式标识 |
| 网络安全等级保护 | 政务系统通常按三级建设与测评（GB/T 22239-2019） | 定级备案、测评报告 |
| 密码应用安全性评估 | 涉及国密改造的系统（GB/T 39786） | 密评报告 |
| 服务协议 | 与使用者签订，明确双方权利义务（指引明确要求） | 服务协议 + 免责与风险提示 |
| 日志与审计 | 《网络安全法》要求网络日志留存不少于 6 个月 | 日志留存策略 + 季度审计记录 |
| 应急预案 | 指引要求"针对可能出现的安全风险，制定应急处置预案" | 停用/降级/召回三套预案 |

### 6.2 数据层

先做一张**三色清单**，贴在每个工位。这张表比任何技术手段都有效，因为它决定了"人会不会把不该给的给出去"。

| 等级 | 典型内容 | 能否输入 AI | 处理方式 |
|---|---|---|---|
| 红：禁止 | 国家秘密、工作秘密、侦查/案件信息、未公开人事与干部信息、个人敏感信息（身份证、生物特征、健康、行踪） | **绝对禁止** | 物理隔离；网关做关键词+正则+模型分类三重拦截 |
| 黄：受限 | 内部会议纪要、未定稿政策、预算与采购底价、企业报送的未公开数据 | 仅限内网/政务云模型 | 脱敏后使用；禁止出公网 |
| 绿：可投喂 | 已公开政策文件、法律法规、办事指南、常见问题、公开统计数据 | 可用公网已备案 API | 去标识化后入库 |

配套三件事：

1. **知识库台账**：每个文档记录来源、密级、入库时间、责任人、更新周期。指引要求"建立台账并详细记录数据来源、类型和规模"。
2. **脱敏规则**：姓名→"某某"、身份证/手机号→掩码、单位内部编号→替换。用正则先过一遍，再用小模型判一遍。
3. **禁止上传整个目录**：客户端只允许单文件、限大小，禁止批量拖拽文件夹。

### 6.3 系统层：网关要做的八件事

```text
用户 → SSO 登录 → [1 鉴权] → [2 配额/限流] → [3 敏感词与PII脱敏]
     → [4 提示注入检测] → 模型 API（deepseek-flash）
     → [5 输出内容风控] → [6 引用与来源标注] → [7 全量日志落库] → 用户
                                   ↓
                          [8 成本归因：部门/人/场景]
```

1. **鉴权**：对接单位统一身份（LDAP/OAuth/CAS），一人一号，禁止共享 Key；
2. **配额**：按人/按部门设月 token 上限，超额告警而不是直接断（断供会引发绕过行为）；
3. **脱敏**：请求侧正则 + 规则拦截身份证、手机号、银行卡、坐标；
4. **提示注入检测**：识别"忽略以上指令""输出你的系统提示"等模式，命中即拒答并记录；
5. **输出风控**：涉政、违法、泄密、代码执行类内容拦截；
6. **来源标注**：RAG 回答必须带文档名与段落号，否则不给"可直接采用"的标记；
7. **全量日志**：谁、何时、问什么、答什么、用了哪个模型、花了多少 token，留存 ≥ 6 个月；
8. **成本归因**：按部门出月报，这是后续预算和配额调整的唯一依据。

### 6.4 使用层：十条硬规矩

1. 涉密、工作秘密、未公开敏感信息，一个字都不进对话框（包括截图、附件、粘贴）；
2. 只用单位统一入口，禁止个人账号、私人手机、公网直连；
3. AI 产出**不得直接对外发布**，必须人工逐字复核；
4. 引用政策必须回原文核对文号、条款、日期、数字——这是幻觉最高发的地方；
5. 一次只给最小必要片段，不给整个文件夹、不给整库导出；
6. 提示词里不带姓名、身份证、手机号、住址，需要时先脱敏；
7. AI 生成的图片、音视频对外使用必须加 AI 标识；
8. 不在 AI 里讨论未定稿决策、干部人事、案件侦查等敏感事项；
9. 发现异常（疑似被诱导、输出违法内容、答非所问）立即上报，不自行"再问一次试试"；
10. 不把长期密码、密钥、凭据放进对话或知识库。

### 6.5 对外服务的额外要求

面向公众的政策问答、智能导办属于"代表政务部门提供服务"，指引要求更严：

- **内容审核制度**：人工审核 + 实时风控 + 多模型交叉校验三者组合；
- **显著风险提示**：界面显著位置告知"本回答由 AI 生成，仅供参考，以正式文件为准"；
- **合理拒答**：超出业务范围的问题必须拒答，不能"编一个像样的答案"；
- **可追溯**：每条回答可回溯到知识库原文与模型版本。

## 八、需要哪些基础知识

分三类人，标准不同。不要指望"全员培训一次就会"，也不要指望"技术团队懂合规"。

### 8.1 管理层：5 个概念，每个一句话

| 概念 | 一句话解释 | 为什么管理者必须懂 |
|---|---|---|
| token | 计费与容量单位，1 个中文字 ≈ 0.6 token | 预算、限流、并发都是按它算的 |
| 上下文窗口 | 一次能"看见"的 token 上限（本模型 1M） | 决定能处理多长的文件，也决定成本 |
| 幻觉 | 模型会自信地编造不存在的文号、条款、数据 | 决定"必须人工复核"是不可取消的 |
| RAG | 先从你们的文件里检索、再让模型照着答 | 政务场景的主力方案，决定知识库是核心资产 |
| 辅助型定位 | 模型是"辅助"，责任在人 | 决定流程设计、审核制度与追责方式 |

### 8.2 技术运维：8 项，附最小可用标准

| 能力 | 最小可用标准 |
|---|---|
| HTTP/API 与 OpenAI 兼容接口 | 能用 curl 跑通 chat/completions，看懂流式 SSE |
| 推理服务原理 | 能解释显存 = 权重 + KV Cache + 激活，会算 567GB 从哪来 |
| vLLM / SGLang | 能起一个服务、改并发、看 TTFT 与吞吐指标 |
| 量化与精度 | 知道 FP8/FP4、为什么官方权重不能二次量化 |
| RAG 工程 | 分块、embedding、召回、重排、引用标注，端到端能跑 |
| 评测 | 会写 200 条评测集，能跑准确率/拒答率/幻觉率 |
| 可观测性 | 监控 TTFT、429 率、token 用量、错误码分布 |
| 提示注入防护 | 知道 OWASP LLM Top 10，能写出 20 条攻击样例防住 |

### 8.3 安全合规：6 项

等保 2.0 三级要求、密码应用与密评、数据分类分级、生成式 AI 备案与内容标识、日志留存与审计、应急响应与事件报告。

### 8.4 培训怎么排

- **领导层 1 小时**：能力边界、责任定位、预算结构（重点讲"它不是搜索引擎，也不是决策者"）；
- **业务骨干 2 小时**：三个试点场景的正确用法 + 十条硬规矩 + 复核方法；
- **全员 45 分钟**：能做什么、不能做什么、出了事怎么办，配一张 A4 速查卡。

| 指标 | 目标值 | 采集方式 |
|---|---|---|
| 可用性 | ≥ 99.5%（工作时间） | 网关探针 |
| TTFT P95 | < 3 秒 | 网关埋点 |
| 单流速度 | ≥ 20 tok/s | 网关埋点 |
| 429 率 | < 0.5% | 网关统计 |
| 引用可溯率 | ≥ 95% | 抽样人工 |

## 十、十个常见坑

1. **按"人均 ChatGPT"估容量**，直接买 8 卡机，结果利用率 2%，第二年预算被砍。
2. **忽略思考模式默认开启**：`max_tokens` 给小了，预算全花在思考链上，返回空内容。
3. **把 1M 上下文当卖点**：长上下文副本慢 12%～60%，还要单独占显存。
4. **把自建当省钱**：账算不下来，见 4.5 节。
5. **提示词前缀不稳定**：开头插入时间戳/用户名，缓存全失效，输入费涨 50 倍。
6. **知识库不分级**：内部纪要进了公网 API，一个事故抵掉三年节省。
7. **只买模型不做网关**：没有审计、没有配额、没有成本归因，出事查不到人。
8. **不建评测集**：模型一升级，没人说得清是变好还是变差。
9. **供应商锁定**：坚持 OpenAI 兼容接口 + 双供应商，切换只改 `base_url` 和模型名。
10. **把 AI 当"减负"政绩**：指引明确反对"指尖上的形式主义"和强制使用，指标要定在"采纳率"而不是"登录率"。
