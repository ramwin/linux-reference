# 需求说不清就举例子：AI 需求描述的四个坑与五类例子


## 引子：一段真实的群聊

这篇文章的起点是一段真实的群聊，原话照抄：

> **小华**：AI 生成需求描述词有缺点吗，我开发小程序的时候不知道怎么描述，就把需求给 AI 了，他给我生成了一大段描述，我看都没看就丢给 workbuddy 了。
>
> **小飞**：描述不好的话，可以给 ai 举例子，ai 举一反三还是很强的。
>
> **小华**：需求描述咋举例子啊。
>
> **小王**：小华我给你一个例子，有 AI 的时代要左脚踩右脚螺旋飞天。

这段对话里有三个问题，一个比一个具体：

| 疑问 | 本文的回答 | 在哪一节 |
|---|---|---|
| AI 生成的需求描述有缺点吗 | 有，而且缺点不是"写得差"，是"写得太像真的" | 一 |
| 需求描述怎么举例子 | 举的不是说明性例子，是**可判定的验收实例**；一共五类 | 二、三 |
| "左脚踩右脚螺旋飞天"是什么 | 一个四步迭代环：生成 → 挑刺 → 反向质疑 → 再生成 | 四 |

先把第一个问题说透，因为它是后面所有方法的动机。

## 一、坑不在"差"，在"太像真的"

AI 起草的需求描述，问题不在于它写得比你烂——恰恰相反，它往往比你写得更像一份正经的需求文档：有编号、有优先级、有验收标准、有边界说明。**格式的完备会伪装成内容的完备。**

具体有四个高频坑：

| 坑 | 长什么样 | 谁来买单 |
|---|---|---|
| **幻觉功能** | 你没提过的"多人协作""数据看板""积分体系" | 工期 |
| **不可验收** | "界面简洁友好""响应流畅""智能推荐" | 验收时扯皮 |
| **丢约束** | 平台、技术栈、性能、权限、合规一个字没提 | 方案返工、小程序审核不过 |
| **语义漂移** | 你的口语被它"扩写"成它以为的意思 | 最难查，因为你以为自己说过了 |

### 1.1 "太像真的"为什么是问题

需求文档的外观（编号、优先级、验收标准）会给出一个强烈的信号：**这玩意儿是评审过的**。而你实际做的只是"让它生成一段"。

于是出现一个危险的错配：

> **需求描述的自信程度，和它的正确程度，没有任何相关性。**

一个形容词被翻译成三个带单位的数字，格式规范、语气笃定、结构完整——它看起来像某次需求评审的会议纪要，实际上是一次凭空补全。你越是不看，这份"补全"越是被当成事实往下传。这个机制在[先让 AI 写需求文档](../coding/requirements-delegation.md) 第三节里展开过，这里不重复。

### 1.2 第五个坑：责任链断了

这是小华那段话里最真实的一句——「我看都没看就丢给 workbuddy 了」。

它造成的不是"需求可能不准"，而是**三段链路里没有一段经过人**：

```text
你的口语  →  AI 扩写成需求  →  下游 Agent 实现  →  验收
   ↑               ↑                 ↑              ↑
  你            没人审           没人审          只能看结果
```

出了问题，三种归因同时失效：

- 是需求写错了？——你不会知道，因为你没读过那份需求；
- 是实现理解错了？——没法判断，因为需求没有可判定的例子；
- 是本来就没想清楚？——最可能，但也没法确认。

而下游 Agent 是**放大器**：一份"看着挺对"的需求里写了积分体系，它会顺手建四张表、写三个定时任务、加一个后台页面。上线前没有人问过"要不要积分"，但复杂度账单已经记在你头上了。

```{mermaid}
flowchart LR
    A["口语需求<br/>（只有你脑子里清楚）"] --> B["AI 扩写<br/>（幻觉 + 形容词）"]
    B --> C["下游 Agent 实现<br/>（照着不存在的需求做）"]
    C --> D["验收<br/>（只能说像不像）"]
    B -. "缺口一：你没读" .-> X["无法归因"]
    C -. "缺口二：没有可判定标准" .-> X
```

堵住这两个缺口，其实只需要一样东西：**例子**。

## 二、"举例子"举的到底是什么

小飞说"给 ai 举例子，ai 举一反三还是很强的"，这句话对，但要补一个前提：**你给的"一"必须是能判定的具体实例**，否则 AI 的"反三"会反到你没想去的地方。

### 2.1 一条判据：这个例子能不能被判成"通过/不通过"

先看假例子和真例子的区别：

| 假例子（举例说明） | 真例子（举例示范） |
|---|---|
| 界面要好看，像苹果那样 | 首页只有一个主按钮，点下去 300 ms 内变成"已打卡" |
| 打卡要快 | 弱网（3G）下点击到界面反馈不超过 1 s，允许先本地记账再同步 |
| 支持各种异常情况 | 同一分钟连点两次只算一次；跨零点不弹任何提示 |
| 数据要能导出 | 导出 CSV，字段顺序为日期、习惯名、状态；空数据导出只有表头 |

判据只有一句：**能不能被自动化脚本或一个较真的人判定成"通过/不通过"**。答不出来的，还是形容词。

这也是为什么「例子」在需求里的地位比在文档里高：它同时承担了两件事——**说明**和**验收**。写完的例子直接就是测试用例的原料，中间不需要再翻译一次。

### 2.2 为什么例子比形容词管用：三个机制

**第一，可判定性。** 形容词的判定权在说话人手里，"流畅"到底多流畅，验收时你说了算，于是开发永远做不对。例子的判定权在事实手里，300 ms 就是 300 ms。

**第二，收回解释权。** 同一个词在你和模型脑子里的先验完全不同。"大文件"你想的是 20 MB 的图片，它想的是 10 GB 的视频。一个具体例子能把歧义**钉死在一个点上**，而不是留在整段描述里到处冒头。

**第三，例子是压缩过的约束集。** 这是最关键的一点，也是小飞那句话真正成立的地方：

> 昨天没打卡、今天打卡 → 连续天数 = 1

这一个例子，隐含了至少四条规则：连续天数会重置；重置后从 1 开始而不是从 0；显示的单位是天；"昨天没打卡"这件事本身不报错、不提醒。AI 确实能从一个例子推出这四条——**举一反三就发生在这里**。

但反过来，正因为它会推，你必须控制它往哪儿推。**正向例子定方向，反向例子定边界。** 没有反向例子，它会顺着"连续打卡"推出排行榜、徽章、分享裂变——这就是 1.2 里那张复杂度账单的来源。

### 2.3 例子的三种失效方式

例子不是万能药，用错了同样会出事：

| 失效 | 表现 | 修法 |
|---|---|---|
| **例子太少** | 把唯一的例子当全部需求，硬编码"张三"、只支持一个习惯 | 至少给一条正常 + 两条异常 |
| **例子互相矛盾** | 两个例子推出相反规则，模型静默挑一个 | 冲突显性化，见[提需求防遗忘、防冲突](../coding/requirements-prompting.md) |
| **例子写成实现** | "用 Redis 存打卡记录""用云函数定时触发" | 只描述**可观察的结果**，不描述手段 |

第三条尤其容易犯：你想帮 AI 想清楚，于是把实现也写进例子，结果它照着你的实现做，需求里真正重要的边界反而没人管了。**例子描述"用户看到什么"，不描述"代码怎么跑"。**

## 三、五类例子（附小程序完整示范）

需求描述里的例子，按作用分五类。前两类是必给的，后三类是加速收敛的：

| 类型 | 治哪个坑 | 一句话写法 |
|---|---|---|
| **1. 正常流程** | 语义漂移 | 用户【做什么】→ 看到【什么】 |
| **2. 边界/异常** | 不可验收 | 在【某种刁钻情况】下 → 应该是【什么结果】 |
| **3. 参照物** | 语义漂移、幻觉功能 | 像【某产品的某功能】，但去掉【某部分】 |
| **4. 反向例子（非目标）** | 幻觉功能 | 这次**不做**【A、B、C】 |
| **5. 使用场景** | 丢约束 | 谁、在什么环境、受什么限制的情况下用 |

- **正常流程例子**定"做对是什么样"；
- **边界/异常例子**是 AI 最容易漏、也最能体现你专业度的地方（时间边界、空数据、断网、重复操作）；
- **参照物**是把 UI/交互需求压缩成一句话的最快方式——但它同时也是幻觉的高发区，因为 AI 对"像 XX"的理解可能来自过时或错的印象，参照物必须是你亲自确认过的；
- **反向例子**（非目标）的性价比最高：写"不做社交排行"这六个字，省掉的是一个功能模块；
- **使用场景**决定了性能、交互、合规这些约束，而这些是 AI 猜不出来的——它不知道你的用户在地铁上单手操作。

### 3.1 完整示范：习惯打卡小程序

一句话需求：「做一个习惯打卡小程序，用户每天打卡，能看到连续天数。」

按上面五类例子，把这句话扩成一份**能直接交给执行者**的描述：

```text
【一句话】做一个习惯打卡小程序：每天点一下，看连续天数。

【用户与场景】地铁上单手操作，打卡路径不超过 2 步；弱网可用；
             不做登录，用微信 openid 识别（这条要和后端确认）。

【正常例子】
- 新用户张三第一次打开 → 首页显示"今天还没打卡" + 一个主按钮；
  点一下 → 立即变成"已打卡 · 连续 1 天"
- 第二天打开 → 显示"已打卡 · 连续 2 天"，连续天数会随打卡增长

【边界/异常例子】
- 昨天没打卡、今天打卡 → 连续天数 = 1（重置，不显示 2）
- 23:59 打卡，00:01 再打开 → 算两天，不弹任何提示
- 同一分钟连点两次 → 只算一次，不报错
- 用户改手机时间 → 以服务端日期为准
- 断网时点击 → 先显示已打卡，网络恢复后同步，最终状态一致

【参照物】打卡日历的月视图像滴答清单，但不用颜色区分习惯类型。

【反向例子】v1 不做：社交排行、付费、消息推送、多习惯并行、数据导出。

【验收标准】把上面每条例子做成一条能回答"是/否"的检查项；
           全部为"是"才算 v1 完成。
```

这份描述比让 AI 扩写的三页 PRD 短得多，但**每一行都能判对错**。更重要的是：它 90% 的内容是只有你能提供的——用户在地铁上、v1 不做排行、跨零点算两天。**AI 扩写不出这些，因为它不知道你的产品边界在哪。**

## 四、左脚踩右脚：把一次生成变成四步循环

小王那句玩笑的实质是：**需求描述的正确性不来自单次生成的完备，而来自多轮迭代中歧义的收敛。**

所以不该"让 AI 写完就丢出去"，而该让它转起来：

```{mermaid}
flowchart TD
    A["你的口语原稿<br/>（可以很粗）"] --> B["① AI 反问<br/>先别写，问 10 个问题"]
    B --> C["你来回答<br/>（补例子、定边界）"]
    C --> D["② 带例子地生成<br/>例子 + 验收标准 + 假设清单"]
    D --> E{"③ 你当甲方挑刺<br/>多了 / 少了 / 擅自决定"}
    E -- "有 ❌" --> C
    E -- "全 ✅" --> F["④ 让执行者反向质疑<br/>换会话或换模型"]
    F -- "仍有歧义" --> C
    F -- "只剩实现细节" --> G["定稿，交给执行"]
```

### ① 先让它反问你（价值最大的一步）

不要一上来就要 PRD。第一句应该是：

```text
先别写需求文档。读完我下面这段原话，列出 10 个你没搞清楚的问题，
按"答错会导致返工的程度"从高到低排序。

我的原话：【……】
```

为什么这一步最值钱：**它在替你找歧义**。你自己都不知道自己哪里没说清——它一问就露出来了。而且这一步的输出极短，你读起来几乎没成本，不像读三页 PRD 那样需要消耗意志力。

判据：如果它一个像样的问题都问不出来，说明这个需求已经够清楚，后面全可以跳过，直接做。

### ② 让生成带着形状

第二轮才让它写，但要约束形状：

```text
按我的回答产出需求描述。规则：
1. 每条功能必须配一个具体例子（谁、做什么、看到什么）；
2. 每条功能必须配一条能回答"是/否"的验收标准；
3. 只写从我原话和回答里能得到的，别替我补功能；
4. 任何你不确定的，单独列"假设清单"，说明这条假设错了会影响什么；
5. 结尾列出"我不做的东西"（非目标）。
```

第 4 条是这类 prompt 里最容易被忽略、收益最高的一条：它把 AI 的"发明"改造成"澄清"，把隐性幻觉变成显性的待确认项。你会读到五六条"假设"，其中两三条你会点头——那就是它替你省下的返工。

### ③ 你当甲方挑刺（10 分钟，只抓三样）

不需要逐字读那一大段。只读三样就够，抓的也只有三样：

| 只看这三块 | 只挑这三样 |
|---|---|
| 功能清单 | **多了什么**——我根本没要的 |
| 每条功能的例子 | **少了什么**——我明明说过的 |
| 假设清单 | **替我做主了什么**——我不同意的假设 |

这个动作的成本被严重高估了。你不需要"读懂"那份文档，你只需要判决：这一条留、删、改。十分钟能过完一个 v1。

### ④ 让执行者反过来质疑（关键：换一个上下文）

最后一步是螺旋真正闭合的地方——**让将要执行的那一方，先吐一份"读需求后的疑问"**：

```text
你是要按这份需求开发的工程师。读完先别动手，列出：
1. 哪些地方你一定会回来问我；
2. 哪些要求自相矛盾或者做不到；
3. 哪些地方你打算自己猜（把猜测写出来）。
```

在群里这句话就是小王的实操版：让 workbuddy 在动手前先返一份疑问清单，比你事后看一个"感觉不太对"的成品便宜得多。

**这一步必须换会话、换模型，或者至少换角色**。原因在[先让 AI 写需求文档](../coding/requirements-delegation.md) 2.2 节：同一个会话里，模型已经读过你的原始模糊表述，它会替你补全，你俩共同的不确定被悄悄变成了确定，而且你看不出哪一段是它补的。

### 收敛条件与两个反模式

**收敛判据**：连续两轮，④ 提出的问题只剩实现细节（"用不用缓存""接口要不要分页"），不再有需求歧义 → 定稿。

两个反模式：

- **别让起草者自己挑刺**：起草和评审同源，盲区一起盲。至少要换角色，最好换模型。
- **别无限螺旋**：两三轮就够。超过三轮还在改，说明需求本身没想清楚——那不是流程能救的，得回去想产品。

## 五、丢给下游时，附件比正文重要

把需求交给执行方（人或者 Agent）时，别只递那份定稿的需求描述。四样东西一起给：

1. **你的原始口语原稿**——它带着需求文档丢掉的语境和语气；
2. **需求文档**——编号化的功能、例子、验收标准；
3. **假设清单**——哪些是 AI 猜的，猜错了影响什么；
4. **你删掉的东西**——上一轮你判定为"多了"的功能，附一句为什么删。

第 1 项看着多余，其实最关键：**扩写会掩盖你的真实意图，例子和原话不会骗人。** 执行方在两份材料冲突时，能看出哪一处是 AI 补的、哪一处是你亲口说的。

## 六、什么时候不用这么麻烦

这套流程有成本，别对所有需求都用。

| 场景 | 做法 | 理由 |
|---|---|---|
| 一句话、零歧义（改个文件名、加个参数） | 直接做 | 写文档纯属仪式感 |
| 做完就丢、只这一次 | 三行复述即可 | 例子是为了复用和验收，一次性任务用不上 |
| 要跨会话、跨模型、跨人传递 | 本文这套：例子 + 验收标准 + 假设清单 | 文档是唯一不衰减的载体 |
| 需求本身就是要交付的东西（做测试、做验收） | 再加 ④ 反向质疑 + 用例化 | 需求直接变成测试资产 |

这套分档和[先让 AI 写需求文档](../coding/requirements-delegation.md) 里的 L0～L3 是同一套东西：**歧义越密、返工越贵、越要跨边界，就越值得花那十分钟。** 而例子是其中投入产出比最高的一种投入——它既压缩了描述，又顺手产出了验收标准。

## 七、结论

三句话收尾：

> **形容词是给 AI 留了解释权，例子是把解释权收回来。**
>
> **AI 写需求最大的风险不是写得差，是写得太像真的，而你又没看。**
>
> **所谓左脚踩右脚螺旋飞天，本质是承认一次生成不可能完备——所以把"我不满意的地方"变成下一轮的输入，直到争议只剩下实现细节。**
