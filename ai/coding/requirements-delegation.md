# 直接把需求丢给 AI，还是先让它写一份需求文档？

```{contents}
```

## 引子：一个真实的提问

这篇文章的起点是一次真实的提问，原话照抄：

> 写篇文章描述一下，如果要让 AI 做一个事，我是直接把需求标准给他，让他做，还是让 AI 先根据我的需求生成一个具体的需求描述文档，再把这个描述文档发给 AI。这个流程默认会存在吧？

三句话，三个判断。本文就按这三个判断展开：

| 提问里的判断 | 本文的回应 | 在哪一节 |
|---|---|---|
| 「直接把需求标准给他，让他做」 | 成立，但等于把**判断权**让给了模型的隐式理解 | 二、四 |
| 「先让 AI 生成需求描述文档，再把这个文档发给 AI」 | 成立，但**发给谁**决定了这一步到底有没有意义 | 2.3、三 |
| 「这个流程默认会存在吧」 | 对，而且无法不存在——你只能选择它**可不可见** | 一 |

第三个判断是整篇的钥匙。它把问题从一个二选一，改成了一个更准确的问法：

> **要让 AI 做一件事，你对需求的"理解与规格化"这一步，是留在模型脑子里，还是捞出来放到桌面上？**

先把这个流程为什么躲不掉说清楚，剩下的选择才有意义。

## 一、"默认会存在"是对的，而且无法不存在

### 1.1 从生成机制看：产出第一个字符之前，它已经"想好"了

大模型是自回归的：一次只出下一个 token，而每个 token 都条件于前文。这意味着在它写出第一行代码、第一个标题之前，它对"这次要交付什么、按什么标准交付"已经形成了一个很可能已经收敛的内部表征——否则它没法决定第一个词是什么。

「思考」类模型把这一步外显成 reasoning，普通模型把它压缩在一次前向里。所以"直接给需求让它做"从来没有跳过这一步，只是**不让这一步落盘**。

### 1.2 从 Agent 的循环看：plan 是 act 的前置动作

Agent = 模型 + 工具 + 循环。任何像样的循环都是 `观察 → 规划 → 行动`，规划这一步就是对需求的再描述。DSH 的 plan mode、Claude Code 的 plan mode、Codex 的 plan，本质都是同一件事：**把这个本来转瞬即逝的中间态冻结成文件，塞到你眼前**。

它们不是新增了一道流程，是把本来就存在的步骤变得可审阅。

### 1.3 证据：即使你不要求，它也会留下碎片

注意观察只给一句需求时，Agent 会留下什么：

- 开工前的待办列表（"我打算做这 4 件事"）；
- 文件里的注释和命名；
- commit message；
- PR 描述。

这些全是"需求文档"的碎片。它们只是散落在各处、没有编号、没有验收标准、没人审过，而且互相可能不一致。**所以问题从来不是"有没有隐式的需求描述"，而是"隐式的、碎片化的那一份，还是要一份显式的、可对账的那一份"。**

### 1.4 一张图

```{mermaid}
flowchart TD
    R["你的原始需求<br/>口语、含糊"] --> U["理解 + 规格化<br/>（必然发生）"]
    U --> P["执行 / 产出"]
    U -. "可选：落盘" .-> S["需求文档<br/>编号 + 验收标准 + 边界"]
    S -. "人工裁决后作为唯一输入" .-> U2["理解 + 规格化<br/>（第二遍，基于文档）"]
    U2 --> P2["执行 / 产出"]
```

虚线部分才是你的选择。实线部分，没有讨论余地。

## 二、真正的区别不是"几步"，是"中间产物归谁"

把"直接给"和"先写文档"当成两种流程，容易得出"多一步就是多一层开销"的错误结论。更准确的分类是按**中间产物在谁手里、过不过你的眼**来分档：

| 档位 | 做法 | 额外成本 | 中间产物状态 | 典型失效 |
|---|---|---|---|---|
| **L0 单轮委托** | 一句话需求直接丢，做完再看 | 0 | 只在模型上下文里，随会话消失 | 隐性假设被当成事实执行；走偏了才发现 |
| **L1 复述确认** | "先别做，用三行复述你理解的需求" | 一次确认 | 在对话里，不落盘 | 复述太笼统，等于走过场 |
| **L2 需求文档落盘** | AI 起草 `requirements.md`，你审改后再执行 | 一次人眼审阅 + 一版文档 | 文件，可版本化、可复用 | **AI 把你的含糊扩写成具体，且看起来很像真的** |
| **L3 文档 + 独立评审** | L2 再加一轮异构模型/评审员挑战 | 一次额外调用 | 文件 + 评审记录 | 评审和起草同源，盲区一起盲 |

档位越高，"事前纠偏"的比重越大，"事后返工"的比重越小。**L2 的收益来自一次人眼审阅抵掉 N 次返工**：返工越贵、N 越大，L2 越划算；改动越便宜、越可逆，L2 就是纯粹的仪式感。

用一个具体的对比：

- **该 L0**：「把 `log_parse.py` 里那个时间戳正则从 `[\\d/]+` 改成 ISO8601」。需求零歧义，写文档纯属浪费。
- **该 L2**：「把上传接口优化一下，大文件要快一点」。这句话里"优化""快一点""大文件"三个词全是分歧入口，直接执行等于赌博。

### 2.1 决定档位的是四个量，不是任务大小

- **歧义密度**：需求里有多少不可判定的词（"好一点""规范点""性能好""适当处理"）。密度高就往 L2 走。
- **返工成本**：做错了要多久才能发现、多久才能改回来。不可逆的（数据迁移、发版、对外接口）直接上 L2。
- **可复用性**：这件事要重复做 N 次、还是做给 N 个仓用。文档是一次性投入、N 次摊销。
- **可交接性**：需求要跨会话、跨模型、跨人传递时，文档是唯一不衰减的载体。

### 2.2 一个被忽略的成本项：上下文污染

L2 如果和起草在**同一个会话**里做，有一个隐藏缺陷：模型已经读过你的原始模糊表述，它起草文档时会"替你补全"——它知道你在想什么，所以文档看起来很完整，实际上把你俩共同的不确定**悄悄变成了确定**，而且你看不出来哪一段是它补的。

所以更准确的说法是：**需求文档的价值，和它隔离掉了多少脏上下文成正比。**

### 2.3 回答"再把这个文档发给 AI"——发给谁？

这是提问里最容易被跳过、但最决定成败的细节：

- **发回同一个会话** → 基本白做。模型上下文里还留着原始模糊表述，它会继续按那个理解走，文档只是个装饰。
- **发进新会话（干净的上下文）** → 这才是文档真正的用法。文档成为唯一输入，隐式假设无处藏身。
- **发给另一个模型/另一个 Agent** → 额外获得一次"不同先验"的检验，`AGENTS.md` 之类的项目约定也会被重新读一遍（互相矛盾的文档在这里会露馅）。

一句话：**需求文档不是写给你看的，是写来跨会话边界搬运的。** 不跨越边界，它就只是个仪式。

## 三、最大的坑：让 AI 写需求文档，它会"发明"你的需求

这一节是本文最想说的部分。

让 AI 起草需求文档，最大的风险不是写得差，而是**写得太好**。

你的需求：「做一个文件上传接口，大文件要快一点。」

它起草的文档：「R3 支持断点续传；R4 单文件上限 10GB；R5 平均上传速度不低于 50MB/s；R6 支持 8 路并发分片。」

你既没说过 10GB，也没说过 50MB/s。它把"快一点"这一个形容词，翻译成了三个带单位的数字，而且格式规范、语气自信、结构完整——**看起来像是某次需求评审的产物，其实是一次凭空补全**。

这就是问题的核心：

> **需求文档的自信程度，和它的正确程度，没有任何相关性。**

更糟的是它的二阶效应：如果你不审，这份文档会变成验收标准。当实现达不到 50MB/s，它可能去堆分片、压缩、CDN——这些复杂度是为一个**从未存在过的需求**付的账单。而文档还会被存档、被复用、被下一轮当成"事实"继承下去。**错误被固化了。**

### 3.1 修法：把"扩写"约束成"澄清"

同样一句"帮我写需求文档"，加五条约束，输出的性质就完全不同：

```text
根据我下面这段需求，产出一份需求文档。规则：

1. 只写从我原话里能直接得到的，以及我能从原话里必然推出的。
2. 任何你不确定的地方，写进「待确认」区，并写清楚不同答案会把方案带向
   哪个方向。不要替我做决定。
3. 每条需求给编号 + 优先级 + 一条可判定的验收标准。
   验收标准必须是能回答"是/否"的句子，不能是形容词。
4. 单独列出我原话里互相矛盾、或者彼此有张力的地方。
5. 不要写实现方案。这是约束，不是建议。
```

关键在规则 1 和 2：**允许它说"我不知道"，并且把"我不知道"变成对你有用的形式**。同一句"大文件"，合格的输出是：

```text
R4 [待确认] 「大文件」的边界需要你定：
  - 如果是 10MB 级：普通分片上传就够，不需要断点续传
  - 如果是 1GB 级：需要断点续传 + 秒传
  - 如果是 10GB 级：还要考虑对象存储直传、临时凭证
  这三种方案的工作量差 5~10 倍，请先确定。
```

这份输出比一份"完美"的需求文档有用得多——它不是替你做了决定，而是把决定的代价摆到了你面前。

规则 5（不写实现）同样重要。需求里一旦混进"用 Redis 做缓存"这种实现决策，你就把执行者更好的方案一并锁死了；而且以后分不清"这是需求"还是"这是当时随手写的办法"。**需求文档管「要什么」和「怎么算做到」，不管「怎么做」。**

## 四、什么时候该升级，什么时候纯属自找麻烦

### 4.1 该升级的信号（命中两条以上就上 L2）

- 需求里出现了这些词：好一点、快一点、规范点、健壮一些、适当处理、类似 XX 那样；
- 交付物是**多文件改动、大重构、对外接口**，错了不便宜；
- 你要为结果**签字**（给领导汇报、给客户交付、上线评审）；
- 这件事要**重复做**，或者要**交给别人/别的模型**做；
- 你要用结果去**测别的东西**（见 5.3）；
- 你在写需求的时候，自己就开始犹豫"到底要不要包含 X"——这种犹豫必须在文档里显式化，否则它会变成执行者的随机选择。

### 4.2 不该升级的信号

- **一次性、可逆、便宜**：改个 typo、换个配置、跑条命令。文档的固定成本（写 + 读 + 维护）已经超过收益。
- **探索性任务**：目标本身就是"先做出来看看"。这时候正确的中间产物不是需求文档，是**原型**。给探索任务写需求文档，等于在还不知道要什么的时候假装知道。
- **需求已经结构化且你比它清楚**：你手里就有带编号、带验收标准的文档，那就直接喂，别再让它重写一遍——重写只会引入信息损耗。

### 4.3 一条经验法则

> 需求文档的成本是一次人眼审阅，收益是「把 N 次事后返工换成 1 次事前纠偏」。
> N ≥ 2 就值得做；N = 1 且返工便宜，就不值得。

## 五、三档落地姿势

### 5.1 轻量：三行复述（覆盖 60% 的场景，几乎零成本）

不想维护文档，但又怕走偏时，用这个：

```text
先不要动手。用不超过五行说清楚：
1. 你认为我要的最终交付物是什么（具体到文件/格式）；
2. 你认为的验收标准是什么；
3. 你现在最不确定的两点是什么。
等我确认。
```

第 3 条是灵魂。多数走偏不是因为它做错了，是因为它把不确定的地方按默认值填了，而你不知道它填了什么。让它主动交代不确定点，等于用五行换掉了大部分 surprise。

### 5.2 中量：`requirements.md` 进仓库

把需求文档当代码管理：进 git、有版本号、后续修改走编辑而不是重新生成。好处不止是给 AI 看：

- 它是**人类之间的单一事实源（SSOT）**，冲突时以文档为准而不是以聊天记录里最新那句为准；
- 它天然支持增量修改（改一行 vs 重画一张图）；
- 它能被 diff、被 review、被回溯"当初为什么这么定"。

篇幅一长，必须配**编号 + 验收标准 + 冲突裁决规则**，具体写法见 [如何向 AI 提需求](./requirements-prompting.md)——那篇讲的是"人写需求"，这篇讲的是"AI 起草 + 人裁决"，是同一套 SSOT 思想的两个入口。

### 5.3 重量：把需求文档当成被测对象（做测试的人应该最敏感）

如果需求文档真的写对了，它就是一个**客观、稳定、可复现的输入**。这直接打开了三件测试领域的老办法：

1. **横向对比**：同一份需求文档喂给不同模型/不同 Agent 配置，比谁的产出更接近验收标准。这是最便宜的能力评测——输入固定，只变被测对象。
2. **回归锚点**：换模型、改 prompt、升级框架之后，需求文档不变，于是产出差异可以被归因到被测对象上，而不是"这次需求说得不一样"。
3. **变更影响分析**：改了需求文档的哪一条，产出应该变哪里。这条对不上，说明**需求到实现的链路断了**——这是最有价值的信号。

反过来说，如果需求文档靠 AI 现编、每次都不同，上面三件事一件都做不了。**可测试性要求输入稳定，而稳定的输入必须是人裁决过的。**

顺带一提，这套流程在 Agent 团队里已经被工程化成硬门禁了：任务分 `requirements → implementation → verification → review`，`requirements` 不过，实现根本不许开始；每个质量任务都必须挂 objective + 可判定的 acceptance + verify 命令。这就是 L3 的固化形态，见 [用 DAG 编排 Agent 团队](../agent-engineering/dag.md)。

## 六、需求文档该写什么

| 该写 | 不该写 |
|---|---|
| 目标：这件事解决什么问题 | 实现方案：用什么库、什么结构 |
| 验收标准：能回答"是/否"的句子 | 形容词："高性能""易用""规范" |
| 边界与非目标（out of scope） | 你还没想清楚的细节（那是「待确认」） |
| 约束：技术、合规、时间、兼容性 | 上一轮的主观偏好（"我觉得这样好"） |
| 优先级 + 冲突裁决规则 | 复数来源互相打架的"参考" |
| 「待确认」区 + 每项的方案影响 | 假装确定 |

最后一行值得展开：**非目标（"这次不做 X"）比目标还能约束质量**。没有非目标，执行者会顺手"做好一点"，而那些顺手做的东西往往正是复杂度和 bug 的来源。

对应到写完文档之后的自检：把文档里所有形容词圈出来，逐个问"这句话怎么判定？"——答不上来的，就还没到能交给执行的程度。

## 七、结论

回到最初那个问题：

**「这个流程默认会存在吧？」——存在，而且躲不掉。**

`观察 → 理解 → 规划 → 执行` 是 Agent 的物理结构，不是可选项。所有"直接给需求"的做法，都是选择把"理解与规划"留在模型脑子里的那几秒里；所有"先写需求文档"的做法，都是选择把它捞出来给你看一眼。

所以真正要回答的是三个更小的问题：

1. **这次需求，歧义够不够多？** 少 → 直接给，配三行复述；多 → 落文档。
2. **我能不能拿到一份干净的、只含需求的输入？** 不能（还发回同一个会话）→ 这步别做，白费；能（新会话/换模型）→ 值得做。
3. **我要不要用它来测别的东西？** 要 → 必须落盘、必须人裁决、必须版本化。

一句话收尾：

> **不是新增一道流程，是同一个流程的成本降下来之后，原本只在大型项目里做的动作，现在每次任务都做得起了。**
>
> 直接给 = 赌它隐式理解对了；先要文档 = 花一次你的眼睛，换掉后面所有返工。
>
> 而让 AI 起草文档时，你真正要盯的不是它写得够不够全，是它有没有把"不知道"伪装成"知道"。
