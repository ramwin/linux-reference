## 引子：同一个任务，两种喂法

设想一个改动：给「下单」接口加一条优惠券叠加校验。

- **喂法 A**：把 `order/`、`coupon/`、`db/models.py` 整目录贴给模型，8000 行、约 10 万 token。
- **喂法 B**：先给一份仓库地图（每个模块一行签名），让它自己 `grep apply_coupon`，读 3 个文件共 180 行。

B 的输入大约是 A 的三十分之一，改动正确率通常还更高——不是因为模型变聪明了，是因为 B 的上下文里没有干扰项。

这个差距值得拆开讲清楚，因为它跟「模型有多强」关系不大，跟**你怎么组织代码、怎么发起对话**关系极大。而这两件事今天就能改，不用等下一代模型。

## 一、先把前提修一下：不是「越少越好」

「AI 知道的信息越少越准确」——这半句话对，也容易带偏。

对的那半句是：**与当前这一步无关的信息是纯负担，不是"顺便看看"。**

需要修的是另一半：**信息少本身并不产生准确，产生准确的是"每一步都恰好只有此刻需要的信号"。** 把"少"当目标，会掉进另一个坑——AI 缺了约束，开始编造，然后你花三倍 token 去修。

把上下文体积当横轴、任务正确率当纵轴，形状是倒 U：

```{mermaid}
flowchart LR
    A["信息太少<br/>靠猜：编造、重造轮子"] --> B["最小充分<br/>契约 + 按需实现"]
    B --> C["信息太多<br/>稀释、干扰、中段遗忘"]
    A -.- A1["正确率低<br/>返工多"]
    B -.- B1["正确率高<br/>token 少"]
    C -.- C1["正确率中<br/>token 高"]
```

左半边是「猜」区：模型不知道你的错误处理约定、不知道这个模块的不变量、不知道库里已经有个同名工具函数，于是自造一套——语法正确、逻辑自洽、看起来能跑，实际要返工。

右半边是「稀释」区：后面第二节给证据。

中间那段才是目标。业界的措辞是「最小高信号 token 集」。Anthropic 在 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 里的原话是：

> find the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome.

注意是两个限定词：**smallest** 和 **high-signal**。只满足其中一个都是错的。

## 二、多余的上下文是负收益，不是零收益

很多人默认"多给点总没坏处"。下面五条证据说明，多余信息会主动拉低结果。

### 2.1 注意力是预算，不是硬盘

Chroma 的 [Context Rot](https://www.trychroma.com/research/context-rot) 报告（2025 年 7 月）做了一个很干净的实验：**固定任务难度，只变输入长度**，跑了 18 个模型，包括 GPT-4.1、Claude 4、Gemini 2.5、Qwen3。

结论是全部随输入变长而性能下降——连"把一串重复单词原样复述"这种幼稚任务都不例外。

原因在架构里：注意力是 n² 的两两关系，序列越长，每一对的权重越摊薄；而训练数据里长序列本来就少，模型没有足够经验处理远距离依赖。Anthropic 的说法是模型有一份「attention budget」，每多一个 token 都在花它。

对写代码的直接含义：你贴 3000 行无关代码，不是"多看了点东西"，而是**接下来每一次请求都更贵、更钝**。

### 2.2 无关内容会强迫模型同时做两件事

同一份报告里有个更贴切的实验，基于 LongMemEval：同一段对话历史，两种给法——

| 给法 | 体积 | 结果 |
|---|---|---|
| focused（只给相关片段） | ~300 tokens | 好 |
| full（给完整历史） | ~113k tokens | 所有模型显著更差 |

关键不在"长的更差"，在**为什么**：full 版本里模型必须先「找到相关部分」再「用相关部分推理」，两个动作抢同一份注意力预算。focused 版本只需要推理。

映射到代码：当你把整个 `service/` 目录贴过去，你其实是在要求模型先做检索、再做设计。而检索这一步它做得很差（没有结构信号），于是**检索的失败会被你误读成设计能力不足**。

### 2.3 干扰项比无关项更毒

报告还专门测了 distractor——和答案沾边但不对的东西。**一个**就能拉低准确率，四个叠加更糟。

你仓库里的 distractor 长这样：

- 三年前那版 `OrderService`，还留着，没人删
- `utils/` 里和 `helpers/` 里两个几乎一样的 `format_date`
- 注释掉的旧实现
- 名字接近语义不同的 `get_user` / `get_user_info`

这解释了一个常见现象：**在有历史包袱的仓库里，AI 更容易"改错地方"**。它不是看不懂，是选错了目标。对这类问题，最有效的动作不是改提示词，是把死代码删干净。

### 2.4 长上下文的中段会被跳过

[Lost in the Middle](https://arxiv.org/abs/2307.03172)（Liu et al., TACL 2024）测的是位置效应：相关信息放开头或结尾时模型表现最好，放中间显著变差，即使总长度在窗口内。多文档 QA 里，当答案落在中间，GPT-3.5-Turbo 的表现甚至低于"不给文档直接答"。

工程含义很直接：**重要约束放在上下文的开头或结尾**。你的项目约定、禁止事项、"不要动 `payment/`"，别埋在一大段代码中间。

### 2.5 附带的账：上下文是按步计费的

这一点常被忽略。多轮对话里，第 k 步的输入包含前 k−1 步的全部内容。所以**开头塞进去的 3000 行，会在之后每一步被重新计费一次**（prompt cache 能打折，但打的是单价，不是次数）。

换个说法：上下文膨胀的成本是**累积的**，而"让 AI 自己 grep 一下"的成本是一次性的。这是"少给"最直接的经济学理由。

小结一句：上下文不是仓库的镜像，是工作记忆。工作记忆有容量代价。

## 三、但「少」有下限：实现可以省，契约不能省

这是最容易搞错的地方。AI 用到一个模块时要的信息分两类：

| 类型 | 例子 | 能不能省 |
|---|---|---|
| 实现细节 | 内部用什么数据结构、循环怎么写、私有函数叫什么 | **能，而且应该省** |
| 契约 | 出参含义、异常、副作用、幂等性、线程安全、性能量级、前置条件 | **不能省** |

省实现省钱；省契约让模型编造。而模型编造出来的东西通常语法正确、逻辑自洽，所以最难发现。

一个具体的失败模式：模块内部对参数做了归一化（`None` 当空串处理），但接口没写。AI 在调用侧写了 `if x is None: raise`，单测通过，线上行为变了。AI 没错，它只是没被告知。

所以真正要设计的不是"藏多少"，而是**契约写在哪、写多清楚**。这是下一节的事。

## 四、真正的杠杆：把「预加载」换成「按需求取」

### 4.1 地图便宜，内容贵

先看数量级（按你自己的仓库估）：

| 供给方式 | 覆盖范围 | token 量级 |
|---|---|---|
| 整个仓库源码 | 全部 | 10⁵ ~ 10⁶ |
| 每个模块的入口签名 | 全部 | 10³ |
| 单个模块的完整实现 | 一处 | 10³ ~ 10⁴ |

差 2~3 个数量级。也就是说，**"让 AI 知道有什么"的成本，只有"让 AI 读完所有东西"的千分之一**。

这不是理论。[aider](https://aider.chat/docs/repomap.html) 就把这个想法工程化了：用 tree-sitter 抽出全仓的类和函数签名做成 repo map，**默认预算只有 1k token**，每次请求随对话一起发过去。它的文档里有一句值得抄下来的话：

> The LLM can see classes, methods and function signatures from everywhere in the repo. This alone may give it enough context to solve many tasks. For example, it can probably figure out how to use the API exported from a module just based on the details shown in the map.

「只看签名可能就够解题」——你说的「封装成模块让 AI 只看入口声明」，就是这句话。它不是偷懒，是被生产工具验证过的默认策略。

### 4.2 按需加载要成立，需要两个前提

「让 AI 自己判断该看哪些模块」听起来很美，但只有在两件事同时成立时才省钱，否则会退化成盲目乱翻：

1. **索引**：AI 能低成本地知道"存在什么"。文件树、目录名、README 索引、签名列表、`AGENTS.md` 指针——选哪个都行，但必须有。
2. **检索**：它能把"我要找的东西"变成一次精确查询。`grep` 函数名、`glob` 模式、LSP 找引用。

缺索引，它只能扫；缺检索，它只能猜。两者都缺，"按需加载"就变成"反复试错"，比直接喂全仓更贵。

这也正是 Claude Code 的做法：`CLAUDE.md` 先塞进上下文（一份薄索引），再加上 `glob` / `grep` 这类原语做 just-in-time 检索，绕过"预建索引会过期"的问题。

四种供给模式的性价比：

| 模式 | 代表做法 | token | 准确率 | 适用 |
|---|---|---|---|---|
| 全量塞 | 粘贴整个目录 | 极高 | 中（被稀释） | 极小的仓库、一次性脚本 |
| 预建索引 | repo map / 语义索引 | 低 | 高 | 中大仓库、反复协作 |
| 地图 + 按需 | 薄索引 + grep 下钻 | 低 | 高 | 大多数工程场景，**推荐** |
| 盲搜 | 什么都不给，让它自己翻 | 中高 | 低（找不到就编） | 不推荐 |

## 五、把代码库改成「可被导航」的形状

前四节是"怎么读"，这一节是"怎么写"：**代码结构本身决定 AI 能不能只读一小块就动手**。

### 5.1 模块要深：小接口，大实现

先固定一组词，后面反复用：

- **模块**：有接口、有实现的东西。函数、类、包、跨层切片都算。
- **接口**：调用方要正确使用它必须知道的一切——不只是类型签名，还包括不变量、顺序约束、错误模式、必要配置、性能特征。
- **深度**：接口上能撬动多少行为。接口小而实现厚的，是深的；接口和实现一样复杂的，是浅的。

反例（浅模块，AI 必须读实现才敢用）：

```python
# utils/order.py
def calc(o, c=None, f=False, t=None):
    ...
```

正例（深模块，读签名就能用）：

```python
# order/pricing.py
def final_price(order, coupon=None) -> Money:
    """计算订单最终应付金额（含优惠券、运费、税）。

    Args:
        order: 已持久化的订单，必须处于 CREATED 状态。
        coupon: 已通过 validate_coupon 校验的优惠券，可为 None。

    Returns:
        最终金额，非负；单位与 order.currency 一致。

    Raises:
        InvalidStateError: order 不在 CREATED 状态。
        CouponExpiredError: coupon 已过期（此处不静默忽略）。

    Notes:
        纯函数，无副作用，可重复调用。
        复杂度 O(len(order.items))，不含任何 IO。
    """
```

差别的本质：前者把五个参数的含义、默认值语义、边界行为都藏在实现里；后者把这些搬进了接口。**对 AI 来说，这是一次可能省掉两百行读取的差别**；对人类来说差别一样大，只是人类会靠经验蒙混过去。

有个简单的检验方法（设计圈叫删除测试）：**把这个模块删掉，复杂度会消失，还是在 N 个调用点重新长出来？** 会消失说明它只是个传声筒（pass-through），没帮你压缩任何信息，它的存在反而给 AI 多一层要跳过的目录。

落到工程上还有两个小动作，能让「只看入口声明」有唯一、稳定的落点：

- **包入口只导出公共 API**（`__init__.py` / `index.ts` 里显式 `__all__`），内部模块一律 `_` 前缀或收进 `internal/`。否则 AI 得自己猜哪个文件算"入口"。
- **模块级 docstring 写一句职责边界**（"只做金额计算，不碰持久化"），这句话是 AI 判断"要不要进来读"的第一道依据。

### 5.2 接口即契约：注释写给「要调用它的人」

给 AI 看的接口注释和给人看的不一样：人靠上下文补全，AI 不会。下面几条必须显式写：

| 必须写 | 不写会怎样 |
|---|---|
| 前置条件 / 状态要求 | 它会拿任何状态去调 |
| 抛什么异常、什么时候抛 | 它会写 `try/except Exception` 一把抓 |
| 副作用（写库、发消息、改入参） | 它会以为可以随便重试 |
| 幂等性 / 线程安全性 | 它会在并发路径里复用 |
| 性能量级（是否 IO、复杂度） | 它会在循环里调你 |
| 相关函数（"先调 `validate_*`"） | 它跳过校验直接调核心 |

一个反直觉的建议：**文档宁短勿假**。注释和代码不一致时，AI 会相信注释（它没法验证），然后按错的写。宁可少写，也别留不维护的注释；更稳的做法是让测试表达契约（见 5.5）。

### 5.3 目录即地图

AI 拿到的第一个结构信号是文件树，所以**路径必须携带信息**。

两种拆法对比：

```
# 技术分层
src/
  controllers/   services/    repositories/
  models/        utils/       helpers/       common/

# 领域划分
src/
  order/     pricing.py  submit.py  refund.py  README.md
  payment/   gateway.py  reconcile.py  README.md
  coupon/    validate.py  apply.py    README.md
```

第一种，AI 想知道"下单涉及哪些文件"，得读遍三层目录才能拼出边界；第二种，一行路径就给了答案。

关于 `utils/`：它是 AI 的死角。一个什么都装的目录，等于告诉 AI「这里有四十个函数，慢慢找」。按用途拆开（`format/`、`retry/`、`time_parse/`），或者干脆并进它服务的领域目录。

### 5.4 分形文档：根文件只放指针

`AGENTS.md` / `CLAUDE.md` / `README.md` 的职责是**告诉 AI 去哪找**，不是**替 AI 把内容读完**。

| 放什么 | 例子 | 长度 |
|---|---|---|
| 一句话定位 | "Go 服务，读写 PostgreSQL" | 1 行 |
| 命令 | 装依赖、跑测试、跑 lint 的准确命令 | 3~5 行 |
| 目录地图 | "改计费看 `billing/`，改调度看 `scheduler/`" | 5~10 行 |
| 硬约束 | "不要引入新依赖"、"错误统一用 `pkg/errs`" | 3~5 行 |
| 指向细节的链接 | "细节见 `billing/README.md`" | 若干 |

反模式：五百行的 `AGENTS.md`。它每次请求都进上下文，又长又沉，而里面九成内容跟当前任务无关——这是自己给自己制造 context rot。

正确形态是**分形的**：根目录一份薄索引，每个一级目录一份局部规则，规则离它约束的代码越近越好。AI 改 `billing/` 时读 `billing/README.md`（30 行），改 `coupon/` 时读 `coupon/README.md`，永远只付它需要的那一份。

### 5.5 用测试买「可验证」

这条被严重低估。判断"我改对了"有两条路：读实现去推理，或者跑测试看结果。前者对 AI 是 O(代码行数)，后者是 O(输出行数)。

所以测试对 AI 的价值不只是防回归，更是**一份不用读懂就能确认的契约**。一个 20 行的测试，往往比 300 行的实现更能说明"这个函数承诺了什么"，因为它把模糊的自然语言变成了确定的输入输出对。

配套要求：测试要能单独跑（`pytest tests/test_pricing.py::test_coupon_stacking`），不要"必须启全套环境才能验"。AI 的反馈回路越短，它试错越省 token——这一条对 token 的影响可能比任何提示词技巧都大。

### 5.6 消灭「只能靠读实现才能推断」的隐式性

有些写法对人类老手友好，对 AI 是陷阱，因为它们把意图藏进了运行时：

| 写法 | 后果 |
|---|---|
| 动态导入 / 字符串拼模块名 | 静态分析看不到调用关系，AI 不知道谁在用谁 |
| 装饰器注册表（`@register("x")` 散落各处） | 找不到"到底注册了什么"，只能全仓搜 |
| 隐式全局单例 / 启动时注入 | 依赖关系不可见，AI 会假设它是显式参数 |
| 猴子补丁 | 与源码不一致，AI 读到的不是运行时的东西 |

判据一句话：**能被静态推断的，就不要依赖运行期魔法。** 同样的道理适用于类型标注——类型是全项目最便宜、最不会撒谎的文档，而且 LSP 和 AI 都能直接吃。

（不必消灭一切魔法，框架层有时值得。折中是：把魔法集中到一两个明确的入口文件，并在 `AGENTS.md` 里写一句"魔法只在这里，别的地方都是直白代码"。）

## 六、会话侧：每次让 AI 怎么读

结构改好了，还要把"读法"固化下来。

### 6.1 三级下钻，别跳级

```{mermaid}
flowchart TD
    Q["需求"] --> M["看目录地图 / grep 定位"]
    M -->|候选模块| I["读入口签名与契约"]
    I -->|够用| E["动手改"]
    I -->|不够| D["下钻读实现片段"]
    D --> E
    E --> T["跑测试 / 构建"]
    T -->|失败| D
    T -->|通过| F["交付"]
```

没有 repo map 工具也能做第 0 级：`grep -nE '^(def|class|func|type|export) ' file.py` 先看一眼骨架，往往比从头读起省一个数量级。

一个好的开工提示词，可以直接改改就用：

```
先别改代码。按这个顺序给我信息：
1. 定位和 <需求> 相关的模块，只看导出符号和函数签名，列出候选文件。
2. 说明每个候选文件在这个需求里的职责，以及我必须知道的契约
   （异常、副作用、幂等性、状态要求）。
3. 指出你认为必须读实现的文件，并说明理由。
我确认后你再动手。
```

模板的价值不在措辞，在**它强制分阶段**。你一次性说"帮我改 X"，模型会一次性读完它能读的所有东西。

### 6.2 子 agent 隔离：读十万，回一千

需要跨多模块调研时（"这个功能涉及哪些文件"、"这段逻辑被复制在哪些地方"），别在主对话里翻。

做法是起一个子 agent，让它去读、去搜、去试，只把结论带回来。Anthropic 的描述是子 agent 可以消耗几万 token 探索，但只返回 1000~2000 token 的蒸馏摘要。

对主对话的意义：**调研的噪声留在子 agent 的上下文里，主对话只留结论**。这也是我这边两个委派工具的用法分野：完全独立的活（调研、审计）用 `subagent`，需要继承当前对话的活（基于刚才的讨论继续）用 `subagent_fork`。

### 6.3 让上下文能「卸货」

长任务别指望一个上下文撑到底，三个手段：

- **写笔记**：把已确认的事实落到 `NOTES.md` 或 todo 里，而不是指望它一直记着。
- **压缩**：接近上限时，让它总结"架构决策、未解决的 bug、实现细节"，丢掉冗余的工具输出。
- **重开**：任务切换时新开会话，用一份十行的交接摘要开头，比拖着一个沾满旧任务的上下文干净得多。

## 七、反模式清单

| 反模式 | 为什么坏 | 改法 |
|---|---|---|
| 一上来贴整个目录 | 中段被忽略，检索和推理抢预算 | 先给地图，让它按需拉 |
| 写五百行 `AGENTS.md` | 每次请求都背这个包袱 | 根文件只留指针，规则下沉到子目录 |
| 用 `utils/` 当垃圾桶 | 没有语义，AI 只能全看 | 按用途或领域拆开 |
| 注释和代码不一致 | AI 相信注释，按错的写 | 宁短勿假，契约交给测试 |
| 动态导入 + 注册表魔法 | 调用关系不可静态推断 | 集中魔法，其余写直白 |
| 参数名叫 `data` / `o` / `cfg` | 签名不携带信息，AI 必须读实现 | 名字即文档 |
| 拆得过细 | 一次改动要跨八个文件 | 按"变更边界"而不是"相同性"拆 |
| 一个任务拖到底 | 上下文越滚越脏 | 分阶段 + 子 agent + 交接摘要 |

第七条值得展开：**拆分有拐点**。模块越细，"只看一处就够"的比例上升，但"完整理解一条链路"要跨的文件数也上升。所以拆分的正确判据是**变更局部性**——一次真实的业务改动，期望它落在几个文件里？

落在一两个模块里，说明拆对了。总是要跨五六个，说明拆错了方向，而最常见的错因是**按技术角色（controller/service/repo）拆，而不是按业务能力拆**。

## 八、怎么量：别凭感觉

三四个指标就够，都能从会话记录里算：

| 指标 | 含义 | 取法 |
|---|---|---|
| token / 任务 | 绝对成本 | 会话记录里 usage 累加 |
| 无关读取率 | 读了但没改的文件 / 已读文件 | `read` 的路径对比实际改动路径 |
| 首轮通过率 | 第一次改动就通过测试的比例 | 记测试失败次数 |
| 返工轮次 | 同一任务内"改—失败—再改"的循环 | 数 `step` |

DSH 的会话记录是 zstd 压缩的 jsonl，一个脚本就能出数：

```bash
#!/usr/bin/env bash
# 用法: ./tok.sh <session.v4.jsonl.zstd>
# 文件在 ~/.dsh/sessions/<工作区目录>/<session-id>/ 下
zstdcat "$1" | python3 -c '
import sys, json
keys = ("inputTokens", "outputTokens", "cacheReadTokens", "cacheWriteTokens", "totalTokens")
tot = dict.fromkeys(keys, 0)
steps = reads = writes = 0
for line in sys.stdin:
    e = json.loads(line)
    if e.get("type") != "assistant/message":
        continue
    steps += 1
    usage = e["data"].get("usage", {})
    for k in keys:
        tot[k] += usage.get(k, 0)
    for b in e["data"]["message"]["content"]:
        if b.get("type") == "tool-call":
            if b.get("name") in ("read", "grep", "glob"):
                reads += 1
            elif b.get("name") in ("edit", "write"):
                writes += 1
avg = tot["inputTokens"] // max(steps, 1)
print(f"steps={steps}  reads={reads}  writes={writes}")
for k in keys:
    print(f"  {k:17s} {tot[k]:>12,}")
print("  每步平均输入      %12s" % format(avg, ","))
'
```

拿一个真实会话跑出来长这样（本仓库里一次 GUI bug 排查，62 步）：

```
steps=62  reads=2  writes=1
  inputTokens             62,950
  outputTokens            52,431
  cacheReadTokens      4,390,784
  cacheWriteTokens             0
  totalTokens          4,506,165
  每步平均输入             1,015
```

注意 `cacheReadTokens` 是 `inputTokens` 的七十倍——这就是"上下文按步计费"的实证：每一步都在重发前面所有内容。缓存让它便宜，但没让它免费，而且它依然占注意力。

真正该盯的是**读改比**。上例是 `reads=2 / writes=1`（纯排查，正常）。对一次正经的功能改动，理想区间大概是「读三到五个文件，改一到两个」。读到二十个才改一个，说明仓库对 AI 不友好，或者你的开场提示词没给方向。

## 九、按投入排的四档方案

| 档 | 做什么 | 投入 | 预期收益 | 建议 |
|---|---|---|---|---|
| L0 提问方式 | 先要地图再看代码；强制分阶段；调研丢给子 agent | 0 | token 降 30~50% | 立刻做，零成本 |
| L1 文档层 | 根 `AGENTS.md` 指针化 + 每目录 30 行 README + 接口 docstring | 半天 | 大幅减少"找错文件"和"凭空造轮子" | **推荐先做这一档** |
| L2 结构层 | 目录按领域重排、拆浅模块、清 `utils/` 黑洞、补类型与测试 | 数天到数周 | 最大且持久 | 挑最疼的一个目录试点 |
| L3 工具层 | repo map 生成、LSP 或语义索引接入 | 数天 | 大仓库才回本 | 万行以上再考虑 |

明确的建议：**先做 L0 + L1**，投入半天，当天见效，不碰代码逻辑。L2 不要整体重构，挑一个"每次改都跨五个文件"的目录试点，跑通了当样板再推。L3 等到仓库大到 `grep` 都嫌慢再说——过早引入索引，你还要维护它，那本身就是一个新的 distractor。

## 十、自检清单

对着自己的仓库打勾：

- [ ] 每个模块的入口签名，不看实现能否知道"它能干什么"
- [ ] 导出的函数写清楚异常、副作用、幂等性
- [ ] 目录名能直接回答"改 X 功能看哪里"
- [ ] 没有 `utils/`、`common/`、`helpers/` 这种黑洞
- [ ] 根 `AGENTS.md` 在 50 行以内，且大半是"去哪找"
- [ ] 一级目录有自己的 30 行 README
- [ ] 关键路径有能单独跑的测试
- [ ] 没有"只有跑起来才知道"的依赖注入或动态导入
- [ ] 公共接口的类型标注齐全
- [ ] 废弃代码删干净了（distractor）
- [ ] 一条典型业务改动，落在三个文件以内
- [ ] 上一个任务里，AI 读了几个文件、改了几个文件

最后两条最重要。**读二十个改一个 = 你的仓库对 AI 不友好；读三个改两个 = 刚刚好。**

## 结语

「让 AI 少读点」的真正含义，不是盼着模型聪明到不用读，而是**你把结构做对了，它只需要读一小块就够**。

而这件事的收益并不专属于 AI：一个能让 AI 只读三行签名就正确调用的模块，新人上手时也一样省事；一条能让 AI 自己跑通的测试，你半夜改代码时也一样救命。**上下文工程改造出来的代码库，本质上是"可导航性"更好的代码库**——AI 只是第一个把这件事的成本暴露出来的使用者。
